# Localization

`ani-gui` ships with four locales at MVP, chosen for markets where free-content tooling has the strongest organic demand:

| Locale | Code | Why this one |
|---|---|---|
| English | `en` | Lingua franca of anime fandom outside Japan |
| Brazilian Portuguese | `pt-BR` | Very large fandom; legal options expensive relative to local incomes |
| Latin American Spanish | `es-419` | Large fandoms across Mexico, Argentina, Chile, Peru; patchy legal catalog |
| Russian | `ru` | Crunchyroll exited Russia in 2022; legal options are sparse |

## How translation works

The frontend uses [Paraglide.js](https://inlang.com/m/gerre34r/library-inlang-paraglideJs). It compiles message bundles to type-safe TypeScript at build time — no runtime overhead, no missing keys at runtime, tree-shaken per-route.

Translation files live in `frontend/messages/`, one directory per locale and one file per surface:

```
messages/
├── en/
│   ├── app.json
│   ├── home.json
│   ├── play.json
│   ├── settings.json
│   ├── errors.json
│   ├── backend.json
│   └── …
├── pt-BR/...
├── es-419/...
└── ru/...
```

A message's name is its file's name, an underscore, and its key in that file: `close` in `window.json` is `window_close`, called as `m.window_close()`. `frontend/tools/build-messages.mjs` merges each locale's files into the single `messages/<locale>.json` Paraglide reads; that file is generated and not committed. The backend never returns localized text. Every error the app raises — as an HTTP error body or an SSE error event — carries a `kind` (`no_results`, `timeout`, `parse_failed`, …), a stable key (`error.search.no_results`) and the variant's own fields; the frontend resolves the key to a message of its own, falling back to the kind's coarser sentence — see [Backend error keys](#backend-error-keys). The surface-specific mappers in `frontend/src/lib/play/error-copy.ts`, `frontend/src/lib/download/failure-copy.ts` and `frontend/src/lib/settings/failure-copy.ts` carry copy of their own for the failures a surface says more about. The frontend never shows the error's `detail`, which is free text for logs. Not every failed request carries the envelope: a route the router does not know, a request the HTTP layer rejects before any handler runs, and the image route's refusal of a non-`https://` URL answer with no JSON body, so the API client keeps a fallback (`{ kind: 'http', status }`) for a body that is not the envelope.

## Backend error keys

The `key` on a backend error is the stable name of exactly what failed; the `kind` is the variant's name, which can group several keys (`scraper` answers with `error.download.tool_failed` or `error.download.tool_spawn_failed`). The keys the backend can answer with are published in `backend/error-keys.json`, which `cargo test` holds to the `AniError` variants.

`describeError` (`frontend/src/lib/play/describe-error.ts`, re-exported from `error-copy.ts`) chooses copy in three steps:

1. A field that says more than any one sentence per key could: an upstream's 404 or 410 (not found), 429 (busy) or 5xx (the service is down), and a rate limit's advertised wait.
2. The `key`. Each key has one message per locale in `messages/<locale>/backend.json`, named by the key with its dots as underscores: `error.metadata.source` is `error_metadata_source` in that file and `m.backend_error_metadata_source()` in code. A message may interpolate the envelope's structured fields — `error_network_upstream` takes `{status}`, the two spawn failures take `{binary}` — and never its `detail`.
3. The `kind`, when the envelope has no key, a key this build has no message for, or a keyed message whose field the envelope does not carry. The kind sentences live in `errors.json` (`reason_network`, `reason_timeout`, …); a kind without one gets `reason_generic`.

A renderer older than the backend's key list therefore shows the kind's sentence, not a blank. `tests/arch/error_keys.sh` fails CI when a key in `backend/error-keys.json` has no message in some locale's `backend.json`, when a locale carries a message answering no key, or when a message is empty.

Adding a backend error key:

1. Add the `AniError` variant in `backend/src/error.rs` and its arm in `key()`, with the key constant in `backend/src/i18n.rs`. The variant list in `backend/src/error_variants_test.rs` does not compile until the variant has a pattern/value pair there, and the key-list test then fails until `backend/error-keys.json` carries the new key; its failure message prints the file's expected contents.
2. Add the message to `backend.json` in every locale, named by the key with underscores for dots.
3. Add the key's entry to `MESSAGE_BY_KEY` in `describe-error.ts`, with a field adapter if the message interpolates one of the variant's fields. `describe-error.test.ts` fails until every listed key resolves to its own message in every locale.

## Adding a locale

1. Copy `frontend/messages/en/` to a new directory named by the [BCP 47](https://www.rfc-editor.org/rfc/bcp/bcp47.txt) tag (e.g. `pl`, `tr`, `id`).
2. Translate every value. Keys remain identical to the English bundle.
3. Add the tag to `frontend/project.inlang/settings.json` under `locales`.
4. Add the locale to the language picker: the `LOCALES` list in `frontend/src/routes/settings/+page.svelte`. The e2e smoke test (`electron/e2e/smoke.spec.ts`) checks that the picker offers the shipped locales; add the new one to what it expects.
5. Add the locale to the table in `electron/lib/main-messages.cjs`. The Electron main process shows two dialogs of its own — the one a failed startup ends with, and the prompt on a quit with downloads running — at moments when no page can show them, so their text cannot come from the renderer's bundle. `pnpm test` in `electron/` fails while the table and `frontend/project.inlang/settings.json` list different locales, or while any locale is missing an entry.
6. Check the new bundle against the English one by hand. Nothing fails on a key the new locale lacks: the compile gives that locale the English message for it.
7. Add a translation-attribution line to `docs/i18n.md` under the candidates table below.

Adding a locale is a translation PR with three places to register it: the inlang settings, the picker, and the main process's table.

## What is and isn't translated

**Translated** — every UI string the user sees: labels, buttons, error messages, empty states, tooltips, settings, date/time formatting (via `Intl.*`).

**Not translated**:

- **Anime titles**: the user picks a title-language preference in Settings (English / Romaji / Native). The default differs by UI locale: `en` and `pt-BR` default to English (Portuguese metadata is sparse on Kitsu/AniList); `es-419` defaults to English; `ru` defaults to Romaji.
- **Provider names** (wixmp, hianime, filemoon, etc.) — proper nouns.
- **Genre tags** as raw strings — Kitsu returns them in English; we render them with locale-specific subtitling where applicable.

## RTL support

Out of scope at MVP. No Arabic or Hebrew locale is shipping yet. However, the codebase uses logical CSS properties (`margin-inline-start`, `padding-inline-end`, `text-align: start`) so adding an RTL locale becomes a translation-only PR + a `dir="rtl"` flip on `<html>`. The `tests/arch/i18n.sh` invariant test enforces no use of `margin-left` / `padding-left` / etc.

## Pseudo-localization

Dev builds expose a `pseudo` locale that wraps every translated string in markers and inserts accents:

```
"trending": "Trending Now"
   ↓ pseudo
"trending": "[!! Tréndíñg Nöw !!]"
```

Hardcoded strings show through unwrapped, making them easy to spot. Activate via `?locale=pseudo` in the dev server URL.

## Phase-2 candidate locales

Not blocking the MVP, but the i18n architecture supports adding any of these as translation-only PRs:

| Candidate | Code | Why eventually |
|---|---|---|
| Polish | `pl` | Large fandom, fewer legal options than Western Europe |
| Turkish | `tr` | Large youth fandom, weak legal Turkish-subbed catalog |
| Indonesian | `id` | Massive market, strong free-streaming culture |
| Vietnamese | `vi` | Large audience, weak legal availability |
| Ukrainian | `uk` | Similar dynamics to Russian, separate locale for cultural reasons |
| Arabic | `ar` | Significant audience; **requires RTL enablement first** |
