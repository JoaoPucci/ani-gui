# Architecture

`ani-gui` is a desktop app that lets you browse and watch anime through a graphical interface. It began as a front end over the [`ani-cli`](https://github.com/pystardust/ani-cli) Bash scraper and now resolves streams itself in Rust. The repository no longer carries the script; the terminal flow is upstream's to provide.

## What gets shipped

A single-window desktop application. Linux: AppImage and `.deb`. Windows: NSIS installer. The user double-clicks an icon and gets a native window. There is no URL to visit, no port to remember, no internet-reachable service.

## Why there is a "backend"

The app talks to three things a browser tab cannot reach on its own:

1. The streaming provider — it sits behind TLS-fingerprinting protection that rejects browser and plain-HTTP clients, so requests go out through a `curl-impersonate` subprocess.
2. The watch-history file — needs filesystem access.
3. Anime stream CDNs — hianime's serve a playlist only to a request naming the embed page's own origin as `Referer:`, a header browser fetch APIs cannot set, and none serves segments with permissive CORS. The proxy sends only what the resolved stream named — the embed page's origin for a hianime stream — never a referer of its own.

So the app embeds a Rust backend, bound to `127.0.0.1` on a kernel-assigned port, that orchestrates these pieces. It runs as a sidecar process the desktop shell launches at startup — a localhost daemon, not a server another machine can reach. On this machine it answers the app alone ([below](#who-the-backend-answers)).

## Who the backend answers

Binding to `127.0.0.1` keeps the backend off the network, not away from the machine: every program on it, and every page any browser on it opens, can send requests to a loopback port. So the API answers only requests that carry a secret the app's own callers are given. The backend draws a 32-byte secret at random each launch and prints it last in its handshake (`ANI_GUI_INTERNAL_SECRET <hex>`); the Electron main process reads it from the backend's stdout and keeps it for each window it opens. The window's preload asks the main process for it once, over IPC, as the page loads, and puts it on `window.aniGui.internalSecret`; the main process answers only the main frame of that window holding the app's own page (`app://localhost`, or the Vite dev server in development), and any other page that ends up in the window gets nothing (`electron/lib/secret-handoff.cjs`). The secret is on no process's command line. Every route under `/api`, on every lane, answers a request that does not carry it with an empty `403 Forbidden` before any handler runs (`backend/src/api/gate.rs`). It travels only as the `x-ani-gui-internal-secret` header, which the renderer sets on its own requests. Three requests are made by elements that cannot set a header — the play and download progress streams (an `EventSource`) and `/api/image` (an `<img src>`) — and the main process adds the header to those on their way out, for the same page the IPC handoff answers and no other (a subframe, another page, or a window it was not handed to gets nothing; `electron/lib/secret-header.cjs`). A poster Chromium already holds in its cache is served from there without reaching the gate, to any frame in the app's windows: its bytes are the public cover art. No URL carries the secret, and no route reads it from a query: a URL is kept where a header is not — Chromium's disk cache keys the poster images it stores by their URL, and a log line naming a URL names everything in it. The main process sends the header on its own one request, the launch's flags.

What the secret keeps out is any caller that has to guess it: a page in a browser, and a program running as another user without administrator rights. It is not a boundary against a program running as the same user, or as an administrator, which can read the app's memory and everything the app keeps directly. The main process also keeps the secret out of everything it logs — the renderer's console lines, failed page loads and the backend's output — by its value and by the shapes it travels in (the header, a `secret=` parameter), and logs `<redacted>` in its place (`electron/lib/log-redact.cjs`). Chromium's own "Failed to load resource" lines never reach that log: Electron hands the main process no network console messages.

No request names a program for the backend to run. The external player and Syncplay start from `/api/play/external` and `/api/play/syncplay`, which take the show and the episode: the backend runs the player configured in Settings, with the arguments that player's kind takes (or the custom template from Settings) filled from the stream it resolved. It refuses a stream that is not an `http(s)` URL before anything starts, since the URL goes on the player's and the download tool's command line as a bare argument, and it drops a custom template's token that a substituted value — the show's title, the referer, a subtitle URL — would turn into an option (`-…`, or `/…` as many Windows players take theirs), as it drops a token whose value is empty. A dropped value token takes with it an option the template wrote on its own just before it (`--sub-file {subtitle}`), which alone would take the stream as its value. The player, Syncplay and the template themselves are the user's Settings, which the app's page writes (`PUT /api/settings`): whoever holds the secret can change them, so the secret is what stands between another program and that choice. Settings store the program paths as the page sends them, so the app's own page can still choose what runs; setting them only through a main-process file picker is recorded in `docs/deferred-work.md`, "Which program the app runs is the page's choice".

The stream proxy (`/s/<session>/…`) is not behind the secret: the player's media element and a download's tools fetch it without headers. Its guard is the session id in the path, a random UUID that only the play that made the session learns, and the HMAC on every URI it rewrites.

CORS, on the API and the proxy alike, allows only the renderer's origins (`backend/src/renderer_origin.rs`): `app://localhost`, the scheme the packaged app serves its pages under on Linux and Windows, and a loopback `http` origin on any port, for the Vite server a dev run loads. A page at any other origin is shown no answer, and its browser does not send it a request that needs a preflight. The header makes every request from the renderer one that does, so a preflight's answer is cached for the two hours Chromium allows.

## Components

```
 ┌──────────────────────────────────────────────────────────────┐
 │  ani-gui desktop app                                         │
 │                                                              │
 │  ┌────────────────────┐   fetch()   ┌────────────────────┐   │
 │  │ Renderer (SPA)     │ ──────────► │ Backend (sidecar)  │   │
 │  │ SvelteKit + hls.js │ ◄────────── │ Rust HTTP server   │   │
 │  └─────────┬──────────┘             └─────┬──────────────┘   │
 │            │                              │                  │
 │            │ <video src="http://127.0.0.1:├──► providers    │
 │            │  PORT/s/<token>/...">        │   via curl       │
 │            │                              │                  │
 │            │  bytes streamed via proxy    ├──► Kitsu (REST)  │
 │            └─────────────────────────────►│   AniList (GQL)  │
 │                  Referer + CORS           │                  │
 │                                           ├──► history TSV   │
 │                                           │                  │
 │                                           └──► SQLite +      │
 │                                              image cache     │
 └──────────────────────────────────────────────────────────────┘

```

Three layers, in lockstep:

- **Renderer** — SvelteKit static SPA running inside the desktop shell's web view. Renders the discovery surface, search results, detail pages, and the embedded player (`<video>` + hls.js). Stateless beyond UI state; talks only to the backend.
- **Backend** — Rust crate inside `backend/`. Spawned as a sidecar by the desktop shell at startup. Resolves streams from the providers, fetches metadata from Kitsu/AniList, reads/writes the watch-history file, runs a streaming proxy on a localhost port, and exposes an HTTP API the renderer talks to via `fetch()`.
- **External processes** — `curl-impersonate` for provider requests, `yt-dlp` / `ffmpeg` for downloads, and optionally `mpv` (or the configured external player) for the "Open in …" escape hatch. A download yields to live playback: the host counts requests per address and refuses it once the count runs high, so the proxy notes every media fetch it serves — a playlist as it is admitted, a segment or an mp4 range chunk by chunk as its body streams — and while one landed in the last thirty seconds the download fetches through the proxy itself instead of from the host: its own session there is background traffic at the host's budget — one request at a time however many are in flight; while a player request waits, a turn after the player has taken what it needs with a quarter to spare — for segments alone every other token for one muxed stream at five-second segments, one in four for video and audio at five-second segments, and none once that need is the whole refill or more, as for video and audio at two-second segments or one muxed stream at segments under about two seconds, with fewer turns as the player's other requests — a key per segment, a live playlist's refreshes, the requests that start playback — add to the need, when the download waits for the player to stop asking — at the end of a fill, which can last minutes, while that need is under the refill itself, and only when playback stops once it is over it, since such a player never finishes a fill — and never into the few tokens kept for the player while none waits; not counted as playback — so it takes whatever the player leaves, and what the player's need leaves of the refill while the player fills its buffer, with no byte-rate cap, and waits on each request as long as a paced run may last, so a run that only waited never fails into the fallback that reads the host directly, where with nothing playing it runs sixteen fragments against the host directly; when playback starts or stops under a running download the tool is taken down and, once its process tree has exited, started again on the same output, which it resumes from the fragments it has. Every teardown waits up to two seconds for that exit — the ffmpeg retry after a condemned or failed run, and a cancelled download's sweep of what the tool wrote, start once the tool's tree is gone within them, which for a run that failed by itself includes a helper it left running — in its process group on Unix, in the job objects the tool is put in before it runs on Windows — the teardown ends the inner one, every process in it at once, and the outer one's kill-on-close also takes the tools down with a backend that crashes. A tree still running after those two seconds ends the download rather than meet a respawn or a retry, but the sweep does not wait any longer: the ended download's sweep, and a cancelled one's, then run beside the surviving tree, and what it writes after them is left behind. Each run's tool reports its progress on stdout — yt-dlp a line of the app's own shape with the bytes it has downloaded, run with no user configuration, which could silence that line, ffmpeg its key=value progress — and the backend turns the byte counts into a speed over the last few seconds, reported to the frontend once a second as a status line; the download indicator in the top bar and the bottom bar show the running downloads' total. Paced runs take a single lane in turn, one download for the whole app, and a download queued behind it starts free once playback stops. The ffmpeg fallback is one connection whose source is set at its start — through the proxy while playback is live, unless the yt-dlp run before it failed through the proxy, when it reads the host directly at the stream's own rate; the host directly otherwise; kept to its end either way — and that cannot be resumed, so it holds that lane from its start whether or not anything plays.

The shell and the backend end together. A quit stops the backend, and with it the provider requests and download tools it has running. If the shell ends without quitting — a crash, a kill — the backend notices its parent is gone, through a pipe the shell holds open for as long as it lives, and stops itself and what it has running. Both hold from the moment the backend is spawned, including while it is still starting up — a first run creates and migrates its cache, which on a busy disk takes seconds — and a backend that loses its shell during startup just exits, having nothing running yet to stop. On Linux the shell quits as soon as the session's end is announced — a reboot or power-off by logind, which waits for the quit up to its `InhibitDelayMaxSec` (five seconds by default), and a logout by gnome-session, which does not wait — rather than wait for the stop signals the session sends every process next. A stop signal that reaches the shell's GPU process along with the shell ends it by that signal, provided the shell sees the GPU process die before Chromium tries to start another, which it usually does but cannot guarantee; it has first stopped the backend and written the renderer's saved state (resume positions, recent searches, caption choices) to disk; one that reaches the shell alone quits it, however many arrive (SIGTERM, SIGINT and SIGHUP; any other signal keeps its default action), unless the GPU process crashes on its own within a quarter of a second either side of the signal, when that signal too ends the shell. Once the session's end has been announced, every one of those stop signals ends the shell by that signal at once, in the same way, whoever sent it: mostly the session stopping the shell's processes, which can overtake the quit the announcement started, and also a signal passed on to the shell alone, which cuts that quit short (`electron/lib/session-end.cjs`, `electron/lib/termination-signals.cjs`). A launch that cannot get as far as a working window — the backend does not start, or the first page does not load — exits with code 1; a packaged build says why in an error dialog first, unless it was started unattended (see [`development.md`](./development.md)).

On Linux, what the app starts gets the user's desktop environment, not the one Electron leaves in its own process. Before the main script runs, Electron 33 rewrites `XDG_CURRENT_DESKTOP` to `Unity` when it matches `ubuntu` (in any case) or is one of `Pantheon`, `Unity:Unity7` and `pop:GNOME`, keeping the session's value in `ORIGINAL_XDG_CURRENT_DESKTOP`, and sets `CHROME_DESKTOP` to the app's desktop file; Chromium's GTK start-up then adds `GDK_BACKEND` and, under X11, `NO_AT_BRIDGE`. A browser started from a link with all of that believes it runs on Unity, and draws its window buttons on the left. The main script snapshots its environment before it loads Electron's API, and what it starts is given one rebuilt from that snapshot: the session's desktop back, the kept copy and `CHROME_DESKTOP` dropped, the app's own launch's `DESKTOP_STARTUP_ID` and `XDG_ACTIVATION_TOKEN` dropped, anything added since the snapshot dropped, changed since put back and taken out since left out, and the app's own `ANI_GUI_*` variables as they are (`electron/lib/child-env.cjs`). The AppImage changes more before the main script runs: its runtime exports `APPIMAGE`, `APPDIR`, `OWD` and `ARGV0` (and, in portable mode, points `HOME` and `XDG_CONFIG_HOME` at directories beside the image), and its `AppRun` puts the image's mount ahead of `PATH`, `XDG_DATA_DIRS`, `LD_LIBRARY_PATH` and `GSETTINGS_SCHEMA_DIR` and appends a few system data directories to `XDG_DATA_DIRS`. Run from the image, the rebuilt environment leaves all of that out (a portable `HOME` becomes the account's home again, unless the account has none on record, and except for the backend, which keeps the portable home and config, where the app keeps its data, and so do the external player and Syncplay it starts), and a list with nothing left in it is not passed on, so a browser started from the AppImage does not load the image's libraries or search its data first. The backend is started with it, so the external player and Syncplay, which it spawns, inherit it; so is the reduced-motion read. Links and "Open folder" go through `shell.openExternal` and `shell.openPath`, which take no environment and read the process's own: for the length of that one call the process holds the rebuilt environment, restored as the call returns or throws, so the browser still gets the activation token Electron asks the compositor for, which lets it come forward on Wayland. The session-end watcher, which starts only system programs (`sh`, `setpriv`, `gdbus`), gets the rebuilt environment too, without `DISPLAY`. The app's own process otherwise keeps Electron's environment, and so does the keyring helper, which is the app itself. A Restart from the launch splash starts the new instance from the rebuilt environment too, as a fresh launch would be (`electron/lib/relaunch.cjs`). An AppImage that runs extracted rather than mounted (`--appimage-extract-and-run`, for a system without FUSE) is restarted extracted again, after waiting, ten seconds at most, for its runtime to remove the old extraction, which the new launch would reuse. Windows and macOS are untouched.

One instance runs per profile. The desktop shell takes a single-instance lock before it does anything else, so a second launch on the same profile spawns no backend: it hands over to the running instance and exits, and the running instance brings its window forward — restored if minimized, shown if hidden, then focused. Where the running instance has no window, what happens depends on why. A launch while it is still booting changes nothing; the booting instance shows its window when it is ready. Nor does a launch while a failed start is reporting why, or while the app is quitting. On macOS, which runs from source only, closing the last window leaves the app and its backend running; a later launch, or a click on the dock icon, then opens a new window against that backend. Without the lock, two backends would share one history file, cache database and numbering, and the history's lock, which belongs to the process, cannot see across processes. The lock lives in the shell's profile directory, so the dev profile has its own and a dev build runs beside an installed one (`electron/lib/single-instance.cjs`).

## The window holds the app and nothing else

Every page the window loads runs the preload and gets the bridge: the backend's origins, the stored account tokens, the folder pickers, opening a folder. The internal secret is not handed out with it: the preload asks for it over IPC, and the main process answers the app's own page alone (above). So the window may hold one document, the app's own — `app://localhost` in a packaged build, the Vite dev server's origin in development — and the checks below keep it there and answer that document alone, all ruling by one comparison of the URL's parsed scheme, host and port (`electron/lib/app-document.cjs`). Never by `URL.origin`: for `app:` that is the string `null`, the same as for `file:`, `data:` and `about:`.

- **Navigation** (`electron/lib/window-guard.cjs`). A navigation to the app's own document goes ahead: a route loaded in full, a reload. Client-side routing and hash changes are not navigations and are untouched. A web page is refused and opened in the system browser instead; anything else is refused. Redirects and subframes may not leave the app, webviews are refused, and no second window ever opens — a link that asks for one goes to the system browser if it is a web page. A file or link dropped on the window is never turned into a navigation (`navigateOnDragDrop` is off). Chromium commits `about:blank` without asking the guard; it takes the origin of the page that asked for it, which is the app's own. The launch splash gets the same guard and the same permission handlers: every window the main process makes is made with both installed, before anything loads in it (`electron/lib/guarded-window.cjs`). The splash never holds the app's document, so it navigates nowhere and is granted no permission. On top of that, the splash's own handlers (`electron/lib/splash.cjs`) cancel every navigation alongside the guard's, and refuse every new window in place of the guard's window handler, so a link on it that asks for a new window does not reach the system browser; one that navigates still meets the guard's verdict, which sends a web page there. `tests/arch/window_guard.sh` fails on a window or view made anywhere else in the spelled-out ways a line-by-line search can see; its header lists what it cannot.
- **IPC** (`electron/lib/ipc-guard.cjs`). Every handler in the main process acts only for the main frame holding the app's document; a call from anything else is refused and logged. That includes the renderer's words that its first page has mounted and has rendered: the launch waits for the second before it reveals the window, and maps a hidden window whose rendered word does not follow the mounted one in time (below). The wrapper is the one file that holds `ipcMain`. `tests/arch/ipc_sender.sh` fails when any other file under `electron/` names `ipcMain` or a contents' own IPC object in the spelled-out ways a line-by-line search can see; its header lists what it cannot. Opening a folder takes an existing absolute directory and nothing else, since the call it makes would open a file in its application or run it (on macOS, which runs from source only, an application bundle is a directory and still opens).
- **Permissions** (`electron/lib/permissions.cjs`). Electron grants every web permission unless told otherwise. The app's document gets the two it uses, fullscreen and writing to the clipboard; every other permission is denied to every document.

In development the app's document is whatever the Vite dev server's origin serves. The update notice links only to an `https` release page: the backend offers no release whose page is anything else (`normalise` in `backend/src/meta/github_choice.rs`). What the app's document may load is the content security policy's to say ([below](#the-renderers-content-security-policy)); the policy does not govern navigation, which is the guard's.

## One loopback origin per class of traffic

The backend listens on seven loopback ports, not one — a lane per class of traffic the renderer sends it — and serves every route on each. Chromium opens at most six connections at a time to one host and port over plain HTTP and queues every request past the sixth, whatever it is for, and the renderer's requests differ in how long they hold one: an API call answered from the cache holds it for milliseconds, an availability probe until the provider walk answers or its sixty-second deadline passes, a play resolution as long as the resolve takes, a download's progress stream for the whole download, a poster on a cold cache for the upstream fetch, a franchise read while the backend walks the franchise through Kitsu. On one origin the long holders could fill all six, and the player's playlist and segment fetches — and the next page's metadata — queued behind them; right after an upgrade that re-keyed the availability cache, every visible show re-probed at once and segment loads timed out.

| Lane | What goes to it |
|------|-----------------|
| `api` | Everything the rows below do not name: page data, search, settings, history, account, the cache-only availability batch and the fire-and-forget warm. |
| `stream` | The stream proxy (`/s/<token>/…`): playlists, segments, keys, MP4 bodies, sidecar subtitles. |
| `image` | `/api/image`. |
| `probe` | Availability probes (`/api/availability`). |
| `resolve` | Play resolutions: the progress stream the player's own play and the prefetches open, and the plain, external-player and Syncplay resolves. |
| `download` | Downloads' progress streams. |
| `franchise` | The watch-order reads that walk the franchise (`/api/watch-order/<id>/show`, `…/franchise`, `…/up-next`, `…/handoff`) and the walk's first hop (`/api/kitsu/franchise/<id>/first-hop`). The show page, the player, the franchise page and Home's Continue hand-offs all ask for one, and each holds its response open while the backend walks Kitsu. |

The handshake the backend prints at startup announces each lane as `ANI_GUI_LANE <name> <origin>`, ahead of the API's `ANI_GUI_LISTENING <origin>` and the secret, the two lines the desktop shell waits for; the shell hands them to the renderer through the preload bridge as `window.aniGui.lanes`, and the renderer picks the lane for each request, falling back to the API's origin for any lane it was not given. The stream proxy stamps every URL it writes — the session's media URL, every URI in a rewritten playlist — with the stream lane's origin. The external player and Syncplay are handed the upstream stream itself, and a download's tools reach the proxy from processes the backend spawns, so none of the three draws on Chromium's pool.

Lanes bound how long one class can make another wait; they do not bound a class against itself, so the renderer also holds availability probes to four at once across every surface, background ones to three so a probe the user is waiting on always finds a slot, and aborts a page's probes once the user has left it. The API lane's own reads are held to the same rule: the reads a page makes to show itself take the signal of the page's visit, which ends when the viewer leaves the page or, on a show's page and the player, moves to another show, and a search replaced by another, a live search the query has moved past, and a lookup asked again end theirs too, so a read nobody will read gives its connection back instead of queuing the next page behind it; a read cancelled so shows neither an answer nor a failure. The reads an action makes once clicked — such as an unaired episode's recheck, a Continue card's row read again before it resumes, the questions a failed play or a removed row asks — a tracker list's refresh, and the layout's other reads (the settings, the update check), which outlive every page, run on to their answer, as a write would. The backend, in turn, shares walks of an availability row — a show in one audio mode. A lookup of a row whose walk is already out, from another surface, a page mounted again or the warm, waits on that walk instead of starting another, unless the walk set off before a cache-skipping refresh last wrote the row; an interactive lookup does not wait behind a background walk, but takes its place, and the background walk's callers move onto it. A refresh, and a lookup with no Kitsu id, walk on their own. A probe the renderer aborts stops waiting, and a walk nobody waits on any more ends, except a background one while fewer than three others walk on with nobody waiting: a page mounted again joins it rather than starting over, and its verdict is cached. The list views' warm feeds one worker through a queue that holds each row once and at most 256 rows, and the renderer hands an uncached id to it once per session, and again only once two minutes have passed since it last did. Downloads start at most six at once — as many connections as Chromium opens to their lane, since each holds one for its progress stream and the backend starts a download only when that stream arrives — and the rest wait in the download dock as queued, in order, cancellable before they start.

## The renderer's content security policy

The renderer runs under a content security policy in two halves, and every resource it loads has to pass both.

- **The bundle's half** is a `<meta http-equiv>` SvelteKit writes into the page at build time (`kit.csp` in `frontend/svelte.config.js`). It allows scripts from the app itself plus SvelteKit's inline bootstrap script, by a hash that changes with every build. It also refuses plugins and `<base>`.
- **The shell's half** is a response header. It names the lanes, whose ports are known only at launch, so the shell writes it from the handshake (`electron/lib/renderer-csp.cjs`):
  - anything it does not name is refused (`default-src 'none'`), prefetches included;
  - its script rule only keeps that default off scripts; the meta's rule, which carries the bootstrap's hash, is the one that decides what runs;
  - styles come from the app;
  - images come from the app, `data:` and the lanes;
  - connections go to the app and the lanes;
  - media comes from `blob:` (hls.js attaches through a MediaSource) and the lanes;
  - fonts come from the app;
  - workers, frames, plugins, manifests, `<base>`, form submissions and framing the app are refused.

A lane origin enters the header only if it is exactly `http://127.0.0.1:<port>` and belongs to the API or one of the six lanes the renderer knows. Anything else the handshake carries is dropped, so an extra announced line cannot add a source. The script rule leans on every document the app serves carrying the meta. The bundle's only HTML document is `index.html`, which also answers every route, and its SVGs carry no script; a lint test keeps `frontend/static` that way (`frontend/tests/lint/static-documents.test.ts`).

Two rules follow for the frontend:

- **Nothing may evaluate a string as code**, in either build. The play loader's Lottie animation uses lottie-web's light build, which has no expression engine, and its JSON carries its motion as keyframes rather than expressions.
- **Style attributes are refused**, except SvelteKit's route announcer, which is allowed by its hash. Svelte applies every style that holds an expression through the CSSOM, which the policy does not govern. A static `style="…"` in a template is parsed as markup and reported as a violation, which fails the e2e guard, so it has to be a class (`frontend/tests/lint/no-static-style-attr.test.ts`).

In a packaged build the `app://` protocol handler adds the header to every response it serves: the index, the SPA fallback, every asset and every error, a path that does not decode included. It serves only files inside the bundle directory (`electron/lib/bundle-path.cjs`). It keeps each response's content type; a module script served without its JavaScript type would not run. Until the window opens against the handshake, the header names no loopback origin at all.

In development the shell appends the header to the Vite dev server's main-frame responses, beside SvelteKit's own policy, and allows what Vite needs on top: inline `<style>` elements and its hot-reload WebSocket. A plain browser tab on the dev server, which no longer reaches the backend, would run under SvelteKit's half alone.

Every Electron e2e test fails on a violation it did not declare (`electron/e2e/policy-guard.ts`), including ones on the first load, which the guard reads from the shell's relayed console.

## Data flow: searching and playing an episode

1. The user types a query into the search bar.
2. The search page calls `POST /api/kitsu/search/page` with an offset of 0. The backend hits Kitsu — with every dash that no ASCII letter or digit precedes sent as a gap, since Kitsu reads such a dash as "exclude what follows" — and returns a page of matches — Kitsu serves at most 20 a page, in its own ranking, by popularity, unless the user chose an order — with the offset the next page starts at. As the user scrolls to the end of the results, the page asks for the next offset and appends what comes back. Choosing Year or Rating starts the search over with the order in the request (`sort`), and Kitsu sorts the pages, so a page that lands continues the order below what is shown. (The search bar's live dropdown calls `POST /api/kitsu/search`, which is the first page alone.)
3. The user picks a result; the renderer fetches detail and episode list via `GET /api/kitsu/anime/:id` and `GET /api/kitsu/episodes/:id`.
   Going back to the search page (the back button, or the topbar's chevron, which names the search and steps back to it) restores what the user left: the search page keeps its query, order, type filters, loaded results and the card at the top of the screen in a [SvelteKit snapshot](https://svelte.dev/docs/kit/snapshots) on that history entry; a type filter the page no longer offers (Music, which earlier versions offered though search never answers a music video) is dropped as it comes back. Results under an hour old, judged for the current audio setting, come back without a request; otherwise, and on a reload, the search runs again in the same order and filters, page by page up to that card. A search page opened from another page starts afresh, and the bare Search link empties it; a new query submitted while on the search page keeps the order and type filters on screen.
4. The user clicks an episode. The renderer asks for a play with the chosen anime + episode, on the resolve lane: `GET /api/play/stream`, an event stream that reports the resolve's progress and ends with the session, or `POST /api/play` where no event stream is available. The backend resolves the stream natively against [hianime](https://hianime.fm): it searches the site for the title (falling back through every alias), probes candidates' per-entry episode lists to pick the right show, fetches the episode's server list, and reads the master-playlist URL and any sidecar subtitle tracks off the chosen server's embed page. Requests go through a `curl-impersonate` subprocess — the site sits behind TLS-fingerprinting protection that rejects plain HTTP clients. See [Providers and failover](#providers-and-failover).
5. The backend creates a `StreamSession` (UUID, upstream URL, referer, expiry), stores it in memory, and returns its token to the renderer with the session's media URL.
6. The renderer mounts `<video>` and points hls.js at `http://127.0.0.1:<port>/s/<token>/master.m3u8`, on the stream lane's port (see [above](#one-loopback-origin-per-class-of-traffic)).
7. The streaming proxy fetches the upstream master playlist with the referer the session stores — the embed page's origin for a hianime stream — parses it with `m3u8-rs`, and rewrites every network URI it names — variants, renditions, segments, keys and init segments — to flow back through itself with HMAC-signed sub-tokens. A source that serves a single quality may answer with the media playlist itself, which is rewritten as one. A tag the parser does not know that names a URI (low-latency parts, preload hints, rendition reports, content steering) is dropped, as is a variant or rendition written as an inline `data:` playlist; an inline `data:` key or init segment stays as written, since it names nothing further to fetch. Because hls.js parses the result differently from `m3u8-rs` — it trims attribute names, ends lines at `\r`, U+2028 and U+2029, and so reads a quoted value that spans lines as lines of their own — the proxy then reads its own output the way hls.js does and drops any line through which the player would still fetch something off the proxy. CORS headers are added so hls.js inside the webview can consume the rewritten manifest without preflight blocks.
8. Subsequent segment requests follow the same path: hls.js asks the proxy, the proxy asks the upstream with the same referer, bytes stream back. A fragment hls.js loads but cannot buffer is one it asks for again; past four loads of one fragment in ten seconds the player stops the engine rather than let it run against the host. An hls.js network failure while the player still has buffered media in hand — a 429, a dropped connection, a slow host — is held, and the engine asked to load again after a delay that grows per failure and never outruns what is buffered; the stall recovery and its notices are for a player nearly out of media, and for a progressive mp4, whose element cannot be asked again without dropping its buffer. The host counts requests per address and refuses it once the count runs high, so the proxy spaces every fetch it makes to the host on the player's behalf — playlists, segments, mp4 ranges, and the subtitle tracks it loads, which take turns with the media requests waiting for tokens — to a per-host budget: a burst of twenty for startup and seeks, then one every second and a half. hls.js loads one segment at a time and the player allows it ten seconds for a first byte, so the wait is absorbed; the player still buffers as far ahead as it likes, over minutes rather than seconds, and while it is still filling that buffer a seek past it may take a few seconds longer than it otherwise would. A redirected fetch is followed hop by hop, each hop charged to the host that answers it and carrying the session's referer. The budget is the app's, not the proxy's alone: the subtitle tracks a download stages beside its transfer, and while playback is live the download's own fetches through the proxy, reach the host from the same address and spend it too, as background traffic — one request at a time; while a player request waits, a turn only after the player has taken what it needs with a quarter to spare, and none while that need is the whole refill or more. The proxy learns the need from the player's requests. Its segments name their stream: the master names each playlist's kind of stream — main, audio, subtitles, one of each played at a time, so a level switch replaces rather than adds — and each segment names its kind and the playback it buys, noted at every host a hop of its fetch reaches. The player's other requests — playlists, keys, init segments, mp4 ranges — count too, at the rate they arrived over the last minute: each takes a token the player's turns count, and a playlist that names a fresh key for every segment doubles what the player asks for. While no player request waits, background traffic never takes the last five, which stay for the player's next requests and a seek's — while download tools run free, at most one less than their hold leaves: three beside sixteen fragments in flight, fewer beside more, none from nineteen. The bucket is per host, so a download from a different host than the player's has its own and does not wait on the player's, though a download tool running free holds every host's, as below. The liveness check a cached resolution gets before it is served — a ping and a read of the four tracks the user most likely turns on, once, under a deadline of seconds — is a class of its own between the player's requests and background traffic: each request, at each host a redirect reaches, takes a token only while no player request waits in the host's line, so an episode already playing there never has its next segment queued behind the check, and from the reserve kept for the player's next requests; background traffic yields to the check while it waits — but for a turn the player's line already owes it, which keeps that line moving — so a download never starves it. A check its tokens keep past the deadline reads the row as dead, evicts it, and a fresh resolve takes its place. What reaches the host past the budget counts against it as well: while a download tool runs, every host's tokens are held to what its requests in flight leave of the burst — sixteen for yt-dlp running free, one for yt-dlp reading the host directly while playback is live and it has no relay to fetch through, one for an ffmpeg fallback reading the host directly; a run through the relay is the proxy's, charged as it goes — since its fragments go wherever its playlists send them, which the app does not see. When it ends, every host is left where the hold left it, one the player has not fetched from yet included, so a player starting beside a download running free, or just after one, does not add a whole burst on top of it; the hold never takes a host below one token, and with several tools running it is what all their requests in flight leave. It is a hold, not a count: the requests a tool sent before are not charged, only kept from being joined by a whole burst, and a tree that outlived its teardown is no longer held for. Not charged: the resolver's fetches of a playlist, one or two requests ahead of the player's own. An external player the app hands a stream to fetches from the host on its own, outside the app entirely.

## Providers and failover

The resolver's walks — search the aliases, pick the candidate by episode count and year, chase the episode to a playable URL — are policy, and they read the same whichever site answers. What differs per site sits behind a `Provider` trait in `backend/src/scraper/`: how a query becomes hits, how a slug becomes an episode list, how an episode becomes a playlist — hianime's embed hosts differ even there: zokoanime's page carries the stream in a payload, megaplay's names a media id the sources endpoint on that page's own host answers for, as ciphertext under constants the site's player script carries and for whichever content delivery network the request asks about — the site can stream an episode from several and they do not all stream alike, so the client asks every megaplay page for the one whose segments it can play, whatever network the listing named that server for — and the client reads a page by its shape, asks the master before taking a server, tries megaplay's servers ahead of zokoanime's — megaplay's delivery network has carried the top rendition at real time where zokoanime's has crawled or been down, so the site's order, zokoanime first, would hand every play to the slower host while it still answers — and steps to the next server when a stream's host does not answer — and what the CDN wants on the request (hianime's playlists are served only with the origin of the host that served the embed page as `Referer`, which the site's listing does not always name, since it moves those pages between hosts with a redirect). A resolved stream carries that context — the master URL, its referer, its sidecar subtitle tracks — and every consumer reads it from there: the proxy session, the resolution cache, downloads, and the external-player and Syncplay handoffs.

One provider ships: hianime. anidb.app shipped ahead of it until October 2026, when its domain began redirecting every page to an unrelated site; it was removed, and [what a removed provider leaves behind](#what-a-removed-provider-leaves-behind) is below. The machinery around the seam is written for an ordered list of providers, and the rest of this section describes it that way — a primary and the fallbacks behind it — because adding a provider is a client behind the trait, not a change to any of it. With one provider the walk asks it and nothing else.

A provider's own requests are held to its origin. Every request hianime's client builds from its site — the search, the show page, the episode list, the servers listing — follows a redirect only while it stays on that origin (scheme, host and port): the transport drops curl's `-L` for such a request and follows each hop itself, up to a bound. A redirect anywhere else is not followed, so the site it names never receives the request, and the client reads that redirect, or a page another origin served all the same, as a parse failure — the walk fails over past it and the gate hears distress — never as an answer. That is the failure anidb.app's end produced: its search began redirecting to an unrelated site, the transport followed, and that site's page was read as an empty search and persisted as a clean miss. The embed hosts, their sources endpoints and the CDN are other origins, reached by design, and follow their redirects as before. The cost is a legitimate move: if hianime moves its front to another domain by redirect, the app stops reaching it until a release points the client at the new domain ([`deferred-work.md`](./deferred-work.md#following-a-providers-legitimate-domain-move)).

Each provider has an admission gate of its own — a pacer for background probes and a circuit breaker that opens after consecutive failures — so an outage on one never paces or refuses traffic to the other. The failover orchestrator (`backend/src/commands/providers.rs`) runs every walk against the providers in order and moves to the next only when the current one was **unreachable, refusing or broken**: a transport failure, a timeout, a provider-shaped block or rate limit, a background request the gate refused, a page the parser no longer recognises, or a stream server that did not serve the episode. That last is the episode chain's verdict for every failure that is not an answer — the embed host unreachable or timing out, a page, payload or playlist the client could not play — met past searches the site answered: it is reported as the source's video server not serving the episode (`error.play.stream_server_failed`, naming the stage and host in the log), never as the user's connection or as the app failing to read the provider. It also covers the client no longer reading a host — a payload whose key has rotated, a server listing whose rows it cannot read — which from the chain is told apart from a host serving nothing only by the cause the log carries. Both walks — the resolve walk and the pick walk the probes and the range download's start use — report the failure they met, the one from furthest along, rather than substituting a transport failure for it: a search page the client could not read is a parse failure, and the connection is blamed when a transport failure is the furthest the walk got — no search answered, or a search answered and the provider's own listing probes of every candidate died. zokoanime's own not-found card under a 200 status is read as the 404 it is: the episode's absence, not a failure. A provider that answered conclusively — including one that searched and found nothing — ends the walk; a miss on the primary is not retried on the fallback. An answer that settles nothing does not: a provider that found the show but whose sampled episode rows all say nothing about the requested audio mode has answered inconclusively, and the walk moves on to the next provider as it would from an unreachable one, surfacing the unknown verdict itself when nobody gives an answer that is not negative — a clean miss or an absence from the rest does not replace it. The other exception is a show a live positive availability row already places: the row puts its provider first, and that provider's own first negative — a clean catalogue miss included — is set aside rather than ending the walk, and the rest of the order is asked anyway. What they answer then stands against the set-aside negative by rank rather than by order: a negative that found the show — an episode it does not carry, or the mode absent — outranks a title miss from another catalogue, whether the search matched nothing or matched only candidates whose episode lists were gone — except that an absence and a clean miss, which both deny the show for the mode asked and both persist, are peers — negatives of equal rank keep the one whose provider stands earliest in the configured order — the row the read rule below can serve, since a negative row is served only while every provider ahead of its own is refusing, so a remembered fallback's own miss yields to the primary's equal one and a remembered primary's stands over the fallback's — and the set-aside one stands as given when the rest were unreachable. The paragraph below works that ranking through. A provider that is refusing — its breaker open, or an advertised rate-limit window still running — is skipped while another remains, on background and interactive walks alike; the last one is always tried, since an interactive request may be the trial that closes a breaker, and a click is admitted through a pause regardless. Every attempt but the last is bounded by a 20-second budget under the 60-second resolve deadline, so a stalled outage cannot spend the whole deadline before the fallback is asked. On an interactive walk that skipped a provider for refusing — an open breaker, or an advertised rate-limit pause — one attempt budget is held back for each skipped provider, so a stalling fallback is cut off at its attempt budget and the skipped provider's retry has its time: the breaker's half-open trial, or the click the gate admits through a pause; a background walk, which never retries, reserves nothing. Each attempt's outcome lands on its own provider's gate.

The order is per request when a show is already known. A positive availability row names the provider whose catalogue carries the show, and a play, a download or a handoff for that show starts from it, so a show the fallback listed, in the requested audio, during the primary's outage — a positive row a probe or a fresh resolve wrote says the show and the mode are listed there, not that a stream was played; one a cache-served replay wrote again after the row lapsed says only that a stream resolved there once validated again at its CDN — the replay stamps before anything plays, and a page warm plays nothing — and is where the next walk starts — keeps starting from the fallback after the primary recovers — the primary's clean miss would otherwise end the walk on a show the row says is there. So does the availability probe's own reprobe of a positive row it does not serve — a resolve's count-less stamp, an approximate count — which would otherwise start from the primary and let its clean miss overwrite the fallback's proof with a negative. The row proves the show and its mode at the show's level, not that every episode has an embed, so a remembered provider's own negative — an episode dead end, or a show found without the requested mode — does not end the walk either: the rest of the order is asked, and what it answers stands against the set-aside negative by one rank, whatever its shape — a negative that found the show outranks a title miss from another provider, clean or not — an absence and a clean miss excepted, peers since both deny and both persist — negatives of equal rank keep the one whose provider stands earliest in the configured order, and the set-aside one stands as given when the rest were unreachable. So the remembered provider's own dead end outranks the other catalogue's title miss, clean or not, and nothing persists, while its own answer that the mode is absent has denied the mode, and a negative persists when nothing outranks it — its own absence, or the other catalogue's clean miss when that provider stands earlier in the configured order, the two being peers. A remembered provider heard from with an episode dead end has not denied the show, so an absence from the rest of the order is the verdict the caller sees but not one that persists over the row, and a title miss from the rest, clean or not, is outranked by the dead end; while it is unreachable, an absence from the rest is the same verdict, seen and not persisted, and a clean miss from the rest is not the verdict at all — the remembered provider's unavailability is, the error that took it out of the walk or its gate's refusal when it was skipped and never asked, and nothing persists; whether a held absence came past an undenied affinity is read as the walk finally stands, so a remembered provider whose trial answers a clean miss makes the fallback's absence its own, and it persists. And a probe whose provider found the show but whose sampled rows all answered nothing — episode ids the provider no longer serves — is inconclusive rather than negative: the walk moves on to the next provider holding the unknown verdict it leaves, which an answer that is not negative replaces and no negative does — a title miss, clean or not, or an absence from another catalogue says nothing about the mode where this one found the show — in either order and through the skipped providers' trial; a remembered provider that gave it has not denied the show, and the verdict, when it stands, is unknown and nothing persists. And on an interactive walk the skip of an open breaker is only the fast path — the gate admits a click through an open breaker as its half-open trial — so when the walk's verdict is negative — every provider tried answered a miss or was unreachable, or the one that answered found the show without the requested mode — the skipped ones are asked before it surfaces: an answer that is not negative is the walk's; a retried provider's own negative answer or miss replaces the verdict, author and all, by the same rank as between any two negatives — the provider earliest in the configured order among equals, and never a title miss, clean or not, over the unknown verdict or a dead end that found the show, nor a clean miss over an absence or an absence over a clean miss, the two being peers; and one still unreachable leaves it standing. Background traffic keeps the skip.

The asymmetry is absence. Two verdicts persist as a negative row — a clean miss, where every search completed and nothing matched, and a show found without the requested audio mode: its episode listing is empty, as for an upcoming title, or its first readable episode lacks the mode (the probe samples one episode's server list, not the whole show's) — and each is a verdict from **the provider that answered**, which the row names: since a miss does not fail over, a negative row from the primary means the primary searched and found nothing (or found the show without the mode), not that no provider carries it. A row is served only on the word of a provider the app walks: one naming a provider it no longer walks, or naming none — a row from before rows named their provider — is not served, by the probe or the lists, and the next probe asks the walked providers again. A negative row is served — by the page's probe, and by the lists, which hide a finished show on it — only while its provider has been seen answering since it last failed — its breaker closed by a success, or never opened, no failure recorded since that success, and no advertised pause running — and every provider ahead of it in the order is refusing, where refusing means the gate's breaker is open or an advertised rate-limit pause is still running; otherwise the probe runs again and the card renders. The two are different questions: past its cooldown a breaker refuses nobody but is half-open, one trial let through and nothing yet heard, so a row served on that alone would short-circuit the very probe whose trial could fail over; a half-open primary therefore backs nothing of its own, while the fallback's row yields to the trial. So the primary's negatives stop standing through the primary's own outage once its gate has learned of it — one failed request since its last success is enough, since a breaker opens only after repeated failures and the rows served meanwhile make no request that could supply them; a pause starts on an advertised rate limit — and until some request has taught the gate that, a negative row is still served without a request being made — which would otherwise hide a show the fallback carries. And the fallback's negatives, written during that outage so an absent show is not re-walked on every look, stand exactly as long as both halves of the read rule hold — the fallback's own gate seen answering and the primary's refusing — so a fallback's negative stops standing the moment a request to the fallback itself fails, or the fallback enters a pause, whatever the primary's gate says — and stands again when the pause's advertised window ends, on the clock, but after a failure only once a success has followed it, and after a breaker only once a success has closed it — or once a rate-limited trial has turned the open breaker into an advertised pause, which then ends on the clock like any pause; and otherwise it stands for as long as the primary's gate refuses: a breaker is open for its cooldown, a minute, and a pause for the window the rate limit advertised, and both close on the clock — nothing has to prove recovery — so at the window's end the next look reprobes rather than serving the row, and the reprobe's own outcome teaches the gate again, since absence on the fallback proves nothing about the primary. A positive row's proof is guarded the same way from the other side: while the provider the row remembers is unreachable — skipped for refusing, or failed over, and not heard from since — a show found without the requested mode from the rest of the order is the verdict the caller sees but not one that persists, and a clean miss from the rest is not the verdict at all — the caller sees the remembered provider's unavailability, the error that took it out of the walk or its gate's refusal — so the row stands until the remembered provider is reachable again and the next resolve starts from it, rather than a negative from the other catalogue overwriting proof it never contradicted — for as long as the row itself is live, and no longer. Its lifetime is the [positive availability TTL](#caching), and which window it is depends on what wrote the row last. A row nothing has resolved against since the probe keeps the window the show's status earns it — 24 hours at most for an ongoing show — cut at an hour past its next scheduled airing when that is sooner — 30 days for a finished one, from that probe. Only the probe passes the status, though: a play, a download, a hand-off and a page's warm all stamp the row through the resolve path, which writes without one, so each rewrites the row with the ongoing window — 24 hours at most — dated from that operation — a finished show's 30 days shortened to at most a day like any other. A play, hand-off or page warm served from the resolution cache is the exception: it learned nothing about the listing — the CDN answered for a URL resolved when the provider last served — so it leaves a standing positive row exactly as it is, lifetime included, and only where no positive row stands, the resolution cache outliving the availability row, writes a count-less row naming the provider, with the ongoing window, which the next look at the show reprobes for its cap, starting from that provider. A resolve whose listing runs past Kitsu's count with no reading of the rows past it ([`title-resolution.md`](./title-resolution.md#extras-appended-after-the-last-episode)) is the other exception: its cap is no count, so it leaves a standing positive row with an exact count from the provider that served exactly as it is, lifetime included, and otherwise writes the count-less row naming that provider. So what bounds the remembered provider's protection is at most a day from the last resolve that wrote the row, and the probe's own window only for as long as the probe is the last thing that wrote. Past that the cache stops returning the row, nothing remembers the provider, and an outage that outlasts it leaves the next walk running the plain order, where the other catalogue's negative persists like any other. A remembered provider that answers for itself is heard from, and its own negative persists as before.

The history rows, the numbering sidecar beside the history file, the watched-at stamps and the reverse mapping to Kitsu key on a show key that says whose id it holds — a provider's slug under its label — and the play-resolution row, keyed on the request as the cache section below describes, carries the same key in its value. [`title-resolution.md`](./title-resolution.md#show-keys) describes the format and what reads it.

### What a removed provider leaves behind

A provider's resolves stamp its show keys on every store a play writes, and removing the provider leaves all of it on disk. A key names a retired provider when it names no provider the app walks: anidb.app's bare slugs, the allanime-era ids before them, and the label of any provider later taken out of `ProviderSet::shipped`. Each launch, before the API serves, a sweep (`backend/src/retired_provider.rs`) settles what such keys left; nothing in it names a provider, so the next removal needs no new code:

- **History rows.** A retired row is removed when, for every Kitsu entry it stands for, a walked provider's row that recorded the same entry, one Kitsu has not answered gone, resumes over it: Continue Watching and the detail page both find that row by the entry it recorded, so both already show it in the old row's place. The removal is the one the page uses, so the old row's stamp, mapping, resolution rows, numbering and title matches go with it. A walked row known only by a guess, a title match or a mapping, supersedes nothing, since neither surface is certain of it. A retired row that recorded an entry Kitsu still serves stands for that entry alone, as both surfaces read it by it; a title match or mapping a guess stored for it before does not hold it back. Any other retired row stands for every entry anything names for it. Every other retired row stays: one still resumed from, one whose show no walked row recorded, one nothing names an entry for. Its episode is rewritten in the app's own numbering, the number it already showed, and it gains no Kitsu id: the entry it is shown as may be a guess, and a guess never becomes a row's id. Such a row keeps its card. Playing it from the card is a guessed session: it resolves fresh on a walked provider by the Kitsu entry's titles and writes that provider's row beside it, with no Kitsu id, and the strip shows the two as one card. A play from the show's own page records the entry, and once that row resumes over the old one the next launch removes the old one.
- **The numbering sidecar's** rows for retired keys go once no remaining row reads through them.
- **Watched-at stamps and reverse mappings** of a retired key go with its row; a kept row keeps its own.
- **Cached play resolutions** whose show key is retired are never replayed, and go. Before the sweep removes them, a read refuses them first: a URL a departed provider served can answer a liveness check with a redirect to another site, which would read as live.
- **Availability rows** naming no walked provider, or none at all, are never served, and go; the next look at the show reprobes.
- **Title matches** filed under a segment no walked provider names go, unless a remaining row is read by them: a kept row's sit under the `legacy` segment, or under its provider's label while the app still knows that provider. A match under a retired segment is a `title-match:v3:` key, which the cache reclaim deletes at launch before the sweep runs.

The sweep keeps no marker. It finds its work in the data itself, so a launch with nothing retired reads the history and numbering files and a few key ranges of the cache, under two milliseconds, and writes nothing, and a history or cache restored from an older copy is swept on the next launch. It reads every store it needs — the history, the numbering sidecar, the cache — before it writes any, and a store that exists but cannot be read stops it with nothing written: read as empty, the sidecar would have a kept row's provider slot written as its episode for good. What it changed is listed on the diagnostics page.

### Adding a provider

The seam exists because one provider is one point of failure. Within ten days in 2026 the single provider the app then rode failed twice in two different ways: in late August its server-rendered pages stalled for hours while its JSON routes kept answering, and from early September every route, the JSON API included, answered a maintenance 503. Nothing new could be resolved through either. hianime was added behind the seam as the second provider, and is the one left.

A second provider again is mostly a client behind the `Provider` trait; the recipe in `backend/src/provider_set.rs` lists every place it has to be named. What decides whether a candidate can be a client at all:

- **Reachable by the app's transports, on both packaged platforms.** The scrape rides `curl-impersonate`, spawned once per request: a request carries a URL and headers, one built from the provider's own site is held to its origin, and no cookie jar carries over from one request to the next. Impersonation passes a TLS fingerprint check; it cannot run JavaScript, so a site behind an interactive challenge is out of reach. And the scrape is only half of it, because playback rides other transports: the proxy's own `reqwest` client (`backend/src/proxy/upstream.rs`, a rustls fingerprint) fetches playlists and segments for the embedded player, `yt-dlp` and `ffmpeg` fetch for downloads, and the external player, alone or under Syncplay, fetches for itself. A site can answer every scrape and still refuse every play if its delivery network fingerprints those. A candidate counts as reachable only once a master playlist and its segments have come through the proxy and through each of the other consumers, on Linux and on Windows, through the tools each platform's package ships or relies on ([`AGENTS.md`](../AGENTS.md) §15).
- **A text search** that accepts the titles the bridge feeds it, in priority order ([`title-resolution.md`](./title-resolution.md)). The checks that judge a mapping from the provider's show to a Kitsu entry compare the season the provider's title names with the one Kitsu's entry names, so a provider that names its seasons its own way needs those checks looked at too.
- **An episode listing with numbers.** Availability caps and the disambiguation by episode count both read it. Providers number differently — some continuously across seasons, so a second season's first episode is the fourteenth, and some, hianime among them, within each season's entry — and a cap from one model is not comparable with a cap from the other.
- **A sub/dub signal**, per episode at best. hianime types each server on an episode's server list, which is per episode but costs one request per episode; why that matters is the per-episode audio-mode caps entry in [`deferred-work.md`](./deferred-work.md#interface).
- **An extraction step whose upkeep is sustainable.** Embed obfuscation rotates; the question is how often, and how much each rotation costs to follow.
- **Catalogue breadth, and a tolerance for the request rate.** The gate, the breaker and the reservations apply per provider either way.

Removing a row removes what is kept about its show beside it (`backend/src/commands/history_remove.rs` and the `history_forget*.rs` modules it calls):

- by the row's key: the watched-at stamp, the note of the card its guessed play came from (`guessed-from:`), the note of the show the user linked it to (`history-linked:`), the reverse mapping under every version's key with the mark a play leaves beside it, the resolution-cache rows whose stream played it, and its row in the numbering sidecar;
- by the row's title: the title-match rows stored for it, under every version's key, but for one a remaining row searches too — a legacy opaque-id row and a newer slug of one show search the same key, as does one title on two providers under a version from before the provider joined the key; and, since a provider can rename a show and the row takes the new title, the title-match rows under any title that name a Kitsu id the show is known by and no remaining row claims — one stored under an earlier title that names an entry the show is not known by, or one a remaining row claims, stays;
- by the Kitsu ids the show is known by that no remaining row claims — the one the row records, the ones its mapping and title match name, the pages the running process saw it played from: the aniskip skip times cached under them, and the resolution-cache rows a page of the show resolved under another key (each resolution row carries the page it was asked from), with that key's numbering when no history row has the key and no resolution row still names it.

Clearing the history removes all of these for every show, with every resolution-cache and skip-time row besides, and the numbering of every key the cleared shows' pages resolved under, whatever else names it. The order is what a retry needs: nothing goes before what a retry would find it by. A delete takes the watched-at stamp and skip times; then the numbering of the other keys, while the resolution rows that name them are still there; then those rows; then the title matches stored under an earlier title that name the show's Kitsu ids; then the mapping and title matches those ids are found by, which a retry in a later process, with no pages noted in memory, finds them by besides the id the row records; then the history row; then the row's own numbering, so a failure part-way never leaves a removed row without its offset. A clear takes the other keys' numbering, then the cache, then the history file, then the rows' own numbering. A key with no history row loses its numbering before the history write, so a removal that fails after that point has already taken it, and a play under way that writes the key's first row from the cache after such a failure writes it without its numbering; it records the app's own number, which needs none. A resolve stamps a key's numbering before the key's first row exists, and rows from before the own-number marker read through it, so a delete leaves the numbering of a key a resolution row it does not take still names, and neither a delete nor a clear touches the numbering of shows never in the history.

A removal runs with the history held (`backend/src/history/guard.rs`): every write of the file, and every store of what its rows leave behind, takes the same lock, so none is half-way through while a removal runs and no two writes of the file lose each other's rows; what only takes away — an eviction, a cache clear — does not ask for it. Work that waits on the network between its writes is the other half: a recorded watch waits on Kitsu before it stores the show's mapping and the id on its row, a play resolves before it writes its row, its numbering and its resolution row, a handoff resolves before its player starts and the watch is recorded, a skip-time lookup fetches before it caches. Each takes the history's moment when it begins, a removal moves the moment on for what it removed, and a write for a show removed since the work began is dropped — a removal wins over work begun before it, and the player a handoff had been asked for still opens. A watch's writes after its Kitsu read — the id on its row, and the show's mapping, stored or dropped — also give way to a later watch: a write that gives a row its watch moment or Kitsu id moves the moment on too, and a watch whose row another watch has written since leaves the row and the mapping to that watch. A play's resolve is not a watch, and does not move it on even when its row carries the page's Kitsu id — the id the cache already accepts, which the play's own watch would record. A play's row and a watch's row and stamp give way the same way when another watch was recorded after their request began: a request that stalled — on a cached stream's check, on a resolve — does not put an older episode over a newer watch, and the play or handoff goes on as asked. A show is removed under its row's key, and not everything that would write of it has that key: skip times are cached under a Kitsu id, and a play resolves under the key of whichever provider answers, another's when the walk fails over. So a removal also records the Kitsu ids the show was known by, less any a remaining row still claims; a play names the page it was asked from and loses to the removal of a show known by it, and a skip-time lookup loses by its id. Two stores are written at the renderer's request after waits of its own, the show-id resolve's guessed mapping and the title-match row, so the moment the request arrives says nothing: those are stored only while a history row still carries the show id, or the title on that provider. Work begun after a removal is new activity: playing the show again records it again.

What a removal does not reach (kept as one entry in [`deferred-work.md`](./deferred-work.md#correctness-in-the-app-continued)):

- **A show the history never linked to a Kitsu id.** It is known by its key alone: skip times fetched for it, what a page resolved for it under another key, and a play of it still resolving that lands on another key, are not recognised as its.
- **A resolution row from before rows carried their page.** It is found by its key alone, so one a page resolved under another key stays until the next launch's cache reclaim deletes it (an older schema's at once, the current one's once it expires) or the history is cleared, and the key it names keeps its numbering — through a clear too, unless a row that records the page names the key as well.
- **Numbering with no resolution row beside it.** A handoff's resolve stamps numbering and stores no resolution row, and its watch writes the key's history row only once its player starts. A later resolve of the same request that lands on another key overwrites the row (`play_resolution_cache::store`), and a row whose stream failed — at the check before a cached play, or in the player — is evicted. Each leaves a key's numbering with no resolution row naming the key; when that key is not the history row's, nothing links its numbering to the show any more, and it stays as any rowless key's does.
- **A row the removal was not asked for.** A row of the same show under another key, which a play that failed over wrote before the removal, is a row of its own: removed with it when the home page has seen it — it deletes every row it groups under the show's Kitsu entry — and otherwise still there, claiming the show's Kitsu id.
- **A numbering file that cannot be written.** The numbering file sits beside the history file and is written on its own, under its own lock and rename, and a failure to write it is logged, not returned. When it fails, the removed row's own numbering stays, and so does the other keys' while the resolution rows that named those keys still go; the removal then fails at the history write if the history file cannot be written either, and succeeds otherwise. Either way a retry no longer knows the other keys, and after a removal that succeeded there is no row left to retry.

Catalogue caches shared with browsing — Kitsu details, artwork, episode lists, availability — are not history and stay, as they do for shows only browsed.

## Discovery (landing page)

The landing page shows four rows: **Trending Now**, **Popular This Season**, **Top Rated**, **Recently Released**.

- **Trending Now** is fetched from AniList's GraphQL endpoint (`Page.media(sort: TRENDING_DESC)`). AniList's trending sort follows recent activity (its `trending` value counts the past hour), which Kitsu's cumulative `userCount` cannot match.
- **Popular This Season**, **Top Rated**, and **Recently Released** are fetched from Kitsu (REST/JSON:API). Kitsu's posters and banners (sizes verified at build time) are sufficient for these views.
- Both APIs are hit only when cache misses; cache is SQLite (`$XDG_CACHE_HOME/ani-gui/metadata.sqlite`) with TTLs from 1 hour (trending) up to 30 days (title-match cache).

When a user clicks a discovery card, the backend resolves its title against the provider (searching every available alias from the metadata API: English, Romaji, Native, synonyms) and falls into the same playback flow. The cross-API bridge — including how Kitsu's episode count disambiguates colliding titles on the provider, and how the MAL id is fetched for the aniskip and trending lookups — is documented in [`title-resolution.md`](./title-resolution.md).

When Kitsu's `coverImage` is null (common for shows currently airing — roughly half of the trending row in any given week), the detail-page resolver falls back to AniList: it bridges the Kitsu id through the mappings endpoint to the show's MAL id, then queries AniList for that MAL id's `bannerImage` — or queries AniList by the AniList id the same mappings carry, when Kitsu has no MAL mapping or AniList has no media for the MAL one. Without the fallback the detail page would render a flat colour where the hero banner belongs. A show the trending row has listed skips the query: its banner was remembered from the trending answer (below).

Each home row's actions sit in the row's own header, after its title: Continue Watching has a "Clear history" action, which asks for confirmation, and Watch Later a "Refresh" action, beside a line saying when its lists were last pulled from the trackers: the oldest connected tracker's pull, "Not updated yet" while any connected tracker has no recorded pull (never pulled on this computer, or cleared by a list change since), "Refreshing…" during a pull, and "Couldn't load your list" while the row's last load failed, until one lands. A failed row with no cards to keep says so in its caption and shows no such line. Two arrangements of those headers exist: actions beside the title, the default, and each row with its actions at the end of its header, drawn on a band while the pointer is over the row or focus is in it. The switch between them appears above the rows only while the diagnostics page's "Show row style control" checkbox is on, and the choice is kept with the checkbox in the renderer's local storage (`ani-gui:row-style`), per machine. Clear history and the remove chip on a Continue card each ask in a dialog that stays open while its request is out, runs once however often its confirm is pressed, opens no other dialog over it meanwhile, and closes when it settles. When the request fails, an error toast says the history could not be cleared or the show could not be removed. A failed clear leaves every card, and focus goes back to Clear history. A remove takes every history row of the card's show, one at a time. When one fails, the rows already deleted leave the strip and the show's card stays. If the pressed card's own row was not among them, the card is unchanged and focus goes back to its chip. If it was, the card is now drawn from a row that is left, the pressed chip is gone with its row, and focus is not put back. Either way the user can try again from the cards that stay.

### The hero banner

The home hero and the detail page's band show one image per show, taken in this order: AniList's `bannerImage`, where the trending feed's one request carried it for the show — it rides beside Kitsu's cover on each trending entry and is remembered per Kitsu id for thirty days, as [`title-resolution.md`](./title-resolution.md) describes, so a detail page for a trending show makes no AniList request of its own; Kitsu's cover; the show's poster, blurred, as a last resort. A sizeable share of any week's trending row has no AniList banner (eight of twenty when measured), so the Kitsu cover is a frequent second. The image fills the band's height: the whole image, centred, over a blurred copy of itself that carries its colour to the band's edges, cropped at the sides only when it is wider than the band. The detail band is 4.8:1 at every window size, so a cover cropped to fill it lost about a third of its height when measured against the covers Kitsu serves — the sized covers are nominally 21:5, which alone would cost an eighth, and the uploads run taller — anchored near the top, before its bottom faded into the page; the home band changes shape with the window, and cropped the sides of a cover at widths up to 1920 px and its height on an ultrawide screen. AniList's banners are drawn for a band of roughly this shape, which is why they come first.

The home hero rotates through three trending shows: the first three, in trending order, that have art of their own — an AniList banner or a Kitsu cover. The backend makes that pick (`backend/src/hero/`). Taking the plain top three instead could leave most of the rotation on blurred posters: when measured, the first, second and fourth of twenty trending shows had neither. A show the hero passes over is not lost: the Trending strip lists every show the hero did not take, in trending order, so the shows passed over lead it, and no show appears in both. A show the trending answer names more than once — two AniList entries can bridge to the same Kitsu show — counts once, at its first entry, so neither the hero nor the strip shows it twice. When fewer than three shows have art, the first shows without it fill the rest of the rotation, after the ones with art, on their blurred posters. The choice is made from the trending answer, once the shows already known to be unavailable are dropped from it: Home sends what is left, in trending order, to `POST /api/home/hero` and draws the hero and the strip in the order the answer gives (`frontend/src/lib/hero/rotation.ts`). The answer already carries each entry's banner, cover and Kitsu status, so the choice asks nothing of AniList or Kitsu, only the local backend. When the backend cannot answer, the Trending row fails as a failed trending fetch does, and the hero says the catalogue is unreachable.

With the `hero_airing_first` flag on ([Remote flags](#remote-flags)), the shows with art that are airing now — Kitsu's status `current` — come before the other shows with art, each group in trending order. The fill of blurred posters is untouched: it stays in trending order whether or not its shows air. With the flag off, which is how every release ships it, the pick is the one above. The pick returns the walk that made it beside the result, and the backend keeps the last one in memory: the diagnostics page (**Debug** in the rail) shows it in its "Home banner pick" section (`GET /api/home/hero/walk`), read-only. It lists the flag's value and where the launch's flags came from, and every trending show the pick read, in order, up to the one that settled the hero (the shows after it are in the strip, a repeated show once): its rank, its art, its status, whether the airing preference decided it (it moved an airing show into the hero or to another slot in it, or pushed a show out of the hero for one), and whether it was taken, for which slot, or passed over, and why. An image that then fails to load falls back as below, and does not move its show out of the hero.

Four framings exist — fill height, the default; fit, which never crops and letterboxes the image over its blurred copy; top crop, the previous rendering; centre crop — and the image source can be set to Kitsu's cover alone. The control that changes them is a small group of buttons at the top-right of the band on both pages, with a readout of which image is on screen, and it is hidden until the diagnostics page (**Debug** in the rail) has its "Show banner framing controls" checkbox on. A choice applies at once, without a reload, and is kept with the checkbox in the renderer's local storage (`ani-gui:hero-framing`), per machine; turning the controls off again leaves the chosen framing in place. Nothing of this is in Settings or in the backend's config.

A hero image that fails to load gives way to the next in that order, without a reload, and no hero asks for that URL again until the app next starts. The backend keeps its own verdict: when the image proxy's upstream answers 404 or 410 for a URL, the URL is marked gone for thirty days, keyed like its bytes on disk — a re-signed Kitsu URL is the same object — and is not offered again meanwhile: the next trending fetch drops it from the row, the next detail read forgets the remembered banner rather than serve it, and the null-cover backfill still asks AniList — a replaced banner would arrive as a new URL — but refuses the same URL back, so a detail read made after the verdict leaves the renderer its poster treatment with no failed request. A detail row cached before the verdict, with a backfilled cover in it, is served as it is until its own TTL runs out; the renderer's fallback covers those reads. A transient failure (429, a 5xx) marks nothing, and a later successful fetch of a marked URL drops the mark. The remembered banner is refreshed only by a trending answer that lists the show, so a show that leaves the trending row keeps its remembered URL until the thirty days run out or the proxy finds it gone. The bytes behind an image URL, once fetched, stay on disk until the size cap prunes them, so a banner shown once keeps showing from the cache after AniList has removed it, for as long as the URL is still handed out.

### AniList's budget

AniList limits each client's requests — 30 a minute while its API runs degraded, 90 otherwise — and answers a client past the limit with HTTP 429 and a one-minute timeout, during which further requests are refused too. The trending row, the banner backfill, episode thumbnails, airing schedules, the id bridges and the signed-in account's reads and writes all draw on that one budget, and a home page opened on a cold cache asks for several of them per card at once. Every request to AniList's GraphQL API, public or signed in, therefore leaves through one gate kept for that host for the life of the backend process (`meta::anilist_gate`). The OAuth sign-in's token exchange goes to `anilist.co`, not to the API, and is not gated.

- **Pacing.** At most 25 requests leave in any 60 seconds, a quarter of a second apart. A request is counted from its answer once it has one, rather than from when it left, so the window the backend keeps never ends before the one AniList keeps. Background fills — episode thumbnails, the detail page's banner backfill, the airing seeds and the availability warm — may use 20 of the 25; the last five are held for what the user is looking at. Every request sent is logged at INFO, which the default filter keeps (`ani_gui::meta::anilist_gate`), with what it is for, its class and how many requests the window then holds, so the split can be measured and each request traced to the kind of request that spent it.
- **Cool-down.** A 429, or a 503 that names a wait, records "nothing before now plus `Retry-After`", or AniList's documented minute when no wait came; so does an answer whose `X-RateLimit-Remaining` is zero. Until then nothing is sent — interactive reads and account writes included.
- **Waiting.** A request waits for its turn up to 3 seconds when the user is waiting on it, 1 second for a background fill — under the 2 seconds the episode page gives its thumbnail backfill. A background fill some page is waiting on (the detail page's banner backfill, the airing seed of a pre-premiere availability probe) can so add up to a second to that page under contention. Past its wait a request fails with the rate-limit error (`error.network.rate_limited`, carrying the seconds left) without being sent. A 429 that arrives anyway is retried once when its window ends inside that wait, and is otherwise returned and logged as the rate limit it is.
- **Sharing.** A public query sent again while the same one — same class, endpoint and body — is still out waits for that answer and takes a copy, rather than spending a request of its own; the episode-thumbnail backfill shares one lookup per show the same way, Kitsu's mappings read included (a retry of a held-back one runs on its own). The account's own queries — the list editor's entry read, the episode map's evidence reads, a list pull — share the same way per bearer, but only with one sent since the bearer's last write went out or was answered, so a read after a write — the editor's re-read — always reaches the tracker; its writes never share: each one the user made is sent. Nothing is kept once the answer is out: the next ask goes out again, and what caches the answer is the lookup's own. A background fill and a read the user waits on never share, so a fill the gate holds back cannot hand its refusal to the user.
- **Batching per-show fills.** Home's Continue Watching strip reads each card's episodes and detail as the card's show resolves, one read per card, and each used to send AniList a `Media` query of its own for the episode stills or, for a show Kitsu has no cover for, the banner. Lookups that miss the cache now go through lanes, one per kind (`meta::anilist_batch`). The lookup that opens a lane goes out at once, alone, with the single query it always sent, when the gate would let it go: a card no strip warm is out for waits on its episode details for up to a second before it settles on the show's poster, so that lookup is never held — outside a strip warm (below), whose lookups all wait for the window, and which a card's lookup may then ride. Lookups arriving while the lane is open gather, and every 100 ms what the lane gathered goes out as one batch in a task of its own, without waiting for the batch before it to answer; a window that gathers nothing closes the lane. A background lookup the gate would hold back for a turn anyway, inside its wait (a quarter second after the request before it, say), gains nothing by waiting for it in the gate alone: one with a MAL id that finds no lane open opens one and waits there, and a batch at the end of a window waits there too, until the gate's turn is 20 ms away. The MAL lookups arriving meanwhile join it, and it waits out the rest in the gate's own queue, so it leaves at the turn it would have taken alone. While it waits the lane holds a place in the gate's queue, counted as a request waiting for its turn, so no retry takes that turn ahead of it. Its wait counts against the lookups' own, from when it began or its last lookup joined, whichever is later: past it the batch is handed over with that deadline, and the gate turns it away as it would have turned that last lookup away waiting there alone, so no lookup in it is turned away sooner than alone. A show Kitsu maps to AniList alone is never held this way and never joins a held lane, since its page would wait for the MAL page's answer; a batch at the end of a window that carries one goes at once, as before. 100 ms is under the gate's 250 ms least gap, so the MAL-id page a gathered lookup rides in leaves no later than its own request would have, the lane's first having just been sent; a show asked on the AniList-id page waits for the MAL page's answer first. Each caller is answered as soon as its own answer is in; the single lookups a batch falls back to go together, those the MAL page hands over while the AniList-id page is asked, so a show waits on no other show's single lookup, and only an AniList-id page waits for the MAL page. A batch sends one `Page { media(idMal_in:) }` request per 50 ids for the shows with a MAL id, then one `Page { media(id_in:) }` request per 50 ids for the shows Kitsu maps to AniList alone and those whose MAL id AniList answered without — the order the single lookup asks in, and two requests because AniList ANDs the two filters. A MAL id several media record, a page AniList cuts even for one id, and a node that cannot be read are asked by one single lookup per id; every show of a page that cannot be read at all is asked by its own. A strip whose cards miss together costs the first card's request and as few as one or two more, instead of one per card. Each show still keeps its own cached row; a page that fails or is refused answers only the shows it covered, caching none of them, and each card's fill held back by a refusal is queued its own retry, as below. A batch every caller has stopped waiting for is dropped, out of the gate's queue if its turn has not come. Lanes are kept apart per gate class, so a retry is never sent in a background batch.
- **Warming the Continue strip.** Each Continue card asks for its episodes and detail only once its own row is ready, and on a cold cache rows land seconds apart, so card by card a lane would mostly carry one or two shows. As soon as the history is loaded, Home hands the backend the Kitsu ids its rows recorded, in strip order, at most fifty (`POST /api/continue/warm`, `commands::strip_warm`). The backend reads every show's mappings together, then starts every show's stills and banner lookup at once inside `anilist_batch::gathered`, where even the lookup that opens a lane waits for its window: one page per kind. A card that asks later shares the warm's lookup still out — the stills' and the banner's lookups are both shared per show — or finds its answer kept; one whose lookup arrives while a warm's lane is open rides its page, up to the window later than it would have gone alone. The mappings request carries Kitsu's cover with the ids, and the show's mappings row keeps whether there is one (`kitsu:external-ids:v3:k<kitsu id>`), so the warm asks no banner for a show Kitsu has a cover for, whose detail never looks for one. The warm keeps only what the cards would: each thumbnail listing under its row, and AniList's answer for a banner — the banner, or that it has none — under a key of its own (`anilist:strip-banner:v1:k<kitsu id>`, a day at most) that the detail read takes once, only where Kitsu has no cover, and then keeps in the detail row for that row's own lifetime. The warm's lookups wait for every show's mappings to be read, so a card whose own lookup comes first goes alone, and the warm's lookups for that show share it. Rows without a recorded id are matched by title and fill on their own. A card whose show a warm still out carries does not settle at its one-second episode wait: its own episode read and the warm share one AniList lookup for the show, so it waits for the warm and then its details, at most three seconds from when it first offered its episode (the read itself gives AniList two seconds before answering without the still), and settles at once if the warm fails after the one-second mark ($lib/history/cap-timers). A card whose warm has already answered, or that no warm carries, keeps the one-second wait. Leaving Home closes the warm's request, which drops it.
- **Who asked.** The sent line names the request's purpose, and for a request about shows how many ids it carries, never which: `anilist request sent provider="anilist" purpose=stills shows=35 class=Background in_window=3 …`. A purpose names the job the request does, not the screen that wanted it: `trending`, `banner`, `stills`, `airing`, the id bridges `tracker_ids` (the list editor, progress write-back and the episode map all resolve a tracker's entry through it), `watch_later_ids` and `tracker_map`, and the account's `account`, `user_list`, `list_write`, `list_delete`, `list_entry`, `tracked_media` and `media_evidence`. The class tells a background fill from what the user is looking at. A request not keyed by show — the trending feed, the account and its list — carries no `shows`. Every transport takes the label, and it has no default, so a new caller has to name one. A refused request's retry is a send of its own and logs its own line. A request that shares one already in flight (see Sharing) is not sent again; the one send is logged under the label of the request that sent it.
- **Seeing the batching.** Every request a lane sends logs one line at INFO once its answer lands — or once the gate turns it away unsent, with the rate-limit key as its status; `ms` counts from when the lane handed it to the gate, its wait for a turn in the gate included and a lane's own wait for that turn not — under `ani_gui::meta::anilist_batch::log`, which the default filter keeps: `anilist lane request answered kind="stills" request="mal_page" ids=35 status="ok" ms=711`. `kind` is `stills` or `banner`, `request` is `single`, `mal_page` or `anilist_id_page`, `ids` how many ids it carried, `status` `ok` or the error's stable key. A single lookup that asks again by AniList id is one line.
- **Retrying held-back fills.** An episode-thumbnail or banner fill the gate held back for a page is retried once the pause ends (`commands::held_fill`), so the page fills in without the user leaving and coming back: the read the page was served carries a ticket (`x-ani-gui-refill`), the page waits on it (`/api/refills/wait`, one wait open for the whole renderer), and fetches once more when the retry lands. A retry is a class of its own: it takes a turn only while no other request waits for one, and only while the window holds fewer than ten requests, half the background share, so it never touches the five held for the user and never refills the window the pause just emptied. Retries go one at a time, deduped per show, at most one per pause and three pauses in all; a run that fails for another reason, or a fill no page was served, is not retried; at most 128 wait at once. A page that closes lets its tickets go (`/api/refills/release`) — also when it closed before its read came back — as does a read no page waits on, the read fetched once more after a landing included, and a read whose one refill landed lets its others go; the renderer never lets go of a ticket a page has started waiting on, though a read no page waits on can let go of one another page's read is still bringing, which that page's wait puts back — or, when the release overtakes that wait, its next one, at most 20 s later. Let go, they are off screen at once, even while the backend still holds open a wait the renderer has dropped; served to a page's read again, one counts as on screen for 5 s, as a new ticket does, and a wait on it keeps it there. Those retries still go, since the answer is cached for at least a day — a thumbnail listing serves every episode of the show — but only while no retry for a show on screen waits. Whether a fill landed is read from the cache, which only ever holds an answer.
- **The account's user.** Which user a bearer belongs to — the owner every write-through, removal, list pull and cached read files rows under — is asked of the tracker once per bearer and kept for the life of the process — AniList's list pull and its removal, which need it too, take it from there rather than asking again; a refused lookup is kept nowhere, and a disconnect forgets the tracker's bearers. So a held write landing as a cool-down ends files its row without a lookup of its own, once the bearer has been seen. The `/me` route, which shows the name, avatar and stats, still asks each time.

A write the user made — a save or removal in the list editor, or the progress a watched episode sends to each connected tracker (a play the session could not verify sends none, so nothing of it is ever held) — is not dropped when it is answered with HTTP 429, whether the AniList gate held it back, a tracker, MyAnimeList included, refused it, or a read the write depends on was refused — the tracker episode map's evidence among them, whose rate limit fails the write with its wait. The renderer reads the wait from the error (a minute when none is named, never more than two minutes), shows "AniList is busy, saving in N s" — naming the tracker that refused, which the error names (`refused_by`); when it is not the one the write is for, as when AniList refuses the ownership check a MyAnimeList write's episode map needs, the notice names both: "AniList is busy, saving to MyAnimeList in N s"; a 429 that names no tracker — Kitsu's, on the reads that find the show's tracker entry and build its episode map — says only that a service is busy: "A service is busy, saving to MyAnimeList in N s" — counting the seconds down live, once a second, from the wait's deadline, then "Saving to AniList…" while the write goes again by itself, up to four attempts in all. The wait and its count both read one steady clock, which a change to the system time does not move, and the wait ends at the first timer wake-up past its deadline, however late a hidden window's throttled timers wake, so the notice says the save is going when it goes. That clock does not count time the machine spends asleep on Linux (on Windows it does), so a write held across a suspend waits out the rest of its wait after waking: it may go up to one wait later than the wall clock alone would allow, and never sooner. The notice comes down when the write lands, fails or is dropped, when a newer write for the show starts, or when the user dismisses it. A write dropped while it waits — newer writes took every field, or its tracker was disconnected or signed in as another user — is let go of within a second rather than at the end of its wait; a sign-in or account change still under way does not end the wait, so a reconnect as the same user keeps the write, and the checks at the end of the wait decide. The notice is pinned, like the sign-in notice, so later toasts do not push it off the stack; there is one per show whose write is held, so saves of several shows inside one cool-down stack a notice each. A screen reader hears the words it opened on and then that the save is going, not each second of the count. Each attempt of an editor save or removal reads the tracker's row again before writing, as the first one did. A held write sends again only the fields no newer write for the same show and tracker has been issued for since it started. A field counts as taken from the moment the newer write starts toward the tracker — once its bearer is in hand — not when it lands, and stays taken if that write then fails — its own failure is the one reported. A save of status and episode that a progress-only write was issued beside during its wait re-sends its status alone; a status the held write set without the user choosing it (the one a new row is created with) never goes on its own, and a completion never goes without its episode. A write left with nothing to send is dropped without a word, as is a removal any newer write was issued beside. That is checked when the wait ends and again just before the write goes. A held write also belongs to the tracker account it was made for: the user the tracker was listed under when the save, removal or progress write was fanned out, read before anything is awaited. If, when an attempt starts or a write goes, the tracker has no account, another user, or an account still being changed, nothing of the write is sent — its re-read included — and it is dropped without a word; a write made while the account is being changed is never sent, though the fields it set still count against older held writes of the show. The same user — after a token refresh, a reconnect, or the account marked expired before its refresh — keeps it, and each attempt that does go carries the bearer the account holds at that moment. A disconnect that lands while a write or a list read is already on its way cannot recall it, but its answer does not write the account back into the cache the disconnect purged: each purge starts a new connection epoch, and a write-through lands only in the epoch its request arrived in, noted before it waits on anything — its show's lock, the id resolve, the owner lookup. The editor can be closed while its save waits, and only that show's editor is locked meanwhile — also after the user leaves the show, for another route or another show, and comes back, when the detail page has built a new editor; reopened, it shows the save still out. Once none of the save's trackers is still connected as the user it was made for, the show is free again: its held writes are dropped with the account. The save carries on and its toast reports how it ended, on whatever page the user is on by then; the editor that started the save, while it is still on screen for that show, applies a clean or partial result and re-reads the entry — closing on a clean save and staying open on a partial one, for its retry. An editor mounted after the save started — the user left the show and came back — re-reads the entry when the save settles, whatever its result, and closes if it is still showing what the save left it: the sent form, or for a removal the entry it took away; a form the user opened fresh, or has edited since, stays. A partial save's retry — the status it still owes the trackers that did not take it, which the next open of the editor offers — is kept per show and bound to the accounts the save was made under: only a later save or removal under compatible accounts may replace or clear it — a status partial replaces it, a clean save or a removal clears it. Compatible means no account switched: no tracker both list is under a different user, and at least one both list is under the same user, so a tracker connected or disconnected in between does not keep a retry alive. A save under another user's account leaves it alone. While a tracker it listed is another user's, or none is still the user it was made for, the retry is hidden; it is those accounts' intent, and is offered again if they come back. A save ends with the saved message, the partial message when some trackers took the edit and others did not, the rate-limited message when nothing landed and a tracker refused every attempt, or the failure message; a removal ends with the removed, rate-limited or failure message. A progress write that cannot be saved for any reason says so ("Couldn't save your progress to AniList"). Background fills show nothing: one held back for a page is retried once the pause ends, as above; anything else they would have filled is asked again on the next view.

The other views of a tracker list follow a write once it settles. Each settled fan-out — an editor save or removal, or a watched episode's progress — names the trackers it went out to and which of them took it; a write dropped before any request went out names nothing. A progress retry superseded after an earlier attempt still names that tracker while the same account is current, because the earlier attempt may already have cached mapped entries. The home page's Watch Later row, while it is on screen, reads its list again after a shown tracker's editor write lands, or after its progress write lands, fails, or is superseded after an attempt: the same reads a visit to Home makes — the backend's cached list, then the Kitsu bridge and the availability filter. A mapped progress write may complete and cache earlier tracker entries before failing on the target entry, so its final failure does not imply an unchanged list. Failed editor writes, which affect one entry per tracker, need no reread. A show's page open on the show a progress write was for reads its entry from the tracker again, quietly, whether the write landed, failed, or its retry was superseded after an attempt; a read still loading when the change comes — or when the editor reconciles a save that landed — is replaced by one that ends the way a page's first read does. The editor's own saves stay with the editor. The row moves only the cards the write changed, the way a card leaves the Continue Watching strip: a card that leaves shrinks and fades out, one that arrives — into an empty row too — grows in, and the cards beside them slide over. Under prefers-reduced-motion nothing moves, in either strip.

The backend's cached list follows the tracker's answers row by row, and an older answer never replaces a newer one the app already cached. A write asks the tracker who the account is before it goes out, so the cache row it changes is filed under the right user even when the write spends the last of the tracker's allowance; a rate limit on that lookup holds the write like any other, while any other failure lets the write go and asks again after it. With an owner, the row takes the write's answer; with still none, the row is dropped from every user's cached list for that tracker rather than left as it was, and Home's next visit reads the list from the tracker again — a refresh already out when the write settled does not count as that read. Each write marks the row it changed. A full-list refresh reads the list once and caches every row of its answer except those a write marked after the refresh started: those keep the write's answer, present or removed. A page of the list read after such a write can carry a later change to that row made on the tracker's website; the write's answer is kept anyway, and the next refresh replaces it. A refresh that started before another one already cached writes nothing, and a disconnect since the refresh started still discards its answer. A removal sends a tracker a delete only where its live read found the show; where it found none, the tracker is asked nothing and the show's cached row for that user is cleared locally, so a tracker that never had the show neither spends its allowance on the removal nor fails it. The clear acts on the latest-sent live read of the row: it removes the row only if no write of the show and no refresh started after the read has reached the cache since, and only if no read sent after it found the show listed. Answers arrive in any order, so reads and refreshes are weighed by when they were asked (a write by when it was cached, no earlier): a read sent before a refresh that is already cached cannot clear the row, however late its answer comes.

A rate limit is not an answer about a show, and nothing caches it as one. An episode-thumbnail lookup that got no answer writes no negative row. A trending fetch AniList did not answer serves the last list AniList gave (or, with none kept, Kitsu's list for that load) without writing over the trending row. A trending page Kitsu failed to bridge is not kept either: failed in whole, it is served as an unanswered fetch is; failed in part, the entries that bridged are served for that load. A detail page whose banner lookup got no answer is served without the banner and not cached.

### When AniList cannot answer

AniList refusing this client, or being down, is no answer: what it would have said is unknown. Nothing reads that as "no", and nothing caches it as an absence — the next read asks again, at the gate's pace. Where Kitsu holds the same data it is already the primary source and AniList only fills its gaps; where it does not, Kitsu is not substituted.

Kitsu's per-episode air dates lag and are often missing for a show on air, and a count read from them could grey an episode that is out. Kitsu's `status` already decides "finished" on the detail and play pages, which skip the airing read for a finished show, and in the availability window, which branches on it |
| The aired count of a show AniList calls finished | The appended-extras evidence, beside Kitsu's own count | The rule does not conclude | None: the rule needs both sources to end the show at the count, and Kitsu cannot vouch twice |
| MAL ↔ AniList id translation, and AniList's listing of the media that record a MAL id | The tracker write-back's target; the tracker episode map's ownership check on a MyAnimeList write; the Watch Later bridge | The write fails with the rate-limit or upstream error; the card is left out for that load, with no dead end recorded | Kitsu's mappings are asked first already. A failed translation is not replaced by the other id Kitsu carries: the write would land on whatever entry that id names |
| The signed-in account's profile, list and entries | The account pages, the list editor, progress write-back | The error is returned as it is | None |
| The tracker's own entries — their episode counts, the sequels they name, whether each has finished airing | The tracker episode map a progress write is filed under ([`title-resolution.md`](./title-resolution.md)) | The write fails with that read's error, a rate limit keeping its wait, rather than going ahead as identity; no map is kept, and the next write asks again | None: the map is about the tracker's entries, which do not line up one-to-one with Kitsu's |

## Watch order

Anime reaches the catalogues in pieces: a story a viewer thinks of as one show — *JoJo's Bizarre Adventure*, *Gintama*, *Bleach: Thousand-Year Blood War* — arrives as seasons, "parts" and cours, films, OVAs, specials and recaps, and Kitsu models each as its own anime, so the app does too. The watch-order surfaces say how those entries connect without merging them: every entry keeps its own page, history and tracker entries. The platforms that fold a franchise into one title with numbered seasons (Netflix, or Crunchyroll's season dropdown) own their catalogue and number it by hand, and even they keep films and spin-offs apart; the databases this app reads store typed links between entries, not franchises. Where the grouping is derived from data rather than curated, "what comes next" has to admit ambiguity — two ways on, an order the data cannot settle — rather than guess, and every surface shows that ambiguity as it is.

Which entries form a run, the main story every page of a franchise shares, a page's own chain outside it, and what sits around the run are decided by the backend's franchise read ([Kitsu's relations, walked into a franchise](./title-resolution.md#kitsus-relations-walked-into-a-franchise)). The order a run is shown in, its numbers and everything each surface decides from them are decided by the backend too (`backend/src/watch_order/`), answered per page by the watch-order routes; the renderer words and draws what they answer (`frontend/src/lib/watch-order/`). Nothing on these surfaces asks the streaming provider anything, and nothing writes to a tracker: every play they lead to is an ordinary play of a Kitsu entry. For the library this was planned from, franchises were the normal case and long: by a rough title match, about 70 % of one viewer's 294 MyAnimeList entries fell in families of two or more, many with films or specials beside the run of series. The provider's own versions of a show (an "(Uncensored)" listing beside the plain one) collapse into the one Kitsu entry, whose play picks the listing, and a history row with no recorded Kitsu id and no stored mapping counts toward no title. The provider also names some titles its own way (JoJo's Part 3 is its "Part 2", and three of *Gintama*'s TV entries are its "Season 2", "Season 4" and "Season 5"); the surfaces name every title as Kitsu does. The surfaces are not behind a flag.

Rules every surface follows:

- **Whole titles.** A tile or card names each entry by the full title the rest of the app shows ("BLEACH: Sennen Kessen-hen", "Boruto: Naruto Next Generations"), never a part of it: a tile clamps it to two lines, the player's narrower Up next card to three, the strip's "You're watching" card to one, and the full title is the tooltip of every tile and link that names one, and leads the accessible name of a tile and of the Up next card's links, except on Continue Watching's hand-off card, whose accessible name is "Up next: <next>, after <finished>" and whose tooltip is on the finished title, on the franchise page's row for the title it was opened from, whose name opens with "You are here", and on the Up next card at a chain's end, which names the franchise; the franchise page's rails of poster cards carry no tooltip, though the title leads each card's accessible name. A title cut against the rest of the run (dropping the words another entry shares) reads as an unfamiliar show, and a shared prefix that is not the franchise's name ("Boruto:") renames the show, so no part of a title is dropped.
- **Plain words.** The copy speaks of titles (in Portuguese and Spanish, of "anime"), never of runs, entries, loops, forks or joins, which name how the ordering works inside the app and meant nothing on screen: "The story starts here", "Nothing after this yet", "Linked with 9 others, order unclear". `frontend/tests/copy/watch-order-plain-words.test.ts` fails on the words known to have been used and their translations, in every locale; it is a list, not a vocabulary check, so a new synonym gets past it. Counts beside a noun ("2 ways to continue") take plural variants; the rest put the number where no noun agrees with it ("Comes after these 2").
- **A franchise read only in part** — the walk stopped at its bound, or a listing came back cut short (`complete: false`) — may be missing titles on either side of the show, since the walk goes outward both ways, so no surface makes a claim that needs the whole: no position, no total, no count of the ways on, no caption for a branch or a loop, and no "Nothing after this yet". Mature catalogue apps show nothing rather than a count they cannot stand behind.
- **Motion and direction.** Every transition uses the duration tokens, so it is zero under `prefers-reduced-motion` (the Up next card enters with the skip pill's own transition, which checks the preference itself), and nothing moves on a timer. Layout uses logical properties only, so a right-to-left locale is a translation.

### Order and position numbers

One app-wide setting decides the order a run is shown in. Every decision in this section and the next ones (order, numbering, grouping, progress, what follows a finale, Continue's hand-off) is the backend's (`backend/src/watch_order/`), answered per page by the watch-order routes (`POST /api/watch-order/<id>/show`, `/franchise`, `/up-next`, `/handoff`, and `POST /api/watch-order/rail`; `backend/src/api/watch_order.rs`), which read the franchise walk, the history and the order setting themselves; the renderer words and draws the answers (`frontend/src/lib/watch-order/`):

- **As linked** (the default): the order the links give, using every prequel/sequel link between two run members, whichever of the two lists it. A link that a longer path through the run already covers is a shortcut and is ignored. Titles that lead round to one another (as ten *Monogatari* entries do) are taken as one block: they count as a single step, links inside the block are never shortcuts, and a link counts as covered only by a path that does not pass back through the title it starts from. *Digimon*'s *Last Evolution Kizuna* lists *tri. 6* as its prequel, while *tri. 6* lists the 20th anniversary story as its sequel and that story lists *Kizuna* as its sequel, so the direct *tri. 6* → *Kizuna* link adds nothing and would otherwise show two ways on where there is one. A title with two remaining next titles leads two ways; one with two remaining previous titles comes after both.
- **As released**: every run member by start date (an unknown date last, then the Kitsu id), as one line that never branches.

Positions count along the shown entry's own path back to the run's first entry: as linked, the title reached by following prequels (shortcuts ignored), taking the earliest-starting one where two lead in and stopping at a block of linked titles; as released, the position is the title's place in the date-ordered line. The run's first entry is, among the members no prequel link reaches, the earliest by start, then the lowest id (`backend/src/watch_order/run.rs`). A path that passes a point where the run leads two ways, stops in a block, or ends at a title other than the run's first is unnumbered, since numbering it would give a second "01": *Gintama: The Semi-Final*, which no prequel reaches, has no number. A total ("of 09") is given only where the order is one line: as linked, a run with no branch, no title with two before it and no block; as released, always. A position is a plain number ("05"), never a "part": franchises use "part" for their own divisions (JoJo's Parts 1–9, *Thousand-Year Blood War*'s cours), and the run's count does not match them.

### The order setting

Settings → Playback → **Watch order**, directly under "Auto-play next episode", as two buttons like the audio and quality choices there: **As linked** (the default) and **As released** ("Por vínculo" in Portuguese, since "ligado" reads as "switched on"). Its hint: "How a series' seasons, films and specials are ordered: as the anime databases link them, or by release date. The links generally follow the story, but they are maintained by each database's community and can be wrong." It is stored as `watch_order` ([User settings](#user-settings)).

One setting decides everywhere: no surface has a toggle of its own, and nothing is marked "out of order", since each tile already shows its year; a choice made in one place and explained once is less to think about than a switch and a warning on every surface. The order the links give is called "As linked", never the story order, because the links are not consistently either ([What the links say](./title-resolution.md#what-the-links-say-and-what-they-do-not)); the maintainer disagrees with some links Kitsu's editors chose, but the app follows the source rather than keeping its own list of differences, and the setting is the way out for a viewer who prefers release order. It changes the order and the numbers, never which titles form the run or which are other versions. The backend reads it with every answer it gives a surface, so a surface draws in the order its answer was read in and never re-orders under the viewer, and a setting that cannot be read means As linked.

For most of the library the setting changes nothing. Applied to the links read across ten franchises on 2026-11-01, one page each (two for JoJo and Fate), "Differ" counting the members whose previous or next title is not the same in the two orders:

|---|---|---|---|
| Attack on Titan (season 1) | 8 | 0 | one line |
| Bleach (2004 series) | 5 | 0 | one line |
| Naruto (2002 series) | 4 | 0 | one line |
| JoJo (2012 series) | 9 | 0 | one line |
| JoJo (the 2000 OVA) | 9 | 0 | one line |
| Fate (*Unlimited Blade Works*) | 6 | 3 | two ways on after *Fate/Zero 2nd Season* |
| Digimon (*Adventure*) | 14 | 0 | one line (one shortcut ignored) |

### The show page's strip

A show in a run of seasons or parts shows its watch order right after the masthead, above the synopsis: "where am I, and did I miss something" is answered before an episode is chosen, and the strip costs one row of height. It draws the entry before this one, this one's place, and the entry after, rather than the whole run, which belongs on a page of its own; a rail of the whole run was tried and broke up at every branch. The show page reads its answer (`POST /api/watch-order/<id>/show` with the viewer's local day, which "not aired yet" is judged against), for which the backend walks the franchise and reads the history row each of its titles resumes from (`POST /api/history/by-kitsu`'s lookup, below), through a loader that never rejects (`loader.ts`): a franchise that cannot be read means no strip and no error, the page as it would be without one, and history that cannot be read means a strip without progress. A history link answered while the page is on screen, made there or anywhere else, reads the answer again, the strip staying as it is until it lands, so a row the link moved onto an entry of the run counts there at once; of two links in a row the second's read is the one drawn, and a link answered while the strip is still being read reads it again once it lands (`strip-reads.ts`). The backend's page model (`backend/src/watch_order/page_model.rs`, served by `wire.rs`) works out the caption, the position, each tile's progress and whether it has aired, the "You're watching" card and what "Similar titles" leaves out. The read can take a second or two on a first visit, so the page holds the strip's room rather than letting the strip push the synopsis and episodes down when it lands (`arrival.ts`, `WatchOrderArrival.svelte`, `StripReserve.svelte`):

- **What is coming.** The show's own relation listing, which the walk reads in its first round (with, where needed, the show's detail and what the walk's parent check reads), already says whether a strip, the franchise link alone or nothing is coming (`GET /api/kitsu/franchise/:id/first-hop`, [the first hop](./title-resolution.md#kitsus-relations-walked-into-a-franchise)). It says the link or nothing only where the walk will draw the same, and the strip everywhere else, so the one wrong guess is a held strip that gives way to the link or to nothing. The page waits for that answer together with the show's details, never more than 300 ms past them and no longer than until the walk has answered; a slower answer is not used, and the strip arrives as it would without one.
- **The held room** is a static outline of the strip's layout under the real "Watch order" label, or of the link, with no shimmer, and nothing is held where nothing is coming. It waits for the walk, with no timeout of its own. When the walk answers with something to draw, the strip fades in where the outline stood (220 ms), from the outline's height to its own; when it answers with nothing or fails, the outline fades (100 ms) and folds away (260 ms). An outline already above the viewport goes at once and the page scrolls by what the change gave back or took, so what the viewer is reading stays put (`scroll-hold.ts`). Reduced motion makes every step instant.
- **A show visited again in the session** draws its strip in its first frame, from the last answer kept for it (the last 200 shows, `session-memo.ts`), which is the answer in the order it was read in, so saving another order setting forgets every one; the page still reads the answer again and draws what it says, except that a read that fails does not take away a strip an earlier read drew; what the session remembers is what the strip last drew, the rows a history link wrote included.

Growing the strip into place, and drawing it under the episodes, were tried as alternatives and dropped.

The strip itself:

- **The band.** One faint band, the page's ink a step up (`--ink-050`) at 72 % opacity with the card corner radius, no border, blur, shadow or gradient, under a "Watch order" eyebrow. Three columns mirrored about the centre: the titles before read towards it (poster on the side nearest the centre, text aligned to it), the titles after read away from it, and the outer columns take equal shares of the width, so the position numeral is the strip's centre whichever side is longer, at every window width. A grid of three rows (the keys, the line for two before or after, the tiles) keeps the three keys on one baseline, and the centre's two hairlines run through all three.
- **The keys** name the link, in Kitsu's roles: "Prequel" and "Sequel", plural where a column holds two ("Sequels"), and a side story's "Parent story" ("Parent stories" where Kitsu names two, with no "Comes after these 2" line, since two parents are not a join). A role names a link, so as released, where the neighbours are neighbours by date, the keys read "Released before" and "Released after": calling the 2006 *Fate/stay night* the "Prequel" of *Fate/Zero* would be false. "Previous: *Gintama°*" on a *Gintama°* side story would put the two in one sequence, and "Parent story" says what Kitsu says. Kitsu names both branches of *Fate/Zero 2nd Season*'s fork `sequel`, so the line under the key ("2 ways to continue") is what tells them apart; a title that comes after two reads "Comes after these 2" (`strip-wording.ts`, `strip-copy.ts`). In Brazilian Portuguese a prequel is "Anterior" and a sequel "Continuação" ("Prequela" reads as translated or European), and a parent story "História principal". Latin American Spanish names a parent story "Historia principal" too. In both, the word for "origin story" would read as where the show began, which a parent story is not.
- **The tiles.** Each title before or after is a small landscape tile linking to its show page, two in a column in start order rather than a guess: the poster, the whole title, and a meta line in two parts in the poster card's voice (the figure bright, its word faint) — format and year, then the episode count or the viewer's progress ("EP 9 of 13"); a watched title shows a check, never a dimmed poster, which would read as unavailable. A title that has not aired shows "Coming January 2027", or "Date not announced", in place of the year and count. A title the provider does not carry looks like any other: the show page it opens runs the availability check, and the strip does not dim titles from cached verdicts either. Recaps never take a tile; the run follows prequel and sequel links only.
- **The centre** holds the shown entry's position as an oversized numeral, with "of 09" where the order is one line; where it is not ("05" alone), the position is read aloud as "Position 05". A title with no number reads "One of the ways to continue" there — past a branch, after a loop, or on a path that does not reach the run's first entry, as *Gintama: The Semi-Final*'s — and one in a loop "Linked with 9 others, order unclear"; the centre's key reads "You are here". The masthead's eyebrow takes the same place in its value slot ("TV · Finished · 05 of 09") only for a run that is one line and read whole: a bare "05" there reads as nothing in particular. A side story beside the run shows "Side story" there, or "Film" when the franchise read lists it under films, as it does every movie around the run, so the strip and the franchise page call the same titles films. The shown entry is not a link.
- **Empty columns** keep their place, drop the key and say why: "The story starts here" before the first title, "Nothing after this yet" after the last one and at a side story's end, so the numeral does not move at either end of a run. For a franchise read in part, an empty column stays blank, and the strip shows no position, no total, no branch or loop caption and no line under the keys; a side story keeps its caption.
- **A page outside the main story** draws its own chain, which the franchise read serves: the heading reads "Watch order", a rule, then "Outside the main story" (also for a franchise read in part, which numbers nothing as anywhere else). Its own titles are numbered among themselves (*Heaven's Feel II* reads "02 of 03", in the strip's centre and the masthead eyebrow alike), and a main-story title the chain meets stands beside them, uncounted, in the column it falls in by the order setting, keyed "From the main story" or "Into the main story" in place of the column's usual key: *Fate/Zero 2nd Season* before *Heaven's Feel I*, the 2016 *Berserk* series after the third Golden Age film. As released, the 2000 *JoJo* OVA is "02 of 02", after the 1993 OVA, with the 2012 series after it, into the main story. A seam keys its column only when it stands there alone; where a branch puts it beside one of the chain's own titles, the column keeps its usual key and count, the seam counted among the ways on. As released a seam takes its place by date, so one that started between two of the chain's own titles stands between them. A chain of one film (the *Unlimited Blade Works* film, *Boruto: Naruto the Movie*) reads "Film", not "01 of 01", and one of anything else shows no number. A side story whose parents are all outside the main story is drawn under the earliest, on its chain, with the same heading (`backend/src/watch_order/chain_view.rs`).
- **"You're watching".** When the viewer's history has another title of the run in progress — the last one part-way in the chosen order — and no tile already shows it, a card in the band's footer, under a hairline and centred at 24rem at most, names it: its poster, "You're watching", its title on one line and its episode. It links to that title's page and never plays, with an arrow rather than a Resume button: a line ending in Resume read as a second play button, and the poster says "this is a show" before the words are read. Its visible text is its accessible name.
- **The way to the franchise page.** The band's footer ends with **See the whole franchise**: a small fan of three posters (the entry the franchise is named after in front, then a film or other version and a side story) and what the page holds ("9 in the main story · 4 films and versions · 1 side story · 1 recap"; no counts for a franchise read in part). Beside the "You're watching" card both are centred at one width (24rem at most), one above the other, the card first, where the band is narrow; without the card the link sits alone in the middle. The posters stand on one arc, as if pinned at a point below the stack, and hovering or focusing the link moves each along it, outwards, with the elastic card easing (6.5° apart at rest, 9° open), and lays a faint plate one step up the page's ink under the whole link, the hover the strip's own tiles use; the watching card takes the same plate and has no border at rest, so the two read as a matched pair (`stack-fan.ts`, `PosterFan.svelte`, `StripFranchiseLink.svelte`). Two posters split half a step to each side, one stands upright and lifts. Only entries that have a poster are fanned, and one that fails to load is drawn as a blank frame; a franchise with no poster at all shows three blank frames, the front one counting the titles the page lists. Under reduced motion the fan is drawn open and does not move. On the way back to rest the cards use the soft easing, so they do not overshoot inwards; open, they take a deeper shadow, and the link's arrow moves forward. The stack was chosen over a plain button ("Whole franchise | 15 titles →") because it shows what there is, not only how much; the plate because it is the only highlight that marks the whole link as one target (an underline marks only the label, a ring reads as a second framed card); and the centred footer because it holds at every width, where laying the pair on the strip's columns fits side by side only from about a 1210 px window. A show with no strip whose franchise page still lists other titles — nothing before or after it but films, versions, side stories or recaps around it, or itself a film, version, recap or side story outside the run with no parent story in it — shows the same link on its own under the masthead (`backend/src/watch_order/franchise_link.rs`); a show that is the franchise alone shows none. The franchise page is reached only this way; search results do not lead to it.
- **"Similar titles"** leaves out every other title the franchise page lists, beside the strip or the lone link, so it never offers part of the same franchise, and waits for the watch order rather than showing a card and then removing it. A parent story's strip does not list its side stories.
- **Keyboard.** Each tile is a link with the poster card's focus ring, in reading order, and the "You're watching" card and the franchise link are tab stops of their own; focus shows the same state as hover under the app's focus ring.

Progress comes from the row each title's own page would resume from. `POST /api/history/by-kitsu` with `{"ids": [...]}` answers each id as the detail page's resume lookup (`/api/history/by-kitsu/<id>`) does, from one read of the history, each row's identity looked up once, and local cache reads only, never Kitsu: a row by the id it recorded while Kitsu still has that entry, else by its stored mapping, else, for a row whose recorded entry Kitsu deleted, by the title match Home stored for it under the row's own cour. Where two rows name one title, the route answers the one watched last, as the Resume button does. A title is watched once its row reaches its last known episode, and part-way otherwise (`backend/src/watch_order/progress.rs`). The watch-order routes read the rows through that lookup themselves, for every title the franchise names, its chain's included. History that cannot be read reads as no rows, so a first read draws no progress, and the answer says so (`history` false): a page reading again after a history link keeps the progress it drew rather than drawing none.

Each visit of the show page cancels its watch-order read when the viewer moves to another show or leaves the page. The read holds its response open while the backend walks the franchise — several rounds of Kitsu reads when Kitsu is slow — on the franchise lane, the one every page's franchise reads share; kept after the viewer left, a handful of such reads would hold all of that lane's connections and queue the next show's walk behind them. A cancelled read draws nothing and is not taken for a franchise that cannot be read.

### The player's Up next card

On the last episode of an entry that has finished airing — the last one the player can step to — the end of the video brings an **Up next** card naming what comes after it. Without it a finale was a dead end: the player stopped at the last known episode and nothing said that a second season existed.

- **Which titles.** The entry's next titles in the run, in the order the setting chooses: every run member it links to as a sequel as linked, shortcuts ignored, or the one that started next as released. Recaps and other versions are never offered, and no other filter applies; a film inside a run is offered when the links make it a sequel. Exactly one that has aired is offered as "Up next", with the viewer's progress on it if they have started it (the row its own page would resume from, as on the strip); one that has not aired shows "Next, when it airs" with its date or "Date not announced", and no link; several (as linked only) show "Ways to continue" over one row each; none shows no card, and "Skip Ending" behaves as before — except at the last title of a chain outside the main story that leads nowhere (the third *Heaven's Feel* film), where the card offers the franchise page: keyed "The whole franchise", named after the franchise, with the strip link's poster fan beside the first two counts the link names, in the accent of the entry the franchise is named after, as its page is. A finale shows one card only, the next title where there is one, else that one (`backend/src/watch_order/chain_end.rs`); like a streaming app's end-of-series card it points somewhere useful and starts nothing by itself. A franchise read only in part gives no card, since the title that really comes next may be missing from it. On a title outside the main story the card follows the title's own chain, as its strip draws it: *Heaven's Feel I*'s finale names *Heaven's Feel II*, and the third Golden Age film's names the 2016 *Berserk* series, the main-story title the chain leads into. The 2000 *JoJo* OVA's finale names the 1993 OVA as linked and the 2012 series as released, while the 2012 series' names *Stardust Crusaders* in both orders, since the series does not list the OVA; *Fate/Zero 2nd Season*'s offers *Fate/stay night* (2006) and the UBW prologue as linked, the prologue alone as released (`backend/src/watch_order/up_next.rs`).
- **A finale** is the last episode or later of an entry Kitsu marks finished, judged by the player's own reading of the entry where it has one, and the card waits for the player's own last step: where the source lists an episode past Kitsu's count, the card shows on that one (`is_finale` in `backend/src/watch_order/up_next.rs`, judged on the player's Kitsu detail, which the backend reads itself; `upNextShown` in `frontend/src/lib/play/up-next-window.ts`).
- **When.** Once the video ends: the element's own ended state, or a playhead within one second of a known length. The slack is a precaution: where a stream played through hls.js has less media than the length it declared, the playhead can stop just short of it and the element never reports its end, so the card would never come; on a stream that ends normally it can show up to a second early. An unknown length decides nothing. So the credits and anything after them (a closing scene, the next episode's preview) play uncovered but for their last second at most, with "Skip Ending" behaving as on any episode; the card first appeared at the start of the credits, and covered them. It stays until it is used or dismissed, unlike the skip pill's five seconds: a seek back puts it away as the seek starts, and reaching the end again brings it back. The page counts the playhead only for the stream on screen, so a finale opened from the previous episode's end does not flash the card.
- **What a click does.** It opens the next title's show page, where Play starts episode 1 (or, at a chain's end, the franchise page). Nothing plays by itself: the end of the video stops there whatever "Auto-play next episode" says, since auto-play decides its step with the same function and inputs as the next-episode button and the card shows only where that step is closed. The player's next-episode button stays within the show being watched. The card does not start playback because nothing has asked the provider about the next title, and the show page is where the app answers that.
- **The provider is not asked.** The card names the next title the relations give whether or not the provider carries it, with no request and no cached verdict, so it never differs by what happens to be cached. Offering "the next one that is available" instead would make the viewer wonder whether the app is skipping something, and would hide the real order. If the provider lacks it, its own show page says so, as for any show, and its strip shows what follows.
- **The card.** It takes the "Skip Ending" pill's place in the player's bottom-end corner, where the eye already goes at the end of an episode and away from the picture's centre, in the pill's dark translucent surface and accent border: the next title's 5:7 poster beside an "Up next" eyebrow, the whole title clamped to three lines (the card is narrow, and the words that tell a franchise's titles apart come last) with the full title as its links' tooltip and accessible name, and a meta line of format, year and progress or episode count (the date, for a title not aired). A wider card with the title's banner covered more than half the picture's height at 1280 px, and banners crop unpredictably at that size. On hover it fills with the accent, as the pill does (`UpNextCard.svelte`).
- **Keyboard and screen readers.** The card never takes focus by itself, so Space and the arrow keys keep driving playback. Its links are focusable, with the focus ring, and Enter opens the title's page (a title not aired has no link, only the close button); Esc dismisses the card while it has focus, as does its own close button, a separate tab stop; a keyboard dismissal gives focus back where it was, a mouse click leaves focus alone (`focus-return.ts`). A dismissed card stays away until the viewer moves to another episode or show, and stays away through a recovery of the same episode; it comes back on a return from another episode. "Up next: <title>" ("Up next: the whole franchise, <name>" at a chain's end) is announced once per episode, written into a polite live region after the card mounts, since a region that already holds its text when it appears is not read by every screen reader.
- **Fullscreen and motion.** The player's own fullscreen shows the card, and it is not one of the controls that hide when the mouse is idle: it is a choice, not chrome. With "Custom player controls" off, the browser's controls fullscreen the video element itself, where nothing else can be drawn, so the card is not put up or announced until the video leaves fullscreen, and then shows if the playhead is still at the end. It enters with the skip pill's settle transition, which checks `prefers-reduced-motion` itself; under reduced motion it simply appears.

The play page reads its answer (`POST /api/watch-order/<id>/up-next` with the day and the episode) through the show page's loader, once per viewing, a show and its episode (`latest-read.ts`), and again when a history link answers while the player is on screen (`link-reread.ts`), the card staying as it is until it answers; a franchise that cannot be read means no card. Trackers get no new writes: the finale's play writes the finished entry's progress as any play does, and the next title's first play writes that title through its own episode map.

### Continue Watching's hand-off

Once the finale of an entry that has finished airing has been played through, its card on Home's Continue Watching row moves on to the title that comes next, rather than offering that last episode again (`backend/src/watch_order/handoff.rs`). Home sends the backend's rail (`POST /api/watch-order/rail`) what only it has read — each row's match and its availability probe's count, whether the player kept a resume position for the row's last episode, the history rows with their matches, and the hand-offs read so far (`rail-request.ts`) — and the rail answers which rows ask for a hand-off and which rows show one; each asking series' hand-off is its own read (`POST /api/watch-order/<id>/handoff`).

- **When it moves on.** Only where the player's Up next card would offer exactly one title that has aired, and only when that title has no history row of its own; in every other case — two ways on (as linked), a next title not yet aired, nothing after it, a franchise read only in part — the row keeps its ordinary card. The second condition matters in a loop: as linked, *Kizumonogatari III*'s finale names *Nisemonogatari*, and without it Continue could lead round the ten-title *Monogatari* loop to titles already watched. Outside the main story the hand-off follows the entry's own chain, as the player's card does; at a chain's dead end nothing comes next. As released there is always at most one next title, so *Fate/Zero 2nd Season*'s card stays as it was as linked and moves on to the UBW prologue as released.
- **Which rows ask.** A matched row whose last episode is the finale of an entry Kitsu marks finished (the player card's rule), and that was not left part-way by the saved watch position the Continue card already reads; the finale is the later of Kitsu's last episode and the last one the row's availability probe found, so a source that lists an episode past Kitsu's count keeps offering it first, as the player does. When the probe answers after the card moved on and finds such an episode, the card goes back to offering it. Only such a row asks for its series, through the backend's cached franchise read; the provider is asked nothing, and a series that cannot be read leaves the card as it was, with no error.
- **Played titles.** A row counts as played for the Kitsu id it recorded and for the id its match found, which differ when Kitsu deleted the recorded entry and the row was matched again. Until every row is matched the played set is not known and no card moves on, so a show played from such a row never flashes up as the next one. Before a card moves on, the backend also asks the resume lookup whether a history row resumes the next title, the rule that title's own page goes by, and moves on only when none does: Home's own matches can miss a row whose stored mapping names it. While that answer is out, or if it fails, the row keeps its ordinary card; a history change asks again. Two finished shows that lead to the same title show it once, on the first row.
- **The card** keeps the row's cell, its 16:9 shape (so the rail stays even), its remove chip and its removal animation (`HandoffCard.svelte`). Its frame shows the next title's banner, or its poster where it has none; its first episode's still was considered and not used. An oversized **NEXT** tag stands in place of "EP N": "EP 1" would read as progress on a show not yet started, and the tag is what says the card changed before any text is read. The small line reads "After <the finished show>", by its whole title, which says why the card changed; the large line is the next title's whole title on two lines, since anime titles put what tells a franchise's titles apart at the end, which the ordinary card's one-line show row would cut. Its accessible name is "Up next: <next>, after <finished>".
- **A click** opens the next title's show page, where Play starts episode 1, not its first episode directly: the viewer arrives where the strip, the synopsis and the episode list say what they are about to start, and nothing has asked the provider about it. Nothing plays from the card. Once the next title has a row of its own, the hand-off gives way to that title's ordinary card, so the row never shows both. Removing a moved-on card removes the finished show from history, as it did before.
- **Reads and the franchise lane.** Each series' hand-off is asked for once per page until the history changes, six at a time and the rest in turn (`handoff-reads.ts`), since a hand-off read holds its connection open while the backend walks the franchise, and the franchise lane gives Home six; Home's own calls (a Continue card's resume reads its row again before it plays, and a removal writes) go to the API lane and never wait behind a walk. When the franchise lane falls back to the API's origin — browser-only development, or a window opened without the lane — the walks share that origin with Home's own calls, so Home keeps two out at a time instead. So on a first visit with many finished shows, some cards move on a little later than others. Leaving Home cancels the hand-off reads still out, and a history change cancels the reads whose answers it drops, the cards already moved on staying until the new answers land. The backend reads the order setting itself; a setting that cannot be read means As linked.

### The franchise page

`/anime/<id>/franchise` lists the whole franchise around a show, reached from that show's franchise link (`frontend/src/routes/anime/[id]/franchise/+page.svelte`). It reads its answer (`POST /api/watch-order/<id>/franchise`) through the same loader as the show page, and drops an answer for a show it has already left; one pure function, `franchise_page` (`backend/src/watch_order/franchise_page.rs`, with the main story's layout in `sections.rs` and `no_clear_place.rs`), decides the whole page, using the strip's own ordering, so the page and the strip never disagree about a title's number or about which title the viewer is watching. The topbar reads Home · the show it was opened from · Franchise. There is no order switch on the page; a line under Resume says which order the list follows ("In the order the anime databases link them." or "In order of release."), with a link to Settings.

- **Masthead.** The page reuses the show page's frame. It is named after the franchise as the backend names it ([the name](./title-resolution.md#bounds-the-name-and-what-the-answer-depends-on)), in the italic display serif under a "Franchise · 15 titles" eyebrow (every title the page lists), and the hero band and the masthead's poster show the entry the name comes from, whose accent the page takes: the artwork beside the name is that title's, not the one being watched, which put *Steel Ball Run*'s art beside the 2012 series' name. Where dropping "(TV)" would clash, the suffix stays rather than a year: "(2012)" would read as naming the first season, not the franchise. **Resume**, styled and glowing like the show page's Play, goes to the title the viewer is part-way through, with its number, title and episode beside it; with nothing part-way, **Start from the beginning** goes to the first title.
- **Main story** is a vertical list rather than a rail, so long titles have room and branches and loops can be laid out as what they are: each row an oversized mono numeral, a small poster, the whole title in the body face, a format, year and episode-count line, and the title's progress in words in the right column (`row-progress.ts`): "EP 6 of 14" with a thin line under it where the title is part-way through a known total, "EP 5" alone where the total is not known, a check and "Watched", with no line, for a finished title (a full line on every finished row read as a marker, not a measurement), and nothing for a title not started. The caption is text in the row's link, so a screen reader reads it with the title; the line is decoration, drawn in the one list-progress colour (`--progress-fill` on `--progress-track`) whatever the show, where the player's scrubber and the "You are here" rule keep the show's accent. The title the page was opened from is marked "You are here" (`aria-current`). Progress counts toward the title whose own page would resume from a row, as on the strip. Straight stretches are numbered from the run's first entry as the strip numbers them. Where the story splits, the ways on stand side by side under one heading ("2 ways to continue"), unnumbered and with no label of their own; a split left with one way (the others start at a join or in a loop) is listed as a line. Titles linked to each other in a circle form one group under "10 linked titles, order unclear", with one sentence on why ("These are all linked to each other, so there's no clear order to watch them in. They're listed as they're linked."), listed along their links. A title with no number that only leads into a title with a place stays in place and says "Leads into …"; titles the page cannot number otherwise, such as those after ways that join back up, gather at the end of the main story under "No clear place in the order". As released, every one of these is a single numbered line.
- **Around it**, as rails of poster cards under the app's eyebrow, in the sections the franchise read gives: **Other versions**, **Films** (every movie around the run, whatever its role), **Side stories & specials** and **Recaps**, the last shown from the start like the others, with its count.
- **A franchise read only in part** may be missing titles at either end, so the list ends with "There may be more titles than the ones listed here." and the page leaves out what it cannot stand behind: row numbers, the title count, the place beside Resume and "Start from the beginning", the count over ways on ("Ways to continue"), the count over a group linked in a circle ("Linked titles, order unclear") and the count beside Recaps. The rows keep their layout, the titles with no clear place keep their stretch, Resume still works, and the page never says the show is alone.
- **When it cannot be read** the page says so and offers **Try again**; a franchise that is the show alone says it has no other seasons or related titles.
- **A history link answered while the page is on screen** (one made on the show page or in the player just before) reads the rows again against the franchise drawn, as the strip does, and the page stays drawn until they answer; one answered while the page's first read is still out reads the franchise afresh (`link-reread.ts`).
- **Keyboard and motion.** Resume, the Settings link, each row in reading order and the rails are tab stops in that order. The page enters like the show page and does not animate under reduced motion.

## Caching

| Asset | Storage | TTL |
|---|---|---|
| AniList trending row | SQLite `meta_cache` | 1 hour |
| Kitsu seasonal / top / recent | SQLite `meta_cache` | 6 hours |
| Per-anime metadata (`/anime/:id`) | SQLite `meta_cache` | 7 days for a finished show; 24 hours for any other status |
| A page of Kitsu's episode list (per Kitsu id + page; read by the detail page's strip, the appended-extras check and an episode map's chain rule) | SQLite `meta_cache` | 7 days when the show's cached detail says it finished at least a week ago; 24 hours for any other status, a show that finished within the week or gives no full end date, or when no detail is cached |
| AniList's episode stills for a show (per Kitsu id; fill the stills Kitsu's pages lack) | SQLite `meta_cache` | 7 days when AniList says the show finished and its cached Kitsu detail says it finished at least a week ago; 24 hours otherwise; 5 minutes for a show Kitsu maps to neither AniList nor MAL |
| Availability probe (positive, ongoing show) | SQLite `meta_cache` | 24 hours at most: with the next airing known — when the row is written, or once the schedule is cached after it — until 1 hour after it when that is sooner, and 1 hour when that airing time has already passed or the schedule counts one or two more aired episodes than the provider lists |
| Availability probe (positive, finished show) | SQLite `meta_cache` | 30 days, until a resolve against the show rewrites the row with the ongoing window (a replay, and a resolve whose count was unread beside an exact count from the same provider, leave it as it is; see [Providers and failover](#providers-and-failover)) |
| Availability probe (negative — a clean miss, or the requested mode absent, from the provider that answered; served while that provider's gate has been seen answering and every gate ahead of it is refusing) — finished show | SQLite `meta_cache` | 7 days when the probe wrote the row; 24 hours at most when a resolve did (below) |
| Availability probe (negative) — ongoing show, or one with no airing schedule known | SQLite `meta_cache` | 24 hours at most: with the next airing known — when the row is written, or once the schedule is cached after it — until 3 hours after it when that is sooner, and 1 hour when that airing time has already passed |
| Availability probe (negative) — unreleased show with a known premiere | SQLite `meta_cache` | until 3 hours after the premiere, within 1 hour to 7 days |
| aniskip OP/ED skip-time intervals (per Kitsu id + MAL id + episode + episode length) | SQLite `meta_cache` | 7 days |
| A show's MAL and AniList ids from Kitsu's mappings (per Kitsu id) | SQLite `meta_cache` | 30 days when both are present; 24 hours when either is missing |
| An id AniList translated to or from MAL's (per id, each direction), and every AniList media recording a MAL id | SQLite `meta_cache` | 30 days; 24 hours for an id AniList does not index, or a MAL id no media records |
| A show's episode map on one tracker — which of the tracker's entries each Kitsu episode belongs to, under which number (per tracker + Kitsu id + the resolved entry and its total, or `unresolved` for a show Kitsu's mappings resolve to nothing; `tracker-map:v3:`) | SQLite `meta_cache` | 30 days when the counts agree or a rule explained their difference over entries that have all finished airing; 24 hours when a count was unknown, nothing explained it, an entry is still airing, or the show resolves to nothing; nothing for a read that failed |
| Title matches (search text → Kitsu/AniList ids) | SQLite `title_match` | 30 days |
| Long-term play resolution (resolved stream URLs) | SQLite `meta_cache` (`play:` rows) | 7 days, or until upstream rotates |
| In-flight play-resolution coalescer (`play-cache.getOrFire`) | Renderer-side `Map` | Until the page clears the show's prefetches or the resolve fails; the sessions it holds last the backend session table's 4 hours (also dedupes concurrent calls) |
| AniList banner per Kitsu id (from the trending feed) | SQLite `meta_cache` | 30 days; rewritten or dropped by each trending answer that lists the show, and dropped by a detail read once the image proxy has found the URL gone |
| Image URL the upstream answered 404 or 410 for | SQLite `meta_cache` | 30 days, or until a fetch of it succeeds |
| Poster + banner image bytes | Filesystem `images/<shard>/<hash>.<ext>` | LRU, capped at 500 MB |
| The last good remote flags file ([Remote flags](#remote-flags)) | Filesystem `remote-flags.json` in the cache root | Replaced by every successful fetch, in the launch or later in its session; decides the next launch's flags when the file misses the cap, for 7 days |

Only the probe passes the show's status when it writes an availability row, so a negative row's lifetime, like a positive one's, depends on what wrote it last. A play, a download, a hand-off or a page's warm whose walk ended in a clean miss stamps that miss through the resolve path, which writes without a status, so the negative row it writes — over a probe's row, or where none stood — gets the window of an ongoing show whatever the show's status: 24 hours at most, dated from that operation, a finished show's seven days and an unreleased show's premiere-sized window included. The row is served as any negative row is, under the read rule above, for as long as it lasts, and the status-sized window comes back only when a probe runs and writes the row again.

Image bytes never live in SQLite; they're filesystem-keyed by `sha256(url)[..16]`, sharded two-deep to avoid huge flat directories. The play-resolution cache lives in `meta_cache` as its own `play:` rows — it stores fully-resolved stream URLs keyed by the request tuple `(title, mode, episode, year, episode count, subtype)` so a repeat visit to an episode skips the whole provider walk. Four things retire a row. A cached URL that fails on use is dropped there and then — upstream URLs rotate, so the layer self-heals through a HEAD check before every hit and through the player's own error feedback. A seven-day absolute bound sits on top, which reads do not renew. And the key carries a schema version: when what a row holds changes meaning — a new field its readers depend on, or an existing one that no longer says what it used to — the version moves, no request builds the old keys any more, and those shows resolve afresh. When only the key's shape changes and an old row is still the answer, the rows are carried instead: v29 took the quality out of the key, since every play resolves the master, and opening the cache copies each v28 row asked at `best` to its v29 key, with its moment and lifetime, before the reclaim runs (`cache::play_rekey`); a v28 row kept for another quality held one rendition and goes to the reclaim. No release keyed its rows at v28, so a released install's rows (v26) resolve afresh. Removing a show from the history deletes its rows too, as [Watch history and removing it](#watch-history-and-removing-it) describes.

Every key family the cache keeps is declared once, in `backend/src/cache/families.rs`, with the version this build reads, and every key builder takes its prefix from there. Opening the cache at launch deletes, under the migration lock and in one transaction, every row whose key no declared family holds — a family re-keyed or retired, whose old rows no reader of this build asks for — and every row past its lifetime, except in the families a reader takes past it: the availability verdicts (whose window a reschedule rewrites in place), AniList's trending list (served stale while AniList is down), and the current versions of the reverse mappings and title matches (which a history removal and the detail page's lookup for a deleted Kitsu entry read whatever their age; the removal also reads the versions before by prefix, and finds them only until the first launch after each version bump reclaims them, while the lookup reads the current version alone. A removal then finds fewer Kitsu ids for a show known only by an old mapping or match: skip times and stream addresses under those ids wait out their own lifetimes, a note that Kitsu answered such an id gone stays for its year, and the numbering of a key a page of the show resolved under another key stays until the history is cleared, as a rowless key's does. A row whose recorded entry Kitsu answered gone, matched only under an old version, is matched again only if the home page's next load matches it under the current rules; one it cannot match stays unmatched, and the detail page no longer resumes it under the old match). Before, nothing deleted a row once it expired and a re-key only moved the readers to new keys, so both stayed in the file for good. The reclaim keeps no marker — it finds its work in the rows — so a launch with nothing to reclaim reads the keys and deletes nothing, and the diagnostics page counts what a launch deleted. A version bump needs no step of its own: the old version stops being declared when the bump lands, and its rows go at the next launch — unless they are carried to the new keys first, as the play family's v28 rows asked at `best` are. Going back to an earlier version after that finds its own families' rows gone; it rebuilds them by use, except the mappings and title matches of history rows from a provider no longer walked, which nothing plays again. In test builds every read and write the app's own code makes of a cache row by its exact key is checked against the registry, so a family that is kept without being declared fails the suite rather than losing its rows at launch. The check covers what the suite exercises; reads by prefix and deletes are not checked, and the registry's own cases cover a builder no case reaches.

The **availability TTL branches on Kitsu's `status` field**: shows airing weekly need a 24-hour window so a new episode surfaces within a day, but finished shows can hold for 30 days. A positive row for a show still airing is cut further when the airing cache knows its next airing: it expires an hour after that airing (an hour from now when the airing time has already passed), so a count written just before a weekly drop does not outlive the drop by most of a day. A count written just after a drop can be stale in the other direction: AniList has already moved on to the following week while the provider has not listed the new episode. So when the schedule's aired count is one or two ahead of the provider's count — the most a single drop moves it — the row gets the post-drop hour instead; a wider gap means the two number different entries, and the next-airing bound stands. The home warm batch-seeds the schedule for every show on air or to come before it probes, in batched AniList requests — per 50 shows, one by AniList id and one for the shows Kitsu maps to MAL alone, plus the single lookup for a MAL id several AniList media record and two more for each page AniList cuts short, never one per show — so its rows are bounded when written. Elsewhere the schedule can reach the cache after the count — a detail page asks for both at once, and a seed can fail — so every airing write also cuts the show's live positive rows, in both audio modes, the same way, as a local rewrite of their window that makes no request — and every availability write re-reads the cached schedule after its put and cuts the row it wrote, so whichever of the two lands second applies the cut. Negative rows written with the 24-hour window get the same treatment under their own rule, cut to 3 hours past the airing: a current show's negative probed outside the warm fetches no schedule first, and a pre-premiere one whose schedule fetch failed falls back to the day. The rewrite only ever shortens, whatever window the row was written with — so a premiere moved earlier also cuts the negative its old date sized — and a finished show, which has no next airing, is never cut. Unknown / missing status falls back to the short (24h) window — a stale "no episode 1161 yet" is much worse than re-probing too eagerly. The long window belongs to the probe's own row: every other writer — a play, a download, a hand-off, a page's warm — stamps the row without a status, so a finished show's row is rewritten with the ongoing window, dated from that resolve; a play, hand-off or page warm served from the resolution cache writes only where no positive row stands, and leaves a standing one its own window.

## The copy earlier versions maintained

Versions before 0.12 shipped the script inside the bundle and kept it
current: a writable copy was seeded into `$XDG_CACHE_HOME/ani-gui/`,
the carried test-loader guard was stripped from it, and a background
task ran `-U` against it at every launch. A setting governed that and
the **/diagnostics** page showed a log of the runs.

Native resolution made the whole flow unreadable by anything. The copy
was not on `PATH`, no packaging exposed it, and a separately installed
`ani-cli` was never touched — so it updated a file nobody could reach,
over the network, on every start.

All of it is gone. What remains is a boot-time sweep: if that cache
copy is present, the backend deletes it and reports the path on
`/api/app-info`, so the **/diagnostics** page can say what was removed
rather than the file vanishing silently. The sweep takes a regular
file at exactly that path — a directory wearing the name is left
alone, and the neighbouring image cache and database are never
candidates.

## Remote flags

Remote flags are values a released build reads at launch from a file
on GitHub, so a flag can change without shipping a release, and, from a
signed file, a feature that ships off can be switched on. The code is
in `backend/src/flags/`. How to edit the file is in
[`development.md`](./development.md#remote-flags).

**One file, read by the backend.** The file is `flags.json` on the
repository's `flags` branch:

```json
{ "flags": { "some_feature": false } }
```

The backend reads it from
`https://raw.githubusercontent.com/JoaoPucci/ani-gui/flags/flags.json`,
and its detached signature from the same address with `.minisig`
appended. The renderer never fetches either. `GET /api/flags` answers, once the
launch's flags are decided, with their values and where they came from
(`origin`: `file`, `cache`, `defaults`, or `test` in a test run).

**Every flag is declared in code**, in `flags::DECLARED`, with a name, a
kind and a stated reason. The kind fixes the only values the file may
send.

**Flags are default OFF, and any read failure means OFF.** Every flag's
built-in default is off. It stays off when the file sends anything else
for it (a value the declaration does not allow, the wrong JSON type, or
no entry at all) and when there is no usable file. Flags the build does
not declare are ignored. The value resolution returns is the
declaration's own, never one copied from the file.

**One kind: a rollout, which only a signed file turns on.** A flag is
declared as a `flags::FlagKind::Rollout`: a feature that ships off. Any
file may send `false` for it. `true` turns the feature on, and counts
only in a file whose signature verifies (see "What a signature adds"
below); from any other file it is dropped, and the flag stays off. A
release declares one flag, `hero_airing_first`, the home hero's
airing preference ([The hero banner](#the-hero-banner)); a test-run
build also declares the probe the end-to-end suite drives.

**Read through the declaration, on only for `true`.** Consumers read a
flag through its declaration (`Resolved::enabled`), never through a name
typed out again, so a misspelt or undeclared flag reads off. The
renderer reads one through `flagOn(name)` (`frontend/src/lib/flags.ts`),
which is on only when the window was opened with exactly `true` for it:
a window opened without flags, a backend that never answered and a flag
the set does not hold all read off. Whether a feature is safe to turn
on from a signed file is not something a type can see, so each
declaration states its case in `safe_because`, and a test refuses a
declaration that leaves it empty.

**Every value is tested.** A flag sits at its default until something
changes it, so its other value is the one least likely to have run.
Each consumer registers a test case for its flag's default and for every
other value it allows in `flags::matrix::CASES`, a check that receives
the flags with that value in force. A test over `DECLARED` fails while
any value of a declared flag has no case, or a case names a flag or
value no longer declared.

**What a signature adds.** Each attempt at the file also asks for
`flags.json.minisig`, at the same time, from the same branch and host.
Once the file has arrived the signature gets at most 750 ms more; one
that is later, missing, over 4 KiB or not a signature counts as none,
and costs the turn-on, never the flags. The launch's two-second cap
counts the signature's wait too, so a file that arrives late in the cap
beside a slower signature can miss it; it is then cached for the next
launch, as any late file is. The backend verifies the file's
exact bytes with minisign (Ed25519 over BLAKE2b-512, the prehashed form
only) against the public keys compiled into the build
(`flags::signature::TRUSTED_KEYS`); any of them will do, so a new key
can ship a release before the maintainer signs with it. A verified file
is used whole. Any other file loses every `true` and keeps the rest,
which can only leave features off: so someone who rewrote the file in
transit, or got write access to the branch without the signing key,
can switch nothing on that the maintainer has not signed before (an
older signed pair, below). That is also why the flags still apply while
signing is not set up, or when a signature is stale: an unsigned edit
can still turn a feature off. What is cached is the admitted document
(see "The last good copy" below). The shipped build trusts no key yet,
so no file turns anything on until a release adds one. Signing,
trusting and rotating a key are in [`development.md`](./development.md#signing-the-flags-file).

What a signature does not cover: the cached copy is the user's own disk
and is read back without checking again, so a feature a verified file
turned on stays on for up to the cache's seven days on a machine that
cannot reach the file, including after the signature is withdrawn; and
an older signed pair of file and signature, republished, verifies
again. A feature meant to go off again is set to `false`, which any
file may do.

**Decided once per launch, behind the splash.** The flags are decided
once, within two seconds of the backend starting its refresh (just
after its state is built), and do not change for the rest of the
session. A cache read slower than that decides when it ends, up to the
three-second limit below.

1. The Electron main process puts up a splash at once, as the backend
   starts. It opens before the desktop's reduced-motion setting has
   been read (within half a second; about 20 ms on GNOME, at once
   elsewhere), so it holds its first frame until that read settles,
   and is then told either to start its motion or to rest on its
   finished still frame: a reduced-motion user never sees it move.
2. The backend starts the fetch in a task of its own as soon as its
   state is built, and reads the cached copy beside it. If the file
   arrives within two seconds of that start (the cap), it decides the
   flags. Otherwise the cached copy decides them (below), or the
   defaults when there is none. While a slow cache read is still
   running, a file that arrives first decides, even past the cap.
3. Once the backend has announced itself, the main process asks
   `GET /api/flags`, which answers when the flags are decided. It opens
   the app's window with them, so the preload puts them on
   `window.aniGui.flags` before the first page renders. The main process
   waits at most four seconds for that answer, and opens the window
   without flags if none comes. The renderer then runs on every flag's
   default while the backend may have decided otherwise, for the whole
   session. The preload marks that case with `window.aniGui.flagsOrigin`
   set to null, so a renderer consumer that must agree with the backend
   can ask `GET /api/flags` itself.
4. The splash is on screen first and alone. The app's window, like the
   splash, is made on the app's own dark background (`--ink-000`), so
   nothing white shows before a stylesheet loads. It loads and paints
   its first page hidden, and its renderer says when that page has
   rendered (two animation frames after the root layout mounts); the
   reveal waits for that word, with the splash up and, once the page's
   step has been pending for 700 ms, its stall line. While the splash is
   up the wait has no bound, and a window is never revealed before its
   page has rendered. A launch whose first page has not rendered 15
   seconds after the splash painted, whatever step is still pending,
   leaves the splash stuck instead (below). A window with no splash to
   stand in for it (one opened later, or a boot whose splash could not
   be made) waits at most 15 seconds from its creation and is then
   revealed anyway, on the dark background. Once it is ready to show,
   it also waits up
   to a second for the splash to answer that it has rendered a frame,
   then until the splash has been on screen for 500 ms since that paint
   (300 ms when it rests on its still frame) — long enough for the
   opening to read — and only then is it mapped, already maximized and
   painted, and the splash closes. A launch whose window is ready later
   than that pays nothing for the minimum; a warm one, whose window is
   ready as soon as the splash has painted, pays up to that half second
   for it. The rail's completion hold can add to either: a page that
   renders less than 250 ms before the minimum runs out (150 ms on the
   still frame), or after it, or after a splash that painted too late
   for the minimum, holds the reveal until 250 ms (150 ms) after it
   rendered, so the rail's last stretch is seen lit.
   The two are never on screen competing, so it does not matter that
   native Wayland ignores always-on-top. A splash that never paints, or
   is minimized, holds the window no longer than that first second.
   The exception is a machine where a hidden window gets no frames:
   native Wayland with software compositing (a virtual machine, a GPU
   that failed or is blocklisted, `--disable-gpu`). There the page could
   never draw the two frames, so the renderer also says when the layout
   has mounted, which needs no frame, and a window whose rendered word
   has not followed 1.5 seconds later is mapped without asking for the
   focus (and maximized, on Linux); its frames resume and the reveal
   goes on as above. Where always-on-top holds, the window stays behind
   the splash. Wayland stacks it over the splash and, while the app has
   the focus, focuses it, so the splash is mapped again whenever the
   woken window takes the focus, and the window shows around it until
   the reveal. The splash itself is shown
   250 ms after its page loaded when no paint came first, and the
   window's first-show guard accepts the page's rendered word as well as
   `ready-to-show`, which a window never on screen may not reach. The
   hidden window is made at the size the desktop granted the window when
   a launch last revealed it maximized on the same display (by id, size
   and scale), kept in `window-geometry.json` under the app's user data,
   else at the work area. On Wayland, which reports no work area until a
   window is on screen, that remembered size is what lets the window
   appear at its final size. The first launch on a display, or one after
   the display's size or scale changes, paints at the full screen; one
   after its top bar changes paints at the old remembered size. Either
   takes a one-time correction from the compositor as it appears.
   Closing the splash before the app's window appears cancels the
   launch. Measured on GNOME under Wayland and on Xvfb; X11 with a real
   window manager and Windows were not measured.
5. A first page that is late leaves the splash stuck
   (`electron/lib/splash-stuck.cjs`). Fifteen seconds after the splash
   painted, with the page not yet rendered, its line says "Taking longer
   than usual to start.", the pending stretch of the rail pulses
   faintly, and Restart and Quit appear under the line, in the app's
   language. The film keeps running. The splash stops being
   always-on-top, since it now waits for a decision, and flashes its
   taskbar entry once when it does not have focus. Nothing is focused
   for the person: Tab reaches Restart, then Quit, Enter or Space uses
   the focused one, and Escape does nothing. Quit is closing the splash:
   the launch is cancelled. Restart first arranges a relaunch of the
   whole app, then ends the launch the same way; the new process starts
   only once this one has exited, so it takes the single-instance lock
   rather than handing over to the one that is exiting
   (`electron/lib/relaunch.cjs`). Electron's own relaunch does that for
   the .deb, the Windows install and development; in the AppImage, whose
   binary sits on a mount that goes away with the process, a detached
   shell waits for this process to exit and then runs the AppImage file
   itself. A page that renders after the stuck state hands over as
   usual: the rail completes, the actions go inert, and the window is
   revealed. A choice that reaches the main process before that wins,
   and nothing is revealed. While the splash can offer its choices, no
   new deadline gives up on the person's behalf: a packaged launch keeps its
   two-minute deadlines for the backend's handshake and the window's
   first paint, whose failure dialog takes the splash away, and a
   renderer that dies fails the boot as before. A splash whose own page
   crashes is reloaded, at most twice per launch, and offers its choices
   again. One that crashes past that, or whose page fails to load, is
   navigated away (navigation and new windows are refused on the
   splash), exits, or loads with nothing to offer, can no longer offer
   a way out, so the page gets 15 seconds more, counted from the loss or from the
   window's creation if that came later: if it renders within them, the
   window is revealed as usual; if not, the boot fails with the same
   dialog rather than waiting for ever or revealing a window that may
   be empty. The log has a
   line for each: the stuck state (which step, how long after the
   paint), the choice, and a page rendering after it (how long after).

The splash is a 35mm strip of the app's mark pulled through a lit gate a
frame at a time, beside the app's name with its version above it
(`electron/splash/`). The version is the app's own, labelled as the rail
and About label it (`-dev` in a dev run), and the main process opens the
page with it. Nothing else on the splash is a number, since any number
on a screen this brief reads as a count. Under the name, a wordless rail
of film edge lights one of its three stretches as each step of the boot
lands: the backend's handshake, the launch's flags decided, the app's
first page rendered (`electron/lib/splash-progress.cjs`); the last
stretch lights as the window is about to be revealed, held the same way,
so the rail is always seen complete. The splash waits at most 150 ms, about a millisecond in
practice, for its page to take the last step. A last step landing so
late that the splash's minimum time on screen would not show it then
holds the splash until 250 ms (150 ms on the still frame) after that
step landed, so the rail is seen complete before the app's window
replaces it. A line under the rail, in the app's language, appears only
once the pending step has taken longer than 700 ms, and then stays until
the splash closes; only its words change, when the reason does. While
the flags step stalls it says "Network is slow — starting in a moment…":
the app is waiting on the flags fetch, for at most its two-second cap,
and what it starts with (the file if it lands in time, else the saved
copy or the defaults) is not decided yet. A slow read of the saved copy
can hold that step too, rarely. Any other stalled step says "Starting
up…", and once the flags land the network line gives way to it at once.
The splash's motion starts only when the main process tells it to, once
the window is on screen and the reduced-motion setting is known; under
reduced motion it rests on a still frame and its rail lights without a
wipe, and the page's own fallback timer, for a signal that never comes,
rests it too rather than starting the motion. The mark is `mark.svg`
alone, and the layout holds for a mark of another shape, so a new mark
replaces one file.

The store accepts one decision and refuses every later one. A backend
consumer reads the flags with `FlagStore::settled()`, which waits for
that decision. Past three seconds it decides the defaults itself, so no
reader ever sees a value that changes afterwards. `FlagStore::current()`
does not wait and is for diagnostics only.

**The cap bounds the wait, not the fetch.** After the cap, the fetch
goes on in the background. Its whole request, connect to body, has 45
seconds, 30 of which may go on connecting (DNS, TCP and TLS): the file
is tiny, so the time goes on the connection and round trips. The flags
use a client of their own for that, where the metadata client allows
10 seconds. The connector splits the connect timeout across the
addresses DNS returns, so with the CDN's four addresses each TCP
attempt gets about 7.5 seconds before the next address is tried. When
the file arrives it is cached for the next launch. When that attempt
fails, the file is fetched again later in the session, after 3, 10 and
30 minutes and then hourly, until one attempt succeeds and is cached.
The retries exist to fill the cache, so a launch with no cache
directory makes the one attempt only. A 404 counts as a failed attempt,
so until the `flags` branch exists every session retries on that
schedule. None of this changes the running session's flags. Worst
case: one launch delay; never stuck unless the file can't be downloaded
at all during an entire session. On a connection that always misses
the cap, the cached copy decides the next launch's flags, as long as the
file arrived at any point during the previous session.

Only a 200 whose body is at most 64 KiB and is a `{"flags": {...}}`
object counts as the file. Anything else counts as a failed fetch: a
transport error, the timeout, any other status (404 included), a larger
body, or malformed JSON.

**The last good copy.** Each successful fetch is cached as
`remote-flags.json` in the cache root, together with the time it was
fetched. When the file does not arrive within the cap, the cached copy
decides the flags if it is at most seven days old, and the defaults
decide them otherwise. A copy dated in the
future (a clock set back) counts as too old. The cached copy goes
through the same resolution as a fetched file, so a cache written by
another build, or edited by hand, still resolves only to values this
build declares. The cache marks an entry verified when its document
holds a `true`, which only a verified file keeps through admission. An
entry without the mark is admitted again when it is read, as an
unsigned file. That covers the caches the first remote flags release
wrote, which kept the file as fetched with nothing checked: they cannot
turn a feature on, and their other flags are kept. Why seven days:
every value a document can produce is one its flag's declaration
allows, and a cached copy turns a feature on only if the maintainer
signed that. Its age only limits how long a value the maintainer has
since changed (a feature turned off again) stays in force on a machine
that cannot reach GitHub. A week covers a stretch of launches without
the network, such as a trip, a captive portal or a blocked CDN, so a
flag keeps its value through it. And even on a machine that never
reaches the file again, a changed value clears within the week.

**Test runs bring their own flags.** A test run is a launch with
`ANI_GUI_UNATTENDED=1`, which the end-to-end launch helper and the
backend's integration tests always set. A test run's backend never
fetches the live file, so a flipped flag or a slow or rate-limited CDN
cannot change a test's result. It takes its flags from the file
`ANI_GUI_TEST_FLAGS_FILE` names, admitted and resolved like the live
one (a `true` in it counts only when a `.minisig` beside it verifies
under the build's keys), or the defaults when that names none. A
backend built with the `test-run-key` cargo feature, which only test
builds enable, also trusts a test run's file under a fixture key whose
secret is public, and declares a probe flag that gates nothing; the
live file is never trusted under that key. The end-to-end suite runs a
package whose backend has the feature, so it can run every flag off and
on (`electron/e2e/flags/`). No release script enables it
(`tests/arch/test_run_key.sh`, both platforms), and the e2e workflow
builds the release-shaped Linux package, and the Windows backend as a
Windows release builds it, in jobs of their own and checks that
neither backend contains the key. The Packages workflow, which builds
the release files, makes the same check on each package's backend.
`ANI_GUI_TEST_FLAGS_FILE` means nothing without `ANI_GUI_UNATTENDED=1`. `backend/tests/flags_launch.rs` proves
it by watching the network: a test run never asks for
raw.githubusercontent.com, and a normal launch does. Development runs
(`pnpm dev`) are normal launches and read the live file.

**Rate limits.** `raw.githubusercontent.com` is GitHub's content CDN,
not the REST API. The request does not count against the 60 requests
an hour that GitHub allows unauthenticated REST callers, which the
update check uses. GitHub publishes no figure for the CDN's own limit.
One request per launch, and at most one an hour after the first few
retries of a session whose fetch keeps failing, is far below any
plausible one. A rate-limited answer is a failed fetch like any other.

## Feature tips

The backend keeps a registry of feature tips, short notes about what an
update brought, each meant to be shown once per install. It decides
which ones an install is offered and records the ones closed. It sends
ids and places, never words. The code is in `backend/src/onboarding/`.

**The registry.** Each tip is declared in
`backend/src/onboarding/tips.json`: its id (the key its seen state is
kept under), its tool (`single`, `sequence` of at most three steps, or
`entry`, a balloon on a feature's entry point that offers the feature's
walkthrough), the release that shipped it (`since`), an optional end
(`until`), its page, its moment (`arrive`, or `stream-load` in the
player), an optional flag, and its places, the `data-onboard` ids of
the elements its steps point at. A tip marked `on_demand` runs only when
asked for (a walkthrough, or a tool's demonstration on the Debug page)
and is never offered. The backend's tests hold the file to these rules
(`onboarding::decl::validate`).

**Windows.** A tip is offered for two minor releases from the one that
shipped it, unless it declares its own end: shipped in 0.19.0, it is
offered in 0.19.x and 0.20.x and gone from 0.21.0. The count stays within
one major number, so a major release closes every window the one before
it opened. A tip whose feature is behind a flag is offered only while the
flag is on, and its two releases count from the first read of the tips
with the flag on, with its declared end, which a flagged tip must have,
as a hard limit. A tip
offered and not yet seen is pending. Seen is per tip and forever: any way
of closing a tip marks it.

**The record.** `onboarding.json` in the state directory, beside the
watch history (`config::paths::state_dir`, so on Linux
`$XDG_STATE_HOME/ani-gui/` and on Windows the app's folder under
`%LOCALAPPDATA%`). It holds the tips seen, the release a first-ever
install started on, and per flag a tip names the release of the first
read with it on. A file that cannot be read reads as an update's empty
record, and the next write replaces it. Writes go through a temporary
file, synced to disk and renamed over it.

**First-ever installs.** A new install has nothing new to be shown.
0.19.0 is the first release with the record, so "no record" cannot mean
"new install": every earlier install has none either. The launch asks,
before it creates anything in the profile, whether a watch history, a
metadata cache or a settings file is there; if none is, it records a
first-ever install, and the first read of the tips marks seen every tip
offered then, under that launch's flags. A flagged tip whose flag is off
then is not marked seen, so it is new to that install when the flag comes
on. A profile whose cache was deleted, with no history and no settings
ever saved, reads as new.

**Routes.** `GET /api/onboarding` answers the release counted at and the
tips offered, each with its tool, page, moment, places and whether it is
pending; `POST /api/onboarding/seen {id}` records a tip closed.
`GET /api/onboarding/debug` answers every declared tip with its window
and state, and `PUT /api/onboarding/debug/seen {id, seen}` sets seen
either way. No route sends words: each
step's title and body are the renderer's messages, named after the tip
and the step (`onboarding_<id>_<step>_title` and `_body`).

## Embedded playback

Playback happens inside the desktop window — not in a detached `mpv` process. Implementation:

- `<video>` element receives the master.m3u8 URL from the local proxy.
- `hls.js` handles HLS streams. mp4 streams (some providers) play natively via `<video src=...>`.
- Subtitles inside the HLS manifest are surfaced by hls.js as `textTracks`. Sidecar tracks — the `.vtt` files a provider lists beside the stream, outside the playlist — ride the session: the proxy lists them at `/s/<id>/subtitles` and serves each at `/s/<id>/sub/<n>.vtt` with the session's referer, and the play page appends one `<track>` per listing. Where the session lists sidecar tracks, the track an episode starts on is the language last picked on the show (Off included) — in the app's captions menu, or in the browser's own when the app's custom controls are turned off — kept per show in the renderer's local storage beside the version choices; else the UI locale's language, its own region first, then its script, then any region; else the track the provider flagged default; else none. A stream whose subtitles exist only inside its own playlist gets no start, whichever controls are on (see "The starting captions on a playlist-only stream" in `docs/deferred-work.md`). External players and Syncplay get the tracks in the same order — every play, handoff, next-episode warm and download request names the language last picked on the show and the locale the renderer runs in, and the backend orders by the pick first, then by that locale rather than by `config.toml`'s, which the renderer adopts only when it is one of the app's own — so a player that takes one file takes the track the built-in player starts on; where it starts on none — a show remembered Off, or nothing in the viewer's language and no default — mpv and IINA start with subtitles off (`--sid=no`) beside every track, and VLC or a custom template gets none. mpv starts on the first track unless its own configuration (a `slang`, or `subs-match-os-language`) picks another. The player's CC picker selects among both kinds, and loads only the track it shows. It names each track from its language tag in the app's language rather than by the provider's label, marks the tracks for the deaf and hard of hearing with a short tag, and lists the tracks in the language last picked on the show and in the app's language above a divider, the rest alphabetically below; it stays inside the player and below the app's top bar and grows to at most half the player's height — the screen's in fullscreen — scrolling instead and opening on the ticked entry (a player with less room than two entries still shows two), and two tracks of one language under different provider qualifiers (full and signs-only) read as the language plus that qualifier. Downloads write sidecar tracks beside the media as `<name>.<lang>.vtt` — never over a file already there, which is the user's; external players receive them as subtitle-file arguments, most wanted first and as many as the command line carries, and Syncplay forwards them to the player it wraps the same way.
- The level an HLS master plays is the app's choice, not hls.js's bandwidth estimate: every segment waits its turn in the proxy's paced line to the host, which the estimate reads as a slow network. The backend resolves the master for every play, so the player gets every level the master lists; no setting caps it (the one quality setting, `download_quality`, is for downloads). It starts on Auto at the highest level — or at the level picked earlier in the player session (below) — as soon as the levels arrive, and holds it while playback is healthy. A stall with nothing buffered steps it down one level, at most once every eight seconds and never within three seconds of a seek; a level whose playlist the engine gives up on is left for the stream, and a level the engine switches away from for any other error — its segments failing to load, or failing to append — is stepped down from at once rather than put back. A switch the engine makes over an audio or subtitle rendition — a segment, a track playlist, or the audio buffer — is no failure of the video: the player holds the level it moved to, and leaves the level it left for the stream. A retry the engine still has pending is no verdict. When the engine removes levels it cannot play — the variants of a mixed-codec master the browser refuses — the player carries the level it holds, the levels it has left, what it learned of each and the menu over to the levels that remain, re-seats a hold whose level was removed at the nearest loadable level below it that is left (or, with none, the nearest above) without counting anything as a failure, and puts the engine back on the level held; when every level left has failed, the hold and the pin are released rather than the engine put back on a level that failed. A content-steering pathway switch, which replaces every level object, seats the hold at the highest level, re-pins a pinned stream at the height the viewer picked (or the nearest level below it) among the new levels — as Auto when every new level is above it — and starts the player's knowledge of the levels afresh. After a step down, playback that has run healthy (segments of the level held buffering with fifteen seconds in hand; a segment of the level left, landing late, says nothing) climbs back one level per window — a window any stall outside a seek's grace restarts, under a pin as well as in Auto, as does every move the player did not choose to a level that has proven nothing yet (a failure, a switch the engine made, a removal that took the level held); the window starts at thirty seconds and doubles with every step down, up to four minutes. The player's menu lists Auto and the master's levels — the in-player menu with the app's custom controls, and the ⋯ menu below the player with them off, since Chromium's native controls have no quality menu; with the custom controls on, the ⋯ menu offers none — named by the height their segments are encoded at but ordered as the player moves through them — by the height each playlist declares, which every choice the player makes, and the pin, reads; the log names a level by both heights when they differ. A level picked in the menu switches at once — even when it is the level already held, if another still plays from the buffer — no longer moves for stalls, and is kept, by the height its playlist lists (or, for a level that lists none, its rank from the top of the levels), for the rest of the player session: the next episode keeps it, and it is let go when the player is left or turns to another show, so the next visit, and every other show, starts on Auto. It is never saved, and downloads, external players and Syncplay never read it. A pinned level is never exceeded while the menu shows it pinned, and it is where the play returns: a failure of its segments steps the play down and leaves the pin in place, and once playback has run healthy — the same window as Auto's climb, doubling with every fall — the play climbs back toward the pin, never above it, as long as the pinned level can still load. The pin itself moves only when its level cannot load, down to the nearest level that can — or, when the engine leaves the pinned level over a failing audio or subtitle rendition, down to the level the engine chose, since every level between shares what failed; a play already below its pin that the engine moves further down keeps its pin and climbs back. When no level at or below the pin can load, when the engine's own fallback takes over, or when the engine switches above it over a failing audio or subtitle rendition, the stream's pin is let go and the menu shows Auto. The next stream in the session starts at the pinned height or the nearest level below it, and as Auto when every level is above it. A stream of one level — a master that lists one, or the media playlist a source serves in its place — has nothing to choose: the player leaves its level to the engine, and the menu's row names that level — in the in-player menu listed alone and checked with no Auto, in the ⋯ menu with nothing to open — once a height or a bitrate names it (a media playlist served alone lists neither, so its row appears once the player learns the picture's height: from the first parsed segment for MPEG-TS, and from the video element when its metadata has loaded, which fMP4 segments need since hls.js reports no picture size for them); picking it changes nothing, the pin kept for the session included. mp4 streams play as they are.

An "Open in …" item in the player's More menu, named after the configured player flavour ("Open in mpv", "Open in VLC", "Open in IINA", or "Open in external player" for Custom), runs the External player command from Settings (`mpv` by default) with that flavour's arguments and the natively resolved master-playlist URL. The flavour and the command are separate settings: the item names the flavour, and the command is what runs. A blank command runs the flavour's standard program (`mpv`, `vlc`, `iina`), and so does a command that is only one of those names. Either way the program is looked for where it is installed, not only on the backend's PATH (`backend/src/commands/player_locate.rs`): PATH first, then on Windows the Program Files, per-user, scoop and winget folders and the App Paths registrations, per-user then machine-wide, skipping one whose program is gone (VLC's installer never puts VLC on PATH), on macOS the app bundles and Homebrew (a Finder-launched app has almost no PATH), and on Linux the flatpak and snap launchers. Nothing found runs the bare name, as before. For Watch together, a blank field passes no player (Syncplay opens its own), and a bare name passes the found program on Windows and macOS and the name as typed on Linux, where a flatpak or snap Syncplay could not reach a host path. IINA exists only on macOS, and Settings says so elsewhere. Settings asks `GET /api/external-player/standard` and shows where the program was found, or that it wasn't. Custom has no standard program, so a blank Custom command can't launch, and the failure says to set one in Settings. Changing the flavour in Settings changes the command with it only while the command is the previous flavour's bare name (in any case, with or without `.exe`), to the new flavour's. Leaving Custom clears a command that is only a standard program's name to blank, so the new flavour runs its own. A command the user wrote, such as a full path, flags or a wrapper, is never touched. The rule is the backend's (`backend/src/commands/external_player_kind_change.rs`): Settings asks `GET /api/external-player/after-kind-change`, then saves the new flavour and the command together. When the backend cannot answer, nothing changes and Settings says the save failed. A program the lookup cannot find is chosen with Browse. Opening an external player is always the user's choice, never an automatic fallback from the built-in player.

### Skip OP / ED via aniskip

The player surfaces "Skip Opening" / "Skip Outro" buttons during their respective intervals. The skip times come from [aniskip.com](https://aniskip.com)'s community-submitted database, keyed by MyAnimeList id rather than Kitsu. The backend bridges Kitsu → MAL using Kitsu's mappings endpoint, then asks aniskip for `(mal_id, episode)` skip intervals with the episode's length, which aniskip matches its submissions to, and caches the response for 7 days (skip times stabilize quickly once submitted). The player asks once the stream on screen has learned its length, so after an episode switch it asks with the new stream's length, and the previous episode's times are gone from the player as soon as the episode changes. The cached row is keyed by the Kitsu id the player asked with as well as the MAL id, the episode and the length in whole seconds, so an answer for one length is never served for another, two Kitsu entries that map to the same MAL entry keep separate rows, and removing a show from history finds its skip times by its Kitsu id without asking Kitsu for the MAL id again. When auto-skip is enabled in settings, the player jumps the playhead past the interval automatically; otherwise it just shows the button.

### Leaving the player

The play page makes its own `<video>` element and releases it when the page goes: the stream's engine is destroyed, the element unloads and leaves the page, and Picture-in-Picture — which shows that element — closes with it. Picture-in-Picture is available from the player while the player is open; it does not follow the viewer to other pages. An episode swap on the same show keeps the page and its element, and swaps the stream in place. The volume and mute carry from one visit's element to the next.

While it plays, the engine keeps about 30 seconds of already-played video behind the playhead and releases the rest (`$lib/play/hls-buffer-policy`), so the player's memory stays level however long an episode runs; a seek back further than that loads its stretch again. Ahead of the playhead it fills toward the engine's own bound: 30 seconds, or what 60 MB holds at the stream's bitrate when that is longer.

Each episode's position is kept in the renderer's local storage (`ani-gui.watch-positions`, the 200 most recent episodes): the episode is marked started, at zero, when it is chosen — the detail page's Play button or tiles, the Continue card, the player's episode switch, before the resolve that records the watch — and again when its stream attaches, either time unless a point is already kept for it. Its position is written as it plays, when it pauses and when its stream is replaced or the page leaves. Opening the episode again loads it fresh and seeks there once its metadata is in, unless a stale-stream recovery's position is pending for it, which is fresher. A position under 15 seconds in is kept as the started mark, so the episode reopens from its start; a position within the last 90 seconds, or an episode played to its end, is finished and forgotten. An ended episode stays forgotten when its stream is replaced or the page leaves, whatever its length and however short; only playing it again on the same stream keeps its position once more. A point in the first seconds is never judged finished, however short the stream, and a started mark opens without waiting for the stream's length. A point saved while the stream's length was not yet known cannot be judged then; the next visit checks it once the stream reports a known length — at its metadata, or, when the length is still unknown then, at the first change that brings one — and forgets one that falls in the last 90 seconds instead of seeking to it. Nothing drops the wait: the engine's own seeks are not the viewer, the player holds the stream while it waits (below), and once the hold's bound has revealed the stream the player's seek controls still need a known length, so nothing the viewer does through them reaches it — the resume lands when the length arrives. Until then no position is written for the stream, so leaving keeps the point; a stream whose length never becomes known writes no position, though one that plays to its end still forgets the point, as any ended episode does. Until a visit judges it, such a point still makes its episode the Continue target.

An episode opened at a point — a kept point past zero, or a recovery's — does not show its stream's first frame in the player. From the moment the stream attaches, the player keeps its loading treatment: the picture is hidden behind the start veil, the controls are hidden and inert, Chromium's own controls bar is off, the play and seek shortcuts and a click on the picture do nothing, and auto-skip waits. The element's autoplay is off for the while, and anything else that starts playback, such as a media key, is paused again: the resume wins. The picture is revealed, fading in at the point, once the resume seek has landed within two seconds of it and frames are playing there; when autoplay is refused, it is revealed paused once the frame at the point is in. Hiding the picture is not enough on its own, because picture-in-picture and a `<video>` that is itself fullscreen show the element, not the page: so an hls stream played through hls.js also starts at the point. The engine begins loading at the fragment that holds the point rather than at the first fragment, so nothing before that fragment is fetched, and none of it can be shown, in the page or anywhere else the element is shown; the engine moves the playhead to the point as soon as that fragment is buffered. An mp4 stream has no such start: the element plays it from its start until the seek lands, so picture-in-picture can still show its first frame (see `docs/deferred-work.md`). A point that turns out to be in the last 90 seconds is forgotten and the stream plays from its start: an hls stream, which the engine started at the point, is sought back to its start and revealed once that seek lands, and an mp4 stream, already at its start, is revealed there at once. The hold is bounded: the wait for the seek to be issued, and once it is, the wait for it to land and play, each last at most fifteen seconds — each waits on one fragment, the first the stream loads or the one at the point, and fifteen seconds is how long the engine lets a fragment take before it counts the load as timed out. When a wait runs out the picture is revealed anyway and plays from where it is; the resume is not given up, so a seek still to come is still made when its metadata or length arrives, and the point is still not written over until then. A started mark, or no point at all, opens the stream as it always did.

An episode's watched mark is written when it starts, so the last watched episode is the one the viewer was in when they left. When that episode has a kept position — the started mark included — the Continue Watching card and the detail page's Play button go back to it — the card shows its number, and the button reads "Continue · Episode N" (or "Continue" for a movie) rather than Replay; once it is finished, or with nothing kept for it (pushed out by the 200-episode cap, or storage refused), they go on to the next episode as before. An episode whose stream fails to load every time stays the Continue target: it is the one the viewer chose, and it is marked started as its stream attaches. Only the last watched episode is asked about: a position kept for an older one does not pull Continue back. Removing a show's Continue card forgets its kept positions — under the Kitsu id its history row records, whether or not Kitsu still serves that entry, and under the entry the card was shown as, or, for a card whose match never resolved, the show id → Kitsu id mapping a play stamps, read before the removal deletes it (it expires thirty days after the show's last play and can be refused or dropped as wrong); a show known by none of these keeps them. A show another remaining history row is still a card of keeps them too. That row's show is the card it is — the entry the home page resolved and shows for it, since a card's plays key positions by that entry — or, for a row not yet resolved, the Kitsu id it records unless Kitsu's detail read answers that entry gone (a 404 or 410), then its stamped mapping. This follows the card, not the detail page's resume lookup (`history_by_kitsu`), which reads an entry as gone from the cached mark and never names a row that recorded no id by its title match. The positions are dealt with after the card is gone: a slow Kitsu read does not hold the removal, and what it forgets is only what was kept when the rows were gone — a position the user writes or rewrites meanwhile, playing the removed show again, stays, as does a recovery point captured meanwhile; an episode only picked meanwhile loses its old point all the same and stays started, at zero. Every show keeps them when a remaining row's show cannot be told — its match unresolved and Kitsu's read of the id it records answering neither way, or no standing recorded id and no readable stamped mapping. Those rules find positions by show, and a card's match can be a guess a later load corrects, leaving the positions its plays kept under the guessed show on no show the card names. So a session a Continue card opened carries the card's history row — its provider show id — in its URL (`row`, beside `guess`, kept on every episode switch), and each position it writes, the started marks included, records that row as a third element; the latest write decides it, so a later play of the episode from the detail page, which carries no row, takes the position back to the show rules. Once the deletes succeed, removing the card forgets every position recorded for a removed row unless its show is one a remaining row is a card of, and none while a remaining row's show cannot be told — the show rules' exceptions, told the same way and at the same time. That exception matters here: a card's play resolves by its match's title, so a guessed card's play can land on another provider show and record its watch under that row, which may then be the card of the show played. No remaining row has a removed row's id, since a delete takes every row of it; a group delete that fails partway forgets nothing, and its removed rows' recorded positions are then reachable only through the show rules. Positions kept before rows were recorded carry none and follow the show rules alone. Clearing the history forgets them all. Forgetting a show's positions, a removed row's, or all of them, also drops a pending stale-stream recovery point for that show, which otherwise waits in memory for the episode's next attach.

### Episode prefetching

Two prefetch surfaces warm play data ahead of demand so episode boundaries don't stutter:

- **Adjacent-episode warm.** When the play page mounts, it warms `episode + 1` (and on the detail page, `episode 1`) through the same play-resolution path the click would take. Hits land in the long-term resolution cache. If the current playback ends and auto-play-next is on, the next episode usually plays from cache instead of waiting on a fresh provider walk.
- **Visible-page warm.** The episode strip's currently-rendered Kitsu page is warmed in parallel so episode tiles get titles and thumbnails before the user scrolls.

Both flow through `play-cache.getOrFire` — keyed by show id + episode + mode + version — which dedupes concurrent calls and keeps each answer until the show's entries are cleared or the resolve fails. The 4-hour lifetime is the backend session table's. At most two run at once; a click cuts the queue. Cancellation goes through `clearForShow(showId)`, which drops every entry for that show and aborts those still resolving or queued, a click's included.

The detail page's resume warm uses the same cache. When no listing stood behind the page's availability answer and the history row reads as a fractional episode, the page resolves that episode as a prefetch so the listing puts the row right. It cuts the queue like a click (`getOrFireNow`), since a click on Play waits for it.

When the play or detail page goes, it clears the play cache of every show it showed — warms and clicks alike, running and queued — each show recorded as the page showed it: by the time the page is destroyed, the route already names where the viewer went. When the detail page moves to another show without unmounting, it drops the first show's warms, running and queued (`clearBackgroundForShow`). Picking another version of the show drops the other versions' warms the same way (`clearBackgroundForOtherVersions`), since each version is its own listing and the page re-warms under the chosen one's keys. A click's own play for that show runs on and records its watch, until the page goes.

## Reduced motion

The renderer's animations key off `prefers-reduced-motion`, through CSS media queries and `matchMedia` checks. What sets that media query depends on the platform:

- **Windows.** Chromium reads the system's animation setting itself (Settings › Accessibility › Visual effects › Animation effects).
- **Linux.** Chromium reads only GTK's `gtk-enable-animations`, which follows GNOME's global `org.gnome.desktop.interface enable-animations`. GNOME's Reduced Motion switch (Settings › Accessibility › Seeing) writes a different key, `org.gnome.desktop.a11y.interface reduced-motion`, which Chromium never sees. So at launch the main process reads it itself: the desktop portal's `org.freedesktop.appearance reduced-motion` through `busctl`, asked again through `gdbus` when `busctl` gives no answer, and that gsettings key when the portal cannot answer. When the answer is `reduce` it appends Chromium's `--force-prefers-reduced-motion` switch before the first window opens. Any other outcome — no preference, no portal, no GNOME, a failed or slow read — appends nothing, and Chromium's own reading of `enable-animations` stays in effect. The read is bounded at half a second and runs beside the backend's start; a change to the setting takes effect on the next launch (`electron/lib/reduced-motion.cjs`).

## Saved sign-ins and the OS keyring

A tracker sign-in is saved as a file per provider in the desktop shell's profile directory, encrypted through Electron's `safeStorage` with the OS keyring: DPAPI on Windows, the Secret Service (GNOME Keyring, KeePassXC) or KWallet on Linux. On Linux the keyring can take its time: a locked keyring answers once the user unlocks it, a keyring never set up once its "new keyring" prompt is answered, and a secret service that accepts a call and never replies only when the bus gives up, after about 25 seconds per call. `safeStorage`'s first call in a process waits for that answer on the thread that made it, and in the main process that is the thread every window runs on: the window stays blank and the app answers nothing, SIGTERM included.

So on Linux the main process never calls `safeStorage`. It starts the app's own binary again as a windowless keyring helper the first time a saved sign-in is read or written, and asks it over a pipe (`electron/lib/keyring.cjs`, `electron/lib/keyring-helper.cjs`); the helper waits on the keyring, the app does not, and the helper is killed when the app's main process exits. A main process that is itself killed or crashes cannot do that; its helper then ends once it finishes the call it is in and finds its input closed, which for a call waiting on an unlock prompt is when the prompt is answered. On Windows DPAPI answers in-process without a prompt, and the main process calls `safeStorage` directly. Either way the renderer's reads are asynchronous: the first page renders signed out, each provider takes its account when its read answers (a provider the user changed meanwhile keeps what the change left, and is read again only if the change left it signed out, as a cancelled connect does), a read still out after two seconds puts up a notice that the app is waiting on the keyring, and a read that fails leaves the saved file where it was. Nothing times a read out — a keyring waiting on its unlock prompt is waiting on the user.

## Chromium's sandbox on Linux

Chromium on Linux sandboxes its renderers in one of two ways, and picks the first that works. The namespace sandbox needs nothing installed and works wherever unprivileged user namespaces are allowed. The setuid sandbox needs a `chrome-sandbox` helper owned by root with the SUID bit. When neither works, Chromium aborts the start rather than run unsandboxed, unless it is started with `--no-sandbox`. That choice is made before `main.js` runs, so the flag has to be on the command line the binary is started with.

- **The `.deb`.** Its post-install script (`electron/build-resources/deb-after-install.sh`) prepares both sandboxes. It writes an AppArmor profile, `/etc/apparmor.d/ani-gui`, that grants user namespaces to the installed `/opt/ani-gui/ani-gui.bin` and confines nothing else, with the same rules as Ubuntu 24.04's own profiles for Chrome, VS Code and Obsidian (Ubuntu 25.10 and later add `@{exec_path} mr,`, a variable AppArmor 4.0 and 4.1 do not define). It loads the profile where AppArmor is active, so on Ubuntu 23.10 and later the namespace sandbox starts too. The profile is written only where AppArmor knows the `userns` rule (ABI 4.0), and a failed load never fails the install. The script also makes the installed `chrome-sandbox` SUID root, so a host with no user namespaces at all still starts sandboxed, in the setuid sandbox. Removing the package unloads and deletes the profile (`deb-after-remove.sh`). The package also carries the same profile, never loaded, at `/opt/ani-gui/resources/apparmor-profile` (`electron/build-resources/apparmor-profile`): electron-builder puts one there in every `.deb`, its own for the launcher script unless it is given ours.
- **The AppImage.** It runs from a read-only FUSE mount, which cannot carry the SUID bit, so only the namespace sandbox can work. Whether it does depends on the host. On Ubuntu 23.10 and later, AppArmor grants user namespaces per program, and no rule covers an AppImage's mount path. So the image's `AppRun` asks the app's own binary: it starts the binary once with `--ani-gui-sandbox-probe`, and `main.js` answers that first thing and exits. An answer means the sandbox came up, and the app is started normally. No answer within ten seconds (an abort, any other exit, a hang) and the app is started with `--no-sandbox`, with one line on stderr saying so. A `--no-sandbox` the user passes skips the probe. So does a Restart from the splash's stuck state after a launch that fell back: the restart keeps the `--no-sandbox` it ran with (`electron/lib/relaunch.cjs`), and the new launch starts without the sandbox, unprobed, as the one it replaces did. The repack writes this into `AppRun` and drops the `--no-sandbox` electron-builder puts in the image's desktop entry (`electron/lib/appimage-tree.cjs`, `electron/lib/sandbox-probe.cjs`). Interrupting the launch while the probe runs (Ctrl-C, SIGTERM, or closing the terminal) starts nothing. The probe costs one extra start of the binary, as far as `main.js`, on every launch it runs for.
- **The keyring helper** (see above) is started with `--no-sandbox` in both Linux packages. It opens no window and loads no web content.

Windows keeps Chromium's own sandbox, which needs none of this.

## Localization

Four MVP locales: English (`en`), Brazilian Portuguese (`pt-BR`), Latin American Spanish (`es-419`), Russian (`ru`). The set was chosen for free-content market fit, not language-coverage prestige. Phase-2 candidates listed in `docs/i18n.md`.

The backend never returns localized text. Every error the app raises — as an HTTP error body or an SSE error event — carries a `kind` (the variant's name), a stable key naming exactly what failed (`error.scraper.timeout`, `error.search.no_results`, etc.) and the variant's own fields. The keys are published in `backend/error-keys.json`. The frontend resolves the key to a Paraglide message of its own in each locale, interpolating the variant's fields where a message takes one, keeps the more specific reading of a field that says more (an upstream's 404 or 5xx, a rate limit's wait), and falls back to a coarser sentence chosen by the `kind` when the key is absent or unknown; it never shows an error's free-text `detail`. `docs/i18n.md` has the catalogue layout and the steps for a new key. Answers the router or the HTTP layer gives before a handler runs, and the image route's refusal of a non-`https://` URL, carry no envelope; the API client turns a body that is not one into `{ kind: 'http', status }`. Anime titles themselves are not translated by the app — they come from Kitsu/AniList per a user-chosen title-language preference.

The Electron main process shows text of its own, where no page can: the error a failed startup ends with, the prompt on a quit with downloads running (not on a quit the session's end or a stop signal asks for, where nobody is there to answer it), the launch splash's own words (the line it shows when a step of the boot stalls, its stuck state's line and actions, and its name for assistive technology), and the page the browser shows after a sign-in. That text lives in `electron/lib/main-messages.cjs`, in the same four locales, and the locale is resolved in the renderer's order: the one saved in the config, then the system's languages as Chromium reports them, then English.

## The retired CLI

The project spent its first releases as a desktop shell over the vendored `ani-cli` script, then replaced the subprocess with native resolution and, release by release, retired everything that carried the script: the spawn, the packaged copy, the boot-time updater, and finally the vendored file itself. The repository holds only the GUI now. Users who want a terminal flow install upstream's script; the two share an origin and nothing at runtime. What remains in the tree is the boot sweep (`backend/src/legacy_script.rs`) that deletes the copy earlier versions maintained in the user's cache, and reports having done so.

## Design direction (UI as a first-class surface)

The pivot from CLI to GUI is positioned as a premium-experience product: the UI is the differentiator. The design direction explicitly rejects generic AI aesthetics and embraces:

- Dynamic per-anime theming, with accent colors extracted from `coverImage.color`.
- Editorial typography pairing — a display face for hero titles, a clean body face for paragraphs, oversized tabular numerals for episode numbers.
- Motion as structure: elastic-eased carousels, parallax-on-hover cards, shared-element page transitions (poster card morphs into the detail-page poster), theater-dim into playback.
- Subtle anime motifs: manga-page-inspired dividers, oversized episode numerals, occasional Japanese typography accents — restrained, not cosplay.
- A player chrome closer to Apple TV+ than to VLC: minimal, autohides cleanly.

`tests/arch/i18n.sh` enforces that no `.svelte` file ships with hardcoded English. The wider design guard rails are documented in `AGENTS.md` §7.
