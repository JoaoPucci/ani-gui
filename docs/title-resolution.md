# Title resolution and the cross-API bridge

`ani-gui` reads from five catalogues that don't share an id space:

- **Kitsu** (REST/JSON:API) — discovery surface (search, trending fallback, top rated, recently released, detail pages, episode metadata).
- **AniList** (GraphQL) — recency-weighted "Trending Now" row, banner backfill when Kitsu's banner is null, and episode stills Kitsu lacks.
- **anidb.app** — the streaming catalogue the backend resolves playback against first.
- **hianime** — the streaming catalogue the backend resolves against when the walk moves on from anidb.app (unreachable, refusing or rate-limiting, a page the app cannot read, a background request its gate turned away, or an answer that settles nothing — the show found with nothing said about the audio asked for, or a denial of a show a live record remembers it carrying), and first for a show it was found on while that memory lasts — the availability record's lifetime: at most a day from the last resolve that found the show there — a play, a download, a hand-off, or the background warm a page runs as it follows what is in view: the detail page for the episode its Play button targets, the play page for the next episode, or with resolution caching on for every aired episode in view, again as the grid or strip is paged — or, for a show a probe alone found and nothing resolved since, at most a day for an ongoing one and thirty days for a finished one; a play, hand-off or page warm served from the resolution cache leaves a live record as it is and writes a record with the ongoing window again once it has lapsed, and a download never reads that cache (see [Providers and failover](./architecture.md#providers-and-failover)).
- **aniskip** (REST) — community OP / ED skip-time intervals, keyed by MyAnimeList id.

Every interaction other than discovery has to find the same show in two or more of these. None of them carry the others' ids, and any given anime may appear in some but not others (aniskip in particular is sparse). This document describes how the backend bridges them and what the cache stores in the process.

## The four bridges

```
                       ┌──────────────────────────────────────────┐
                       │                                          │
                       │             Discovery surface            │
                       │                                          │
                       │   ┌──────────────┐    ┌──────────────┐   │
                       │   │   AniList    │    │    Kitsu     │   │
                       │   │  (trending)  │    │ (everything  │   │
                       │   │              │    │   else)      │   │
                       │   └──────┬───────┘    └──────┬───────┘   │
                       │          │                   │           │
                       │     mal id only         kitsu id (canonical
                       │          │              for the renderer)
                       └──────────┼───────────────────┼───────────┘
                                  │                   │
                  ┌───────────────┴───────────────────┘
                  │       Kitsu mappings endpoint
                  │       (kitsu id ↔ mal / anilist id)
                  ▼
       ┌──────────────────┐                ┌──────────────────────┐
       │     aniskip      │                │    stream provider   │
       │   (mal_id, ep)   │                │  (canonical title +  │
       │  → skip times    │                │   alt titles → hits  │
       │                  │                │   → probe episode    │
       │                  │                │   lists → pick)      │
       └──────────────────┘                └──────────────────────┘
```

Four distinct lookups, each with its own gotchas:

1. **Kitsu → provider title match** — the native walk searches the provider's catalogue: anidb.app's browse page, or hianime's search page when the walk moved on from anidb.app — unreachable, refusing or rate-limiting the request, answering a page the app cannot read, its own gate turning a background request away, or answering without settling the question: the show found with every sampled row silent about the requested audio, or a denial of a show a live positive row remembers it carrying, which the row outranks until the rest of the order has been asked — or when the show's still-live availability record names hianime. Kitsu canonical titles (often the licensed English form) and the provider's index don't always agree, so the bridge tries the canonical first and falls back to romanized Japanese, native script, and known synonyms before giving up.
2. **Candidate disambiguation** — multiple browse hits can match the same query string ("Gintama" returns the series and its movies in the provider's own ranking). The browse page carries titles only, so the picker probes each considered hit's episode list — bounded to the first few hits whose titles could be the entry (with a count, refused hits among the first few are probed besides, as evidence), since real queries put the right show near the top and every probe is an upstream request — and Kitsu's authoritative `episode_count` picks the candidate whose count is closest.
3. **Kitsu ↔ MAL / AniList** — neither Kitsu's id nor the provider's slug matches MAL's or AniList's. Kitsu publishes a mappings endpoint that exposes the third-party ids it knows about; the backend fetches `kitsu/anime/:id?include=mappings` and walks the included documents for the MyAnimeList and AniList rows.
4. **MAL / AniList → aniskip / AniList** — once the ids are in hand, aniskip (MAL id only) and AniList's `Media(idMal:)` query are direct lookups. The banner and episode-thumbnail backfills fall back to AniList's `Media(id:)` when Kitsu carries the AniList mapping but no MAL one, which is common for fresh seasonal shows, and retry by that id once when AniList has no media for the MAL id.

## Title resolution: Kitsu → the provider

When the user clicks an episode, the backend builds a list of search terms from the Kitsu metadata in priority order and feeds them to the provider's search in turn:

1. Canonical title.
2. `titles.en_jp` (romanized Japanese).
3. `titles.ja_jp` (native script).
4. `titles.en` / `titles.en_us` (English alternates).

Empty / whitespace-only titles are skipped and exact-string duplicates are deduped, so the backend never makes a redundant provider query. A pool whose pick is rejected keeps the walk going — the next alias may carry the real show — while an upstream refusal (the provider's protection page) stops it: a block on one query blocks them all, and each further request deepens the hole.

## Disambiguation by episode count

The picker probes at most the first few browse hits the entry's titles admit via the episodes endpoint — with a count, plus the refused ones among the first few, as evidence (see the decision tables below) — and scores each by the distance between its episode count and Kitsu's authoritative `episode_count`. The best distance wins, rejected outright when it exceeds the tolerance (`max(3, expected / 10)` — long-running shows get proportional slack, short shows a hard floor); ties prefer an exact case-insensitive title match on the search term. The same picker is used by:

- **The play path** — so clicking "play" lands on the right show even when the provider ranks a movie or side story first.
- **The availability probe** — so the home / detail page's "is this in the catalogue?" gate matches what the play path would do.
- **The download path** — so a download started from the player picks the same show the player was streaming.

One Kitsu entry can be several shows on the provider. Steel Ball Run is twelve episodes on Kitsu, while hianime lists its March premiere as a one-episode show of its own and the weekly run as "… 2nd Stage", numbered from 1. The picker recognises the parts among the candidates it already probed — a bare title and the same title followed by a short part marker ("2nd Stage", "Part 3", "Season 2", "II"), every part's own premiere year equal to Kitsu's — and stitches them when together they explain the expected count better than any single candidate, either within the tolerance or short of it as an airing entry is. Where a single candidate already sits within the tolerance, the count cannot tell a finished split (1 + 11 against 12, the later part one off) from a cour and its same-year sequel (12 + 1 against 13, the bare title one off), so the near miss decides: the parts are stitched over it when it is one of the later parts, never when it is the bare title — a bare title that fits alone is the entry. The entry may itself be a later part: Kitsu keeps "X Season 2" as its own entry, and asked for it, the provider's same-year "X" is the season before. Any candidate that a title the entry goes by — its canonical title or any alias — names a later part of is dropped from the pool before probing, so it neither heads a chain (a finished 12-episode "X" beside a "X Season 2" five episodes into an announced 24 would otherwise stitch, 12 + 5 short of 24 like an airing split, and play Season 2's first twelve episodes from the first season), nor wins alone when its count happens to fit, nor stands in when the provider has not listed the later part yet. Steel Ball Run's Kitsu titles name no part, so its pool keeps both parts. The reverse has no title to go on: asked for a bare "X" that has finished but that the provider lists short, beside a same-year "X Season 2" that Kitsu keeps as its own entry, the two can still stitch when together they fit the count better than "X" alone, since nothing in the titles or counts tells that from a real split. Beyond that check the parts' titles are not compared with the one searched, so a provider that spells the parts differently from the title searched (an English title against Kitsu's romaji, say) stitches the same way, and an airing split stays stitched the week its later part comes within the tolerance. A bare title whose own listing is numbered as a continuation is never stitched: played alone, its key already carries that offset and its history rows speak those numbers. Stitching makes one listing in the entry's numbering: each part normalised to its own numbers and numbered on from where the part before it ends, every row keeping the episode id it streams from, and every row taking its position across the parts as its slot, with its episode identity in the tag where the two differ — as a single listing's rows do. The first part's id is the show's identity, the key history and every cache file the plays under, so Kitsu's episode 2 of Steel Ball Run streams the 2nd Stage's episode 1 and records as episode 2 under the first part's key. A sibling that lists nothing yet, one from another year, a gap in the part numbers or a candidate whose probe failed leaves the pick as it was; so does a single candidate the rules above leave standing, which keeps a provider entry spanning several Kitsu entries on its continuation offset (below).

Before anything is probed, a card's format badge disproves candidates whose format cannot be the entry's: a movie is not a series, and a special, an OVA and a movie are not each other — for single-video entries of one title and year the badge is the only thing that separates them. TV and ONA are the one pair that does not disprove: a series a streaming service premiered is a TV series to one catalogue and a web release to the other (Stone Ocean is TV on Kitsu and ONA on hianime), and the count and year separate the two where they differ.

The entry's titles rule which candidates can be picked, on either provider. Both these rules and the split detection above read one marker grammar: a marker word — season, part, cour or stage — with the ordinal after it ("Season 2", "Season Two", "Part 1+2") or a spelled ordinal before it ("2nd Season", "Second Cour"), an ordinal spelled as one standing alone ("Overlord III", never a bare number), and in Japanese 第N期, 第N部 or 第Nクール, with full-width digits read as ASCII and a number written in kanji read as the number it is, compound ones included (第十期 is 10, 第十二部 12, 第二十一話 21, 百 100). A kanji number is read where a Japanese number is expected — after 第, or before a counter — and nowhere else, so the 一 of a word like 一騎当千 is no number. Every reader of a title's tail — the markers it ends on, the one ordinal a later part's tail names, the stem — is a view of one parse of it. A candidate whose title ends on a season or part marker must name an ordinal one of the entry's titles names somewhere: in a marker, as any small number or numeral in it ("… Slime Datta Ken 2", "Mushoku Tensei II: Isekai Ittara Honki Dasu"), as a Japanese 第N, or as a number written before a Japanese counter (the ８ of "怪獣８号" or the 八 of "怪獣八号", before 号, 期 or 話). The kind of marker does not have to match, since the catalogues disagree on it ("86 Part 2" is hianime's "Eighty Six: 2nd Season"); a first part or a span through it ("Final Season, Part 1", "(Part 1+2)") never disqualifies, any other span needs every part in it named ("Part 2+3"), while a zeroth one is an ordinal like any other ("Season 0" only for an entry that names 0); and only markers a title ends on count, so the story parts JoJo numbers mid-title ("Part 4: Diamond is Unbreakable") are not read as cours. A bare number of one or two digits that a title ends on, before any markers, is held to the same rule — "Show 2", the 2 of "Show 2 Part 1", the ２ glued to "ショー２" — since that is how a sequel is numbered as often as by a marker: "Overlord: Ple Ple Pleiades 2" is not Overlord, while "Kaiju No. 8" stays admitted for an entry whose titles name 8, a 1 never disqualifies, and "Mob Psycho 100" names no sequel at all. A title that matches one of the entry's titles only by carrying its first number with more digits after it — the words before the number alike, the number continued — is another show and is refused: "Show20" is not "Show 2", "Mob Psycho 1000 Part 2" is not "Mob Psycho 100 II", and "861" is not "86 Part 2". A title's first number is the first run of digits in the first word that holds any, so a separate word after it never lengthens it ("Kaiju No. 8 2nd Season" carries 8, "Show 2 (2020)" carries 2). A title carrying the entry's number itself, or the number another of the entry's titles carries after the same words, is not touched by this; a number another title carries after other words does not count ("Show20" is refused for an entry known as "Show 2" and "Other Name 20"). With a count, a candidate the entry's titles refuse is still probed and stays in the pool as evidence — the split stitching above may stitch it as a later part, never as the lead — but it is never picked, rescued as an airing part, or counted as the pool's best distance, and its probe dying blocks no winner; without a count, a hit the titles refuse is passed over. When nothing the titles admit fits, the pool is rejected and the walk searches the next alias. This is what finds a first season the provider's search leaves out of the canonical title's results: hianime answers "[Oshi no Ko]" with its second and third seasons only, and its "My Star" comes back for "【推しの子】". Refusing by title is an inference from how titles are written, so a pool rejected because the titles refused a candidate the count accepted — or, without a count, refused any hit and nothing else was picked — is never the clean miss the availability cache persists: the walk moves on as it does from a pool of dead listings. Among candidates tied on distance, below an exact title match and above a positively matched year, a candidate whose part marker agrees with the part the entry's titles end on — no marker reading as the first part — wins, so "Season 2" and "2nd Season Part 2", twelve episodes each from the same year, are told apart for an entry that names no second part. Every selector keeps that order: an airing part rescued short of the count, the countless pick, the lead of a stitched chain among chains that fit equally well, and the rank a candidate whose probe died is weighed by — so a dying candidate whose part agrees makes the pick transient rather than handing it to one whose part does not.

The inverse of a split is one provider listing spanning two Kitsu entries: hianime lists a 22-episode "Attack on Titan Season 3" holding Kitsu's Season 3 (12) and Season 3 Part 2 (10), beside a 10-episode "Season 3 Part 2" of its own. A probed candidate is read as spanning this entry and the next when it carries the entry's own year, its title is admitted, it lists more than the entry has, and another candidate lists exactly the remainder while naming, right after its stem (a stem being the title with the markers it ends on removed), a later part than the entry's — "Part 2" in "Season 3 Part 2", "2nd Season", or the "Second" of Gintama's "Silver Soul Arc - Second Half War" beside "Silver Soul Arc". The spanning listing is then cut to its rows up to the next entry's first episode — the entry's own episodes and any recap tagged among or right after them — and scored as the exact fit it is; the candidate that completes it is the next entry and is never picked for this one, whether the cut is made or the entry's own listing stops it. The cut keeps the spanning listing's own numbers, which on hianime number the entry from 1, so it plays under that listing's key at offset 0. The later entry keeps its own listing; a spanning listing is never cut for it at an offset, since its key would then carry two numberings — offset 0 when played as the first entry and the first entry's count when played as the second — and the offset store holds one per key. The cut is made only when the entry is the spanning listing's head — the spanning listing carries the name one of the entry's titles carries and reads as that title does — and no admitted listing of the entry's length is the entry's own beside it: one of the entry's titles, or a title that reads as the entry and carries the spanning listing's stem alone or opens what follows it with a division. That one stops the cut, even when the broad listing is exactly twice the entry's length. Any other exact-count hit, a spinoff of the franchise included, numbered or not, is no such evidence — admission says nothing about which show a title names — so the cut stands and wins, that hit kept just behind it. The decision tables below state the rule in full.

Without a count, a pool from which the title rule dropped a hit it refuses is never a clean miss: when it is rejected — every hit refused, the year filter emptying what is left, or every remaining listing answered with an error status — the pool answers as the refusal by title the availability cache does not persist. A transport failure still answers as the transient network failure it is.

**One reading of a title.** The spanning cut compares titles through one reader, applied the same way to the entry's titles, to W and to every candidate. A title *reads* as the ordinals of the divisions it names, in order, from first word to last: a marker pair ("Season 2", "2nd Season", "Part 2"), an ordinal standing alone — spelled ("Second", "II") or a bare number of one or two digits ("Show 2"; "Mob Psycho 100" names none) — a Japanese division (第2期, 第2部, 第2クール, a word of its own or glued to the word before, each of several glued one after another — "ショー第2期第2部" reads `[2, 2]`), and a number of one or two digits glued to the end of a Japanese word ("ショー２"; the ８ inside "怪獣８号" is not). A division whose first ordinal is 1 is left out, being the whole ("Part 1", "Season 1", "First Half", "(Part 1+2)"). A numeral right before a marker that carries its own ordinal is a division of its own ("Show II Part 2" reads 2, 2). So "Show 2", "Show 2nd Season" and "ショー 第2期" all read `[2]`; "Show", "Show Part 1" and "Show First Half" read `[]`; "Lucky 2 2nd Season" reads `[2, 2]` and "Lucky 2" `[2]`. A title's *name* is its words up to the first division it names, with what a Japanese word holds before a division glued to it: "Show", "Show 2", "Show 2nd Season Part 2" and "Show II Part 2: Arc" are all named "Show", "Other Show Season 2" is named "Other Show", "ショー２" is named "ショー"; a title that opens on a division ("86") is named by its stem. A title *reads as the entry* when it reads as one of the entry's titles does and starts with that title's name — at a word's end, or with a digit or 第 glued to it, no digit when the name itself ends in one ("Mob Psycho 1000" does not start with "Mob Psycho 100") — so "Other Show 2nd Season" does not read as "Show 2", and "Show 2nd Season" does not read as "Showtime 2". The entry *heads* a W when one of its titles carries W's name and reads as W does: reading alike under another name ("Other Show Season 2" for "Show Season 2") is another show. A title's *stem* is the title with every marker and Japanese division it ends on removed, Japanese ones stacked one after another included ("ショー 第2期 第2部" → "ショー"); a bare or glued number it ends on stays in the stem ("Lucky 2", "ショー２"). A title that does not start with W's whole stem is read past it without that number, the number then one of the divisions W ends on: "Show Season 3" names a season 3 past "Show 2" as it does past "Show 2nd Season", and "Show 2nd Season" opens what follows "Show 2"'s stem with the season 2 W itself names. A title whose number where W's stands only continues W's — the digits of W's number as a number, any zero padding W writes it with aside — ("Show 20 Part 2" or "ショー２０第2部" beside "Show 2" or "ショー２"), or is lower than W's, is not read past it; the same number written apart ("ショー ２" beside "ショー２") is, and so is a higher one that does not continue it ("Lucky 3" beside "Lucky 2", the next season, as "Show Season 3" beside "Show 2" is; "Show 21" continues "Show 2" and is not). What *follows W's stem* in a title is what comes after it at a word's end, or after a number or 第 glued to it ("ショー２", "ショー第2期"); "Showtime 2" does not start with "Show", and a stem that ends in a digit takes no further digit glued to it, so "Show 20 Part 2" does not start with "Show 2", nor "860" with "86".

**The spanning cut** — inputs, read through that one reader:

- W, an admitted candidate from Kitsu's year listing more than E episodes, with a stem; when several qualify, the first in the provider's order that the entry heads and beside which an L or an O exists, and only when there is none, the first beside which an L, an O or — the entry not being its head — an F exists;
- L, a sibling listing exactly W's count minus E that opens what follows W's stem with divisions — read up to the first word that names none, any W itself ends on left out — one of them above the entry's part, and that is not an O; beside a W the entry is not the head of, also not the entry's own by title (as an O is, whatever its count). Beside a W the entry heads, a sibling that reads as the entry but does not fit is still an L: "Show Part 2" (10) beside "Show Season 2" (22) for "Show 2";
- O, an admitted candidate listing exactly E that is the entry's own beside W: one of the entry's titles, or a title that reads as the entry and either carries W's stem alone or opens what follows it with a division. A spinoff — a title going on past W's stem with a word that names no division ("Show Side Story", "Show Side Story 3") — is never an O, numbered or not, unless it is one of the entry's titles;
- F, beside a W the entry is not the head of, a candidate that opens what follows W's stem on first divisions alone, any W itself ends on left out ("Show Part 1", "Show Season 1", "Show First Half"), and is not the entry's own by title: W's first half.

| The entry heads W (same name, read alike) | L exists | O exists | Outcome |
|---|---|---|---|
| no | — | — | nothing is cut; every L and every F is never picked; an O scores every other exact fit one behind it |
| yes | no | — | nothing is cut; an O scores every other exact fit one behind it |
| yes | yes | yes | nothing is cut; every L is never picked; O scores every other exact fit one behind it |
| yes | yes | no | W is cut to the entry's episodes and scored exact; every L is never picked; every other exact-count candidate is scored one behind the cut |

Names are compared as written: the entry's titles have to carry the provider's name for the show for its broad listing to be read at all, which Kitsu's titles do for every recorded pool ("Gintama.: Silver Soul Arc" among Shirogane no Tamashii-hen's). The title rule that admits a candidate weighs only the divisions a title ends on and never its name, because the provider answers an alias with titles that share no words with the canonical one ("My Star" for "[Oshi no Ko]").

Not decided by this rule: what follows the divisions a title opens with is read like the rest of it, so "Show 2nd Season Recap" reads `[2]` and is "Show 2"'s own beside "Show". One shape is recorded in `docs/deferred-work.md` instead: a broad listing completed by a sibling written in another script is never cut. A title that extends the entry's name after it still starts with that name, while one that extends it before does not: for "Show 2", "Show Other Season 2" (12) beside "Show Other" (24) reads as the entry and plays, while "Other Show Season 2" (12) beside "Other Show" (24) is an L and nothing plays. Which of the two a provider's subtitle is cannot be told from the words, and the table leaves the first as it stands.

So a numbered spinoff ("Show Side Story 2") or a recap of W's own season ("Show Season 3 Recap") never completes a span, and a spinoff never stops one.

**Choosing among candidates** — part agreement sits in every selector's order, below an exact title where the selector reads one, and the provider's order breaks only a full tie:

| Selector | Order |
|---|---|
| Winner (candidates at the best distance) | exact title, part agreement, matched year |
| A dead candidate's rank | the same |
| Airing rescue (confirmed, short of E) | distance, exact title, part agreement |
| Countless pick | exact title, then part agreement, then matched year |
| Stitched chain | fit to E, then a lead whose part agrees |

When Kitsu's episode count is unknown (rare, but happens for upcoming shows), the countless pick takes an exact title match; failing one, a candidate whose part agrees with the entry's comes before one naming another part, and within each a candidate whose year matched comes before the rest, the provider's order breaking ties. Failing an exact title, when the year disproved part of the pool, only a candidate whose year matched is taken. A candidate whose listing answers with an error status gives way to the next. The frontend treats this as a soft signal and still renders the card; the lazy click path will surface a real error if the bridge picked wrong.

Two verdicts of absence are the ones the availability cache may persist as a negative row: a walk in which every search completed and nothing matched, and the probe's answer that a show it found is listed without the requested mode — a listing with no rows, or a sampled row that lacks the mode. Transport failures, upstream refusals, failed probes, and a mode nobody answered for — every sampled row saying nothing either way — are transient and write nothing, so a real show can't hide behind the negative TTL.

## Episode caps

The picked show's episode list arrives with the probe, so the availability cap is the highest listed episode number, normalised to the entry's own numbering — a continuation cour on anidb.app lists its episodes with the franchise offset, which the cap subtracts — with no second fetch and no approximation. The cap is an integer on both providers. Both keep a fractional display tag on a recap row (`number2`: `1061.5` for a One Piece recap on anidb.app, a `7.5` the listing numbers a recap with on hianime, where the row's position is its slot and the site's number its tag), and the resolver surfaces those as playable extras beside the cap rather than inside it. The two number differently: anidb.app counts continuously across a franchise's seasons, hianime within each season-split entry — which is why the cap is stamped per provider and never compared across them. A stitched pick's cap is counted across its parts, in Kitsu's numbering, and a cut spanning listing's cap is the entry's own count.

## Kitsu → MAL and AniList via the mappings endpoint

The Kitsu API exposes its known third-party ids on the `mappings` relationship of an anime resource. The backend queries `GET /anime/:id?include=mappings` and walks the `included` documents for the ones whose `attributes.externalSite` is `"myanimelist/anime"` or `"anilist/anime"`; their `attributes.externalId` values are the MAL and AniList ids.

The mappings response is not cached on its own. The detail row with its backfilled banner and the episode-thumbnail map are keyed by the Kitsu id, so a hit skips the mappings round-trip along with the AniList lookup it fed, and the row stays unambiguous whichever id space that lookup used. aniskip caches its intervals by Kitsu id, MAL id and episode, and needs the MAL id to form that key, so it reads the mappings on every request.

## What this enables

- **Trending Now** uses AniList's `TRENDING_DESC` sort, then bridges each MAL id back to a Kitsu id so the rest of the renderer can treat the row uniformly with Kitsu-sourced rows.
- **Banner backfill** — when the detail page sees a null `coverImage` from Kitsu, it asks AniList for `bannerImage`, by MAL id when Kitsu has one and by AniList id otherwise, retrying once by AniList id when AniList has no media for the MAL id. Roughly half of any week's currently-airing top 20 shows hit this fallback path.
- **Episode-thumbnail backfill** — episodes Kitsu has no still for take one from AniList's `streamingEpisodes`, reached the same way: MAL id first, AniList id when there is no MAL mapping or AniList has no media for the MAL one.
- **aniskip** lookups need the MAL id to query, and the same Kitsu→MAL mapping is reused.
- **Availability** can answer "is this in the catalogue in the requested mode?" by running the same walk the play path would and caching the verdict per `(kitsu_id, mode)`, naming the provider whose catalogue answered.
- **Continue Watching** reads each history row's show from the row itself: a watch records the Kitsu id of the page it was played from in the row's last column, and a row carrying one renders that Kitsu entry with no matching, search or enrichment — unless Kitsu answers that the entry is gone (a 404 or 410), when the row is matched as a row without an id is; any other failure to read it (the network, a 5xx, a rate limit, a timeout) renders the row unmatched for that load and leaves its id alone. A play from the detail page, the play page, an external player or Syncplay all record it; a resolve that played nothing does not, and neither does a watch whose provider title names a different cour than the Kitsu entry's slug. Rows written before history recorded the id fall back to matching them back to Kitsu. A play from a Continue card records the card's entry only when the match is one the user stands behind — the id the row recorded, or a mapping a play stored — and a play page opened from a card whose match was a guess (a title match, a search pick, a guessed mapping, or the fallback of a row whose recorded entry is gone) keeps that guess off the row too for the session's whole life — the verdict travels in the session's own URL, through its episode switches, while a session opened from the detail page records its id whatever the home page guessed — so one click cannot pin a wrong guess for good; a guessed session also writes nothing to the user's tracker accounts (AniList, MyAnimeList), while the episode's position, which stays on this computer, is kept under the guessed entry as under any other; such a row gains the id when the show is played from its detail page. The detail page's resume finds a row whose recorded entry is gone too: a 404 or 410 from Kitsu's detail fetch — only one something already asked for, such as the home page reading the row's id — marks the id gone in the cache for a year and drops the id's cached detail, unless Kitsu served the id after that fetch began; a later fetch that serves it clears the mark, from the cached detail or from Kitsu — a fetch Kitsu serves clears it in one step with caching the detail, once its banner backfill is done, and does neither if a fetch begun after Kitsu served it has been answered gone meanwhile, reporting the entry gone instead, and a fetch that cannot clear the mark fails rather than load the entry as live — the detail page's resume lookup runs beside its detail fetch, and whenever it finds no row it asks again once the fetch has served the entry, so the visit whose fetch clears the mark resumes too; for a show never watched that is one more lookup of the local history — removing the show from history takes the marks of the ids it was known by that no remaining row claims and clearing the history takes them all, and the lookup then reads the row by its mapping while that names a live entry, else by the title match the home page stored for it. A row that never recorded an id goes by its mapping alone, as before. The fallback takes the stored `(show key → kitsu_id)` mapping first. A mapping is dropped only when it is a music entry; one its count or cour doubts is passed over, and one only the provider's title doubts — the provider lists Seitokai ni mo Ana wa Aru! as "There Is Also a Hole in the Student Organization!", which shares only "student" with Kitsu's English title for it, "Even the Student Council Has Its Holes!" — is kept when a play stored it, known by the mark a play leaves beside the mapping it stores, naming the entry — any other write of the mapping, dropping it and removing the show take the mark — and passed over when a resolve guessed it; a mapping stored before plays left the mark got one once, at upgrade, when it was written within seconds after the show's watch stamp — the rule earlier versions read it by — and reads as a guess otherwise; the marking changes nothing an earlier version reads, so a downgrade opens the cache as before and ignores the marks. Past the mapping, the fallback searches Kitsu by the row's title, or by the words of the show key's slug (`there-is-also-a-hole-in-the-student-organization-10497`), and never takes a hit whose titles share too few words with the row's — under a third of either side's words, with neither title's words all in the other, and the hit not a single long word leading the row's title: Kitsu answers words it does not carry with its closest entry, Here is Greenwood for those, which shares only "is" with them. Both sides apply one rule over the shared vectors in `tests/fixtures/title-words/`, with sequel markers — season, part, cour, ordinals, numbers, roman numerals — not counted as shared words. A guess from the slug's words is stored as the mapping only while the row is still in history — a row removed while its resolution was out leaves nothing to map, and the title match the resolution would have stored is dropped the same way — and unless a play's mapping already stands, whatever doubted it: a play's mapping a read passes over on its count or cour stays until the next play of the show replaces it or it expires. A row nothing matches renders as a card with the history title, its first two characters in place of a poster, that opens a search for its title. When two providers have each left a row for the same show, the detail page and the strip pick the same row. A watch writes its moment beside its history row and in the cache, and a row ranks by the later of the two, so a cache that refused the stamp still leaves the row ranked as the watch it was; the latest moment wins, a row with one beats a row without, and when the moments do not separate two rows the further progress does, counted in Kitsu's numbering, since two providers' rows can count from different offsets.

## Failure modes the bridge tolerates

- **Kitsu has no MAL mapping** — aniskip lookup returns an empty list (the player just doesn't show the skip button). The banner and episode-thumbnail backfills use the AniList mapping instead when there is one; with neither mapping, the banner falls through to the blurred-poster placeholder and episodes keep their placeholder stills.
- **The primary provider is unreachable** — the walk runs against the next provider. A clean catalogue miss reached there — every search completed and nothing matched; an episode dead end on a show that was found persists nothing — is persisted as that provider's negative verdict, naming it, as is the availability probe's answer that the show is listed without the requested mode — unless a live positive row remembers the unreachable provider, in which case the miss is not the verdict at all — the caller sees that provider's unavailability, and nothing persists, since the row's own provider has not denied the show and an unrelated absence must not overwrite its evidence — and a persisted one is served only while that provider's gate has been seen answering since it last failed and the primary's gate is refusing — a breaker open for its cooldown, or a rate-limit pause running for its advertised window; both end on the clock, with nothing having to prove the primary is back, and at the window's end the row stops standing and the probe runs again.
- **The provider has no candidate matching any title** — the play path returns `NoResults`; the frontend renders an "isn't in the streaming catalogue" overlay instead of a cryptic backend error. A provider that answered conclusively ends the walk — the miss is not retried on the next provider — unless a positive availability record put that provider first, in which case its miss is set aside and the rest of the order is asked, the record proving the show and not every episode. A provider whose answer settles nothing — the show found, every sampled episode row silent about the requested mode — does not end it; the walk moves on.
- **The picker can't disambiguate** — with a count, the closest count within tolerance and its tie-breaks; without one, the countless order above, down to the provider's order. This is the worst case for correctness, but it's still a real entry on the provider; the user sees a sub-show rather than no show. They can pick the right one manually from search.
- **A cached play-resolution URL stops working** — the silent retry path evicts the cached row and re-resolves once before surfacing an error to the user.

## Show keys

Every store a resolve stamps holds the show key the resolve produced, as a string: history rows, the numbering sidecar beside the history file, the watched-at stamps and the reverse mapping key on it, and the resolution-cache row — keyed on the request itself — carries it in its value. anidb's key is the bare slug (`one-piece-69`), which is what every row written before there were two providers already holds, so nothing migrates. Any other provider's key carries its label as a prefix (`hianime:cowboy-bebop-1281`). The read side parses the string back: a known label names its provider; anything else — including the allanime-era ids that predate slugs — is anidb's. The renderer treats the id as opaque except for that label, which it reads to say which provider's title a title-match cache key is for: the title-match cache is keyed per provider, so two providers naming different shows identically cannot read or overwrite each other's mapping.

The cross-cour guard on the reverse mapping write compares the provider's title against Kitsu's slug convention, and it guards every provider's ids: the resolve carries no identity the guard could defer to — no Kitsu or MyAnimeList id, only the title, year and count the picker scored — so a wrongly picked sibling cour on any provider would otherwise persist the caller's Kitsu id under its slug, the row Continue Watching and resume then read. Lifting the guard for a provider wants identity provenance the resolve does not carry yet.
