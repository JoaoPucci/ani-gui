# Localization

`ani-gui` ships with four locales at MVP, chosen for markets where free-content tooling has the strongest organic demand:

| Locale | Code | Why this one |
|---|---|---|
| English | `en` | Lingua franca of anime fandom outside Japan |
| Brazilian Portuguese | `pt-BR` | Very large fandom; legal options expensive relative to local incomes |
| Latin American Spanish | `es-419` | Large fandoms across Mexico, Argentina, Chile, Peru; patchy legal catalog |
| Russian | `ru` | Crunchyroll exited Russia in 2022; legal options are sparse |

## How translation works

The frontend uses [Paraglide.js](https://inlang.com/m/gerre34r/library-inlang-paraglideJs). It compiles message bundles to type-safe TypeScript at build time — no runtime overhead, no missing keys at runtime, tree-shaken per-route.

Translation files live in `frontend/messages/`, one directory per locale and one file per surface:

```
messages/
├── en/
│   ├── app.json
│   ├── home.json
│   ├── play.json
│   ├── settings.json
│   ├── errors.json
│   └── …
├── pt-BR/...
├── es-419/...
└── ru/...
```

A message's name is its file's name, an underscore, and its key in that file: `close` in `window.json` is `window_close`, called as `m.window_close()`. `frontend/tools/build-messages.mjs` merges each locale's files into the single `messages/<locale>.json` Paraglide reads; that file is generated and not committed. The backend never returns localized text. Every error the app raises — as an HTTP error body or an SSE error event — carries a `kind` (`no_results`, `timeout`, `parse_failed`, …), a stable key (`error.search.no_results`) and the variant's own fields; the frontend chooses its copy from the `kind`, and from the fields that change what the user should do (`status` on an upstream answer, `retry_after_secs` on a rate limit, `binary` on a player that would not start, the key on a download-tool failure). See `describeError` in `frontend/src/lib/play/describe-error.ts`, and the surface-specific mappers in `frontend/src/lib/play/error-copy.ts`, `frontend/src/lib/download/failure-copy.ts` and `frontend/src/lib/settings/failure-copy.ts`. The frontend never shows the error's `detail`, which is free text for logs. Not every failed request carries the envelope: a route the router does not know, a request the HTTP layer rejects before any handler runs, and the image route's refusal of a non-`https://` URL answer with no JSON body, so the API client keeps a fallback (`{ kind: 'http', status }`) for a body that is not the envelope.

## Counts

A message that puts a word after a number gives that word the form the number needs, through Paraglide's plural variants. The value is a selector object rather than a string, and `Intl.PluralRules` for the active locale chooses the variant:

```json
"dock_active_label": [
	{
		"declarations": ["input count", "local countPlural = count: plural"],
		"selectors": ["countPlural"],
		"match": {
			"countPlural=one": "{count} download in progress",
			"countPlural=*": "{count} downloads in progress"
		}
	}
]
```

- Variants are tried in order and the first match wins, so the catch-all (`=*`) goes last.
- Russian has three integer forms: `one` (1, 21, 31…), `few` (2–4, 22–24…) and `many` (5–20, 25–30…). No integer reaches `other`, so the catch-all carries the `many` form, which is also the one a non-numeric placeholder such as `?` reads best with.
- Portuguese files 0 under `one`, but zero takes the plural ("0 episódios"). Every pt-BR message that uses the plural rule also selects on the input and matches `count=0` ahead of it.
- A literal match on the input (`"count=1"`) covers wording that changes for exactly one, such as dropping "all" from "all 1 episodes".
- A locale whose text does not inflect keeps a plain string: English "{count} aired" needs no variants where Portuguese "{count} exibidos" does.

`frontend/src/lib/i18n-plurals.test.ts` pins every counted message in every locale; a new counted message gets a row there.

## Adding a locale

1. Copy `frontend/messages/en/` to a new directory named by the [BCP 47](https://www.rfc-editor.org/rfc/bcp/bcp47.txt) tag (e.g. `pl`, `tr`, `id`).
2. Translate every value. Keys remain identical to the English bundle. A message with plural variants gets the variants the new language needs, not a copy of English's two — see [Counts](#counts) — and the new locale gets its forms in `frontend/src/lib/i18n-plurals.test.ts`, whose table names each locale.
3. Add the tag to `frontend/project.inlang/settings.json` under `locales`.
4. Add the locale to the language picker: the `LOCALES` list in `frontend/src/routes/settings/+page.svelte`. The e2e smoke test (`electron/e2e/smoke.spec.ts`) checks that the picker offers the shipped locales; add the new one to what it expects.
5. Add the locale to the table in `electron/lib/main-messages.cjs`. The Electron main process shows two dialogs of its own — the one a failed startup ends with, and the prompt on a quit with downloads running — at moments when no page can show them, so their text cannot come from the renderer's bundle. `pnpm test` in `electron/` fails while the table and `frontend/project.inlang/settings.json` list different locales, or while any locale is missing an entry.
6. Check the new bundle against the English one by hand. Nothing fails on a key the new locale lacks: the compile gives that locale the English message for it.
7. Add a translation-attribution line to `docs/i18n.md` under the candidates table below.

Adding a locale is a translation PR with three places to register it: the inlang settings, the picker, and the main process's table.

## What is and isn't translated

**Translated** — every UI string the user sees: labels, buttons, error messages, empty states, tooltips, settings, date/time formatting (via `Intl.*`).

**Not translated**:

- **Anime titles**: the user picks a title-language preference in Settings (English / Romaji / Native). The default differs by UI locale: `en` and `pt-BR` default to English (Portuguese metadata is sparse on Kitsu/AniList); `es-419` defaults to English; `ru` defaults to Romaji.
- **Provider names** (wixmp, hianime, filemoon, etc.) — proper nouns.
- **Genre tags** as raw strings — Kitsu returns them in English; we render them with locale-specific subtitling where applicable.

## RTL support

Out of scope at MVP. No Arabic or Hebrew locale is shipping yet. However, the codebase uses logical CSS properties (`margin-inline-start`, `padding-inline-end`, `text-align: start`) so adding an RTL locale becomes a translation-only PR + a `dir="rtl"` flip on `<html>`. The `tests/arch/i18n.sh` invariant test enforces no use of `margin-left` / `padding-left` / etc.

## Pseudo-localization

Dev builds expose a `pseudo` locale that wraps every translated string in markers and inserts accents:

```
"trending": "Trending Now"
   ↓ pseudo
"trending": "[!! Tréndíñg Nöw !!]"
```

Hardcoded strings show through unwrapped, making them easy to spot. Activate via `?locale=pseudo` in the dev server URL.

## Phase-2 candidate locales

Not blocking the MVP, but the i18n architecture supports adding any of these as translation-only PRs:

| Candidate | Code | Why eventually |
|---|---|---|
| Polish | `pl` | Large fandom, fewer legal options than Western Europe |
| Turkish | `tr` | Large youth fandom, weak legal Turkish-subbed catalog |
| Indonesian | `id` | Massive market, strong free-streaming culture |
| Vietnamese | `vi` | Large audience, weak legal availability |
| Ukrainian | `uk` | Similar dynamics to Russian, separate locale for cultural reasons |
| Arabic | `ar` | Significant audience; **requires RTL enablement first** |
